Audit · 2026-11-17 · skills-repo

Is our testing and CI/CD approach optimal?

A strong delivery loop with weaker gates than it looks. Merging is fast and well observed, but several checks that look like gates are not, a lot of CI runs are noise, and the deploy path has nothing watching production after promotion. Most of the fixes are cheap. The biggest gap is that most of the browser test suite never runs.

Read-only audit of the repo, the Actions run history, merged PRs, the master ruleset and the production-error issues. It builds on the 2026-11-15 regression audit, whose findings were mostly fixed this week.

What is working

118PRs merged in 30 days, 0 reverts
30 minmedian from PR open to merge (p90 8 h)
~3 minfor the 876-file unit chain in CI
0.4 hmedian time to close a production-error issue (8 of 9 closed)

This week added two real signals: the wiring smoke test (pws-s1) and Scenario A and B running on the pull request's own build (sep-s1), proven by a deliberate break that turned a job red. The staging deploy is correctly skipped for bookkeeping-only pushes.

What is not

A. Gates weaker than they look

1
Most of the browser suite never runs on a PRhigh

The check "Playwright E2E smoke tests" reads audit.e2e_tests from context.yml. The key is absent, so the job logs "E2E skipped (opt-in flag not set)" and reports green in about 15 seconds. 88 of 94 Playwright spec files, the local-mocked UI, layout and journey specs, are not exercised. Measured by a one-off trial run: 308 tests in 15.7 minutes, 186 passed, 90 failed, 32 skipped (67% of those that ran). 45 of the 95 spec files have at least one failure, the worst being the design canvas render, reference upload, pod creation and right-panel layout specs; 48 pass completely. It needs triage into a stable core and a quarantined remainder before it can be required. One run only, so flakiness is not yet separated from genuine breakage.

2
"Lint, typecheck, test, build" overstates what it checksmedium

lint is node --check (syntax only), typecheck only requires each file, build checks that server.js exports createApp. No ESLint, no TypeScript, no coverage.

3
The unit chain is not a required checkhigh

The ruleset requires the assurance gate, Scenario A, Scenario B and a pull request. The job that runs all 876 test files can be red and the PR still merges. Branches need not be up to date, there is no merge queue, and direct pushes to master are allowed by bypass.

4
Nothing verifies production after promotionmedium

No Fly health checks, no post-promotion check, no automated rollback. Production builds its own image from the commit rather than promoting the one staging ran. The error chain reports failures within minutes, which softens this.

5
131 old production approvals are still waitingmedium, to verify

Each promote job builds its own run's commit, so approving an old one should deploy an old commit over newer production code. Reasoned from the workflow, not tested. Superseded runs should cancel themselves.

6
Every bookkeeping push to master starts workflows that add nothinghigh volume

About 74% of master commits (442 of the newest 600) touch only artefacts/, workspace/ or pipeline-state.json. Each push starts dreaming, Trace Commit and Vulnerability Check, and until recently the Pages and Fleet workflows. About 440 runs in 40 hours, and a red mark on most master commits.

7
Retry until green on the old real-staging designbaseline

In E2E Tests (Playwright), 61 of 213 runs (29%) were re-run and 50 of those ended green. Re-measure now that the scenarios test the PR's build; it should fall sharply.

8
Staging Deploy fails 21% of the timemedium

10 of 47 completed runs failed, and 8 of the 10 were the @mocked smoke test.

9
28% of test files read repository text, not behaviourmedium

246 of 876 files read artefacts, workflows, skills or templates. They guard governance rules, but they also act as change-detectors: five guards had to be reversed for one workflow change this week.

C. Process overhead and missing coverage

10
Bookkeeping dominates the historylow

It buys an audit trail but each commit has a CI cost (finding 6) and none is reviewed. Path filters fix the cost without changing the practice.

11
Security tooling is minimalmedium

npm audit only: no Dependabot, no code scanning, no secret-scanning workflow. Repository settings not visible in the files may add some; check Settings, Code security.

12
A fresh environment did not boot cleanlymedium

Against an empty database the startup migrations race and run out of order (three boots to settle), and the durable chat table needs a manual script. A new environment or disaster recovery would hit this.

13
The real model and production configuration are never testedlow

Everything uses the mock gateway. Production secrets, the real model and the real database are only exercised by users and the error chain.

14
34 skipped specs and no coverage measurelow

The Stripe hosted checkout is among the skipped. Without coverage there is no way to see which code is untested.

Recommendations, in order

  1. Find out what the browser suite is worth. Run the 88 local-mocked specs once in CI on a trial branch, record pass, fail and time, then require a fast stable core and quarantine the rest.story, starting
  2. Require the unit chain and name it honestly. Ruleset change by the operator; then rename the job or add real lint.operator
  3. Stop the bookkeeping noise. Path-filter Trace Commit and Vulnerability Check off bookkeeping paths, run the vulnerability check on dependency changes and on a schedule, and finish the dreaming fix.story, starting
  4. Harden the deploy path. Fly health checks, a read-only post-promotion check of /health and /version, auto-cancel superseded promotions, later promote the staging image.
  5. Fix fresh-environment boot (migration order and the manual chat-table script) and test that a fresh database settles in one boot.
  6. Add a security baseline: Dependabot, CodeQL and secret scanning.operator and workflow
  7. Reduce change-detector tests by moving workflow-text assertions into one contract file per workflow.
  8. Add non-blocking coverage reporting before deciding on any threshold.

Method and limits

  • GitHub returns at most 1,000 runs, so the all-workflow view covers only 2026-11-15 to 11-16. The PR-gate view covers 2026-10-17 onward (1,241 runs). Durations of re-run jobs include waiting, so medians are used.
  • Test timings come from one full local Windows run; CI's unit chain takes about 3 minutes.
  • Test classification is by static pattern matching, so counts are approximate.
  • The 88 local-mocked specs were not run for this audit.
  • Finding 5 is reasoned from the workflow and not tested.
  • No cost in minutes or money was computed, and the Actions plan was not checked.
