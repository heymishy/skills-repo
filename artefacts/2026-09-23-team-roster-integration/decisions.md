## `/review` run 1: MC-SEC-01 gap found in rtri-s2/rtri-s3, fixed by adding explicit safe-rendering ACs (2026-09-24)

**Context:** `/review` run 1 (all 5 categories, all 3 stories) found `rtri-s1` (read API) passing clean, but `rtri-s2` (pod-manager picker) and `rtri-s3` (`/team/members` list) both failing Category E — Architecture compliance. Neither story's ACs required the real identity string (`person_identities.identity_key`: GitHub login, Google email, or email/password email — externally-influenced, not a fixed literal) to be rendered safely when displayed. This is the same risk class as `ep4-s1`'s own real, recently-fixed Critical stored-XSS vulnerability (commit `6adfb5b2`, a DB-sourced identity string rendered via unescaped client-side string concatenation), and directly violates MC-SEC-01 ("No user-supplied content in innerHTML without sanitisation"), a mandatory constraint in `.github/architecture-guardrails.md`.

**Decision:** Added `rtri-s2` AC6 and `rtri-s3` AC5, each requiring the real identity string to be rendered via safe DOM construction (`createElement`/`textContent`) or template auto-escaping — never raw string concatenation into HTML — matching `ep4-s1`'s own fixed pattern, and each verified by a test asserting on a payload identity string (containing `<`, `>`, `'`) rather than a clean-looking one. Also added a corresponding line to each story's Security NFR cross-referencing the new AC. Fixed directly in the story artefacts rather than only noted here, since this is a pre-implementation finding (no code yet to patch) and the fix is narrow, well-understood, and directly traceable to a proven precedent in this same codebase.

**Rationale:** Given how consequential `ep4-s1`'s real Critical XSS bug was, catching this at `/review` — before any code exists — is exactly what this pipeline stage is for. Fixing the story artefacts directly (rather than deferring to a RISK-ACCEPT or a post-hoc code-review catch) keeps the ACs themselves the source of truth a coding agent and its test-plan will build against, consistent with this feature's own review discipline established across `rtri-s1`'s LOW findings.

**Story:** `rtri-s2`, `rtri-s3` — AC6/AC5 added respectively, NFR Security line updated; no scope change otherwise. `/review` re-run (run 2) to confirm the gap is closed.

**Note:** This feature's `decisions.md` should have been created at discovery approval time per CLAUDE.md's mandatory rule (any feature making an architectural decision needs one) — ADR-025 tenant-isolation and ADR-026 reuse-pattern decisions were made during `/definition` without a corresponding entry here. Created now, at first real decision point; not backfilling the earlier architectural citations retroactively since they are already fully documented in the stories' own Architecture Constraints sections.

## `rtri-s3` AC5 wording corrected during `/test-plan` prep: no templating engine exists in this codebase (2026-09-24)

**Context:** While preparing `rtri-s3`'s test plan, read `routes/team-management.js`'s real `handleGetTeamMembers` implementation directly — this page is built via manual string concatenation (`'<h1>Team members</h1>' + '<form...'`), not a templating engine with auto-escaping. `utils/html-shell.js` already exports `escHtml()` and it is already this codebase's real, established mechanism for escaping identity-adjacent values into concatenated HTML (used for `login`/`initial` elsewhere in the same file).

No substantive change — AC5's requirement (real identity strings must never be concatenated into HTML unescaped) and its MC-SEC-01 mapping are unchanged, so this does not require a `/review` run 3; it only makes the AC's implementation guidance accurate for whoever picks up `/implementation-plan`.
**Story:** `rtri-s3` — AC5 and Security NFR wording only, no scope or substance change.

## `rtri-s2` found during `/test-plan` prep: "pod role" and "team role" are two unrelated vocabularies with no source for the former; AC7 added (2026-09-24)

**Context:** While writing `rtri-s2`'s test plan, read `pod-manager.html` and `pod-store.js` directly to model the picker's real field shapes. `pod_members.role_id` (conductor/engineer/architect/product) is a person's role *within a specific pod* — entirely sourced from `ORG_ROSTER`'s hardcoded fixture today (`VALID_ROLES` constant in `pod-manager.html`, distinct from the identically-named but differently-valued `VALID_ROLES` in `team-management.js`, which is `team_memberships.role`: admin/engineer/product/viewer, a tenant-wide permission role). `rtri-s1`'s real roster endpoint returns only the latter. No real person has a pod role anywhere in this app, and no UI exists to assign one — this is not a case of "wrong field name pointing at something real," it's a genuine missing capability the story's original ACs (AC1/AC2/AC5) silently assumed away by treating the fetched roster as a drop-in replacement for `ORG_ROSTER`'s fuller shape.

**Options considered (put to the operator directly, given the real UX and scope trade-off):** (1) default every real member to a fixed pod role on add, no selector — smallest change, but silently assigns a role nobody chose; (2) add a minimal pod-role selector at add-time — more correct, small bounded new UI; (3) drop the role-tab/chip mechanism entirely for real data — removes an existing, already-shipped feature rather than adapting it.

**Decision (operator's own choice):** Option 2. Added AC7: a pod-role selector (reusing the existing `VALID_ROLES` constant/values, no new role vocabulary) is presented when adding a real member, and the selected value — never anything from `rtri-s1`'s response — is written to `pod_members.role_id`. Amended AC1 (no pod-role chip/tab-group until assigned), AC2 (pod role now explicitly selected, not implied), and AC5 (the "Available" panel's role-tab filter has nothing to filter by for real, role-less members — its exact treatment there is left to `/implementation-plan`, constrained to "never show a wrong/stale role, never throw"). Complexity rating stays at 2 — AC7 itself is small and well-understood (a `<select>` before an "Add" confirms); the story's real ambiguity remains AC4's cross-story verification, unchanged by this addition.

**Rationale:** This is a genuine AC-completeness gap that `/review` run 1/2 did not catch, because Category E (Architecture compliance) — the category that caught the MC-SEC-01 gap above — does not cover functional-data-shape mismatches; that falls under Category C (AC quality) / D (Completeness), which passed both prior runs without noticing the picker's fuller field shape (`userId`/`name`/`roleId`) was never reconciled against the real roster's shape (`identity`/`role`). Catching this now, before `/implementation-plan`, is exactly why `/test-plan` requires reading the real code the story will touch, not just the story text.
**Story:** `rtri-s2` — AC7 added; AC1, AC2, AC5, Complexity Rating, and Out of Scope amended. Re-running `/review` (run 3, all 5 categories) before continuing `/test-plan`.
