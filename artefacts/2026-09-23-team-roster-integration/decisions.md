**Rationale:** Caught before `/implementation-plan`, matching this whole feature's own now-repeated pattern of a story's Architecture Constraints being written before the real touch points are actually investigated. No AC text changes — the observable behaviour AC1-AC5 describe is identical; only the "how" (which adapter, how the provider value gets there) was wrong.

## Live Chrome verification during `rtri-s1`'s DoD found `person_identities` is never populated on first login — new story `rtri-s4` added to fix it (2026-09-24)

**Context:** Per the operator's explicit request ("Confirmed dod with chrome?"), performed a real live check on `wuce-staging.fly.dev` beyond the automated evidence already in `rtri-s1`'s DoD. Signed in via real GitHub OAuth as `heymishy` (already-authorized session, no credentials entered), confirmed AC5 live (unauthenticated tab redirected to sign-in), then confirmed `GET /api/team/members` returns `200 {"members":[]}` for the authenticated tenant. Added `heymishy` as their own tenant's teammate via the existing admin form (`/team/members`) — a real `team_memberships` row was created (`{"personId":1,"tenantId":"heymishy","role":"engineer","updated":true}`), confirmed via the real API response, not assumed. Re-checked the roster: still `{"members":[]}`.
**Investigation:** `listTeamMembers`'s INNER JOIN (exactly matching its own AC2 spec) silently omits any `team_memberships` row with no matching `person_identities` row. Grepped every `INSERT INTO person_identities` write site in the real codebase: only `identity-links.js`'s `linkIdentity` (tir-s2's explicit, opt-in "link a second sign-in method" feature) and the team/client invite-acceptance flows (`team-invitations.js`, `client-invitations.js`) ever write to it. Confirmed directly by reading `routes/auth.js` and `routes/auth-email.js`: neither writes to `person_identities` on login. Confirmed `user-roles.js`'s legacy migration backfill (`_backfillOne`) doesn't either. This means a tenant's own owner — and anyone added via the plain "add teammate by identity" admin form (`tir-s3`) rather than a real invite — has no `person_identities` row and is invisible to `listTeamMembers`, exactly as live-reproduced above.
**Decision (operator's own choice, given 3 options: accept as-is, fix via a login backfill, or fix via widening the join):** Fix via a proper first-login `person_identities` backfill. New story `rtri-s4` added to the `real-team-roster` epic (not a change to `rtri-s1`'s own already-merged, already-DoD-complete code) — see `stories/rtri-s4.md`.
**Scope boundary clarification (important — avoids an apparent conflict with the epic's own Out of Scope):** the epic's Out of Scope explicitly rules out "auto-creating `people`/`team_memberships` rows on raw login — membership stays invite/add-driven." `rtri-s4` does NOT do this — it writes only a `person_identities` row (identity bookkeeping: "this identity_key belongs to this person_id"), never a `team_memberships` row. No tenant membership is created or changed by this fix; it only makes an EXISTING, legitimately-created membership (via invite or the admin add-teammate form) resolvable by `listTeamMembers`, for identities that already have one.
**Rationale:** This is exactly the kind of gap this session's discipline exists to catch before it compounds — `rtri-s2`/`rtri-s3` were about to build real UI on top of a read path that, as shipped, returns empty for the most common real-world case (a tenant's own owner, before any invite is sent). Caught only because the operator asked for a genuine live check beyond automated evidence, not because any outer-loop stage (discovery/definition/review) flagged it — `rtri-s1`'s own AC2 was written and reviewed against a correct-in-isolation spec that nobody traced through to "what does this mean for the very first real user."

## `rtri-s1` `/implementation-plan` prep: verified the DoR contract's wiring assumption against the real, DIFFERING sibling route family — confirmed correct, but flagging the specific pitfall a coding agent could fall into (2026-09-24)

**Context:** The DoR contract (`dor/rtri-s1-dor-contract.md`) specifies the new `GET /api/team/members` endpoint mirrors `GET /api/pods`'s registration shape (`authGuard` + `_pshPool`, standalone route, plain exported handler function) — this was an unverified assumption at DoR time, written without checking the real, EXISTING sibling routes on the SAME path family (`/team/members`, `POST /api/team/members`, `/team/invites/new`, `POST /api/team/invites`, all `tir-s3`/`wsi-s1`/`wsi-s6`). Reading `server.js` directly before task-planning (lines 3640-3688, plus the module-level declaration at lines 130-134) found those existing `/api/team/*` routes are gated by `requireAdmin` (not `authGuard`), wired through a module-level `_teamManagementHandlers` factory bound to `_userRolesPool` — a real-Postgres-only pool with **no `NODE_ENV=test` fallback** (explicit code comment: "assigned inside the DATABASE_URL block... real-Postgres-only, no NODE_ENV=test fallback either"), with every handler guarded by an explicit `if (!_teamManagementHandlers) { 503 }` check.

**Why this matters:** Had the coding agent pattern-matched on "this is a `/api/team/*` route, in `team-management.js`, so it should use the same wiring as its siblings" — a reasonable default without this investigation — it would have produced two real, breaking defects: (1) `requireAdmin` would incorrectly lock the roster to admins only, breaking `rtri-s2`'s picker for its own stated persona ("product owner or feature lead," not necessarily an admin); (2) the real-Postgres-only wiring (503 in test mode) would make the endpoint untestable via the fake-pool convention every test plan in this feature already commits to, and unusable in CI.

**Decision:** Confirmed the DoR contract's `/api/pods`-pattern assumption is correct and must be followed exactly, NOT the same-file sibling routes' pattern: `handleGetTeamMembersApi(req, res, pool)` must be a plain exported function in `routes/team-management.js` — explicitly NOT added inside the `createTeamManagementHandlers(pool)` factory closure — registered in `server.js` as its own standalone `authGuard(req, res, async () => { await handleGetTeamMembersApi(req, res, _pshPool); })` block, separate from the existing `_teamManagementHandlers`-gated `else if` blocks. This constraint is made explicit as its own implementation-plan task step specifically because the "obviously right" pattern-match (same file, same domain, same team) would have been wrong here.
**Story:** `rtri-s1` — no AC/scope/contract change; this entry records the verification and the specific pitfall, carried into `/implementation-plan`'s task wording.

**Addendum — 4th touch point found during planning:** `src/web-ui/adapters/fake-test-db.js` needs a new query-pattern branch for `listTeamMembers`'s JOIN query, or the endpoint silently returns empty results whenever the real server runs against `createFakeTestDb()` (`NODE_ENV=test`/CI, no `DATABASE_URL`) — beyond the DoR contract's original 3-file estimate. Added as its own Task 4 in the implementation plan, verified by a dedicated test separate from this story's own 5 AC tests (which use their own isolated fake pool and would all still pass without this fix, since they never exercise `createFakeTestDb()` directly). A normal estimate-refinement at `/implementation-plan` time, not a scope change.

## `/review` run 1: MC-SEC-01 gap found in rtri-s2/rtri-s3, fixed by adding explicit safe-rendering ACs (2026-09-24)

**Context:** `/review` run 1 (all 5 categories, all 3 stories) found `rtri-s1` (read API) passing clean, but `rtri-s2` (pod-manager picker) and `rtri-s3` (`/team/members` list) both failing Category E — Architecture compliance. Neither story's ACs required the real identity string (`person_identities.identity_key`: GitHub login, Google email, or email/password email — externally-influenced, not a fixed literal) to be rendered safely when displayed. This is the same risk class as `ep4-s1`'s own real, recently-fixed Critical stored-XSS vulnerability (commit `6adfb5b2`, a DB-sourced identity string rendered via unescaped client-side string concatenation), and directly violates MC-SEC-01 ("No user-supplied content in innerHTML without sanitisation"), a mandatory constraint in `.github/architecture-guardrails.md`.

**Decision:** Added `rtri-s2` AC6 and `rtri-s3` AC5, each requiring the real identity string to be rendered via safe DOM construction (`createElement`/`textContent`) or template auto-escaping — never raw string concatenation into HTML — matching `ep4-s1`'s own fixed pattern, and each verified by a test asserting on a payload identity string (containing `<`, `>`, `'`) rather than a clean-looking one. Also added a corresponding line to each story's Security NFR cross-referencing the new AC. Fixed directly in the story artefacts rather than only noted here, since this is a pre-implementation finding (no code yet to patch) and the fix is narrow, well-understood, and directly traceable to a proven precedent in this same codebase.

**Rationale:** Given how consequential `ep4-s1`'s real Critical XSS bug was, catching this at `/review` — before any code exists — is exactly what this pipeline stage is for. Fixing the story artefacts directly (rather than deferring to a RISK-ACCEPT or a post-hoc code-review catch) keeps the ACs themselves the source of truth a coding agent and its test-plan will build against, consistent with this feature's own review discipline established across `rtri-s1`'s LOW findings.

**Story:** `rtri-s2`, `rtri-s3` — AC6/AC5 added respectively, NFR Security line updated; no scope change otherwise. `/review` re-run (run 2) to confirm the gap is closed.

**Note:** This feature's `decisions.md` should have been created at discovery approval time per CLAUDE.md's mandatory rule (any feature making an architectural decision needs one) — ADR-025 tenant-isolation and ADR-026 reuse-pattern decisions were made during `/definition` without a corresponding entry here. Created now, at first real decision point; not backfilling the earlier architectural citations retroactively since they are already fully documented in the stories' own Architecture Constraints sections.

## `rtri-s2` found during `/test-plan` prep: "pod role" and "team role" are two unrelated vocabularies with no source for the former; AC7 added (2026-09-24)

**Context:** While writing `rtri-s2`'s test plan, read `pod-manager.html` and `pod-store.js` directly to model the picker's real field shapes. `pod_members.role_id` (conductor/engineer/architect/product) is a person's role *within a specific pod* — entirely sourced from `ORG_ROSTER`'s hardcoded fixture today (`VALID_ROLES` constant in `pod-manager.html`, distinct from the identically-named but differently-valued `VALID_ROLES` in `team-management.js`, which is `team_memberships.role`: admin/engineer/product/viewer, a tenant-wide permission role). `rtri-s1`'s real roster endpoint returns only the latter. No real person has a pod role anywhere in this app, and no UI exists to assign one — this is not a case of "wrong field name pointing at something real," it's a genuine missing capability the story's original ACs (AC1/AC2/AC5) silently assumed away by treating the fetched roster as a drop-in replacement for `ORG_ROSTER`'s fuller shape.

**Options considered (put to the operator directly, given the real UX and scope trade-off):** (1) default every real member to a fixed pod role on add, no selector — smallest change, but silently assigns a role nobody chose; (2) add a minimal pod-role selector at add-time — more correct, small bounded new UI; (3) drop the role-tab/chip mechanism entirely for real data — removes an existing, already-shipped feature rather than adapting it.

**Decision (operator's own choice):** Option 2. Added AC7: a pod-role selector (reusing the existing `VALID_ROLES` constant/values, no new role vocabulary) is presented when adding a real member, and the selected value — never anything from `rtri-s1`'s response — is written to `pod_members.role_id`. Amended AC1 (no pod-role chip/tab-group until assigned), AC2 (pod role now explicitly selected, not implied), and AC5 (the "Available" panel's role-tab filter has nothing to filter by for real, role-less members — its exact treatment there is left to `/implementation-plan`, constrained to "never show a wrong/stale role, never throw"). Complexity rating stays at 2 — AC7 itself is small and well-understood (a `<select>` before an "Add" confirms); the story's real ambiguity remains AC4's cross-story verification, unchanged by this addition.

**Rationale:** This is a genuine AC-completeness gap that `/review` run 1/2 did not catch, because Category E (Architecture compliance) — the category that caught the MC-SEC-01 gap above — does not cover functional-data-shape mismatches; that falls under Category C (AC quality) / D (Completeness), which passed both prior runs without noticing the picker's fuller field shape (`userId`/`name`/`roleId`) was never reconciled against the real roster's shape (`identity`/`role`). Catching this now, before `/implementation-plan`, is exactly why `/test-plan` requires reading the real code the story will touch, not just the story text.
**Story:** `rtri-s2` — AC7 added; AC1, AC2, AC5, Complexity Rating, and Out of Scope amended. Re-running `/review` (run 3, all 5 categories) before continuing `/test-plan`.
