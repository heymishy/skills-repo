# Decisions — canvas-render-and-story-extraction-fix

## D1 — `listArtefacts` checks the local filesystem before the GitHub API

**Date:** 2026-07-26
**Context:** `listArtefacts()` only ever queried the GitHub REST API, gated on `WUCE_REPOSITORIES` — an env var never set on any deployment this repo actually uses (`fly.staging.toml`, `fly.toml` both omit it). This made the feature-index page always report `noArtefacts: true` on staging, contradicting the kanban board's Postgres-derived artefact-count badge, which was accurate.
**Decision:** `listArtefacts(featureSlug, token, repoRoot)` now checks the local filesystem first via the pre-existing (previously dead-code) `listLocalArtefacts()`, using `repoRoot` resolved through the same `getRepoRoot(req)` / `COPILOT_REPO_PATH` convention used throughout `server.js` and `journey.js`. The GitHub-API path is kept as a fallback, used only when no local `artefacts/<slug>` directory exists — preserving behaviour for any future multi-repo / no-local-checkout deployment mode.
**Rationale:** the web-ui process in every deployment this repo actually runs (local dev, staging) already has a full local checkout of the repo it's serving artefacts for — that's the same assumption `COPILOT_REPO_PATH` already relies on elsewhere. Preferring the data source that's actually populated over the one that's structurally never configured is the direct fix; keeping the GitHub-API path as a fallback rather than deleting it avoids foreclosing a real future deployment shape without evidence it's needed.

## D2 — three-independent-artefact-mechanisms drift: fix the symptom now, flag the systemic cause as an open question

**Date:** 2026-07-26
**Context:** the artefact-listing mismatch is one instance of a broader pattern: at least three call sites answer "what artefacts does feature X have" independently — `listArtefacts` (GitHub API), `listLocalArtefacts` (filesystem, now wired), and `getArtefactCountsForJourneys` (Postgres, powers the kanban badge). Nothing keeps these consistent; each was added for a different surface at a different time with no shared source of truth. The operator explicitly asked (2026-07-26) whether skill/CLI checks should be tightened to prevent this class of deviation, and separately floated a concrete direction: "a mechanism to sync postgres, redis, and file-based updates."
**Decision (scope for THIS fix):** wire the local-filesystem path into the one broken call site (`listArtefacts`/`handleGetFeatureArtefacts`) rather than attempt a full reconciliation of all three mechanisms in this short-track fix. Log the systemic question as an open item rather than silently resolving or silently dropping it.
**Rationale / what's deferred:** unifying all three artefact-enumeration mechanisms behind one canonical source (whether that's "Postgres is the index, filesystem is the content" or a sync/reconciliation job across Postgres/Redis/file state) is a real architectural decision with its own tradeoffs (consistency model, latency, failure modes when one store lags another) that deserves its own discovery/definition pass, not a same-session retrofit onto an unrelated staging bug report. See `workspace/capture-log.md` (2026-07-26, signal-type: gap) for the full signal captured for a future `/discovery` pass. Candidate framing for that future discovery: should there be one canonical "artefact registry" adapter that every surface (feature-index page, kanban badge, resume-links, `/trace`) reads from, with Postgres as the index and the filesystem as the content-of-record — replacing today's N independent readers with 1 writer-of-truth and N thin readers?

**Correction (2026-07-26, same day, post-alrf-s1 staging verification):** the "filesystem is the content-of-record" half of the framing above is wrong for this deployment topology, and is superseded by D3 below. `.dockerignore` deliberately excludes `artefacts/` from the built image, and `fly.staging.toml` has no persistent volume — local disk on `wuce-staging` is wiped on every redeploy (roughly 8 times in one day during this session). Filesystem can be canonical for a developer's own local checkout (where `COPILOT_REPO_PATH` points at a real, persistent clone), but it cannot be canonical for the deployed web-ui surface. D3 below replaces "filesystem is canonical" with "git/GitHub is canonical" for that surface.

## D3 — recommended durable-store architecture: git/GitHub as the single canonical artefact store, Neon Postgres as a read-through cache/index, no Fly volume

**Date:** 2026-07-26
**Context:** operator asked (a) whether Fly or (Neon) Postgres has a clear free-tier winner for durable artefact storage, and (b) what the best architecture is for performance and for aligning the platform's two real surfaces — the IDE/CLI, where artefacts are real git-committed `.md` files under `artefacts/`, and the web UI (SaaS), which currently has no durable store of its own (see the D2 correction above).
**Findings that inform this:**
- **Fly has no free tier for durable storage.** Fly removed its included free allowances in 2024; Fly Volumes are billed per GB-month with no free quota. It is not a contender for "free."
- **Neon (Postgres) does have a real free tier** (this repo already uses it for staging — `bri-s2.2-neon-staging-branch`), and **Upstash (Redis)** likewise (`bri-s2.3-upstash-staging-instance`) — both already provisioned, both genuinely free at this project's scale (artefact markdown is small text; thousands of stories would still fit well inside Neon's free storage quota).
- **So "Postgres vs Fly" isn't actually the right comparison** — Fly was never a real option for durable storage here, free or otherwise. The real question is what Postgres's *role* should be, given a second, already-canonical store already exists: git.
- **This codebase already has a working GitHub-Contents-API commit-on-write pattern** for at least two artefact-touching operations (`adapters/sign-off-writer.js`, `adapters/annotation-writer.js`), and the *original* (broken) `listArtefacts()` was GitHub-API-based too — it was reaching for the right answer, just never had `WUCE_REPOSITORIES` configured to make it real.
**Decision (recommendation, not yet implemented):** git/GitHub should be the single canonical store for artefact *content*, for both surfaces — this is already true for the IDE/CLI surface by construction (a real git checkout, real commits, real PR review, which is the whole point of this platform's "hash-verified instruction sets" premise per `CLAUDE.md`'s Product context). The web-ui surface's artefact-creation path should commit to the same repo via the GitHub Contents API (extending the pattern `sign-off-writer.js`/`annotation-writer.js` already establish), rather than writing to local disk. Neon Postgres's role is a **read-through cache/index** — exactly the role it already plays for the kanban board's artefact-count badge (`getArtefactCountsForJourneys`) — refreshed on write (the write path already knows what it just committed) rather than queried cold from GitHub on every page load. This gives git-level durability and versioning with Postgres-level read latency, and needs no Fly volume at all.
**Why not "Postgres stores full content, sole source of truth":** breaks the dual-surface alignment this platform is built around — IDE/CLI users need real `.md` files under git for diff/PR review/hash verification; making Postgres canonical would turn the git-committed files into a stale mirror requiring its own sync-back job, recreating the exact bidirectional-sync complexity already argued against in D2.
**Why not a Fly volume:** not free; and even if it were, it wouldn't solve dual-surface consistency — IDE commits still land in git regardless of any Fly volume, so a volume-backed disk store would still need reconciling against git as a second, independent store (the same class of bug D2/D1 just fixed).
**Not yet implemented:** this is a recommendation surfaced for the operator's direction, not a decision executed in this session — migrating the web-ui's artefact-write path to GitHub-API-based commits (vs. local disk) is a real, non-trivial change (latency per write, GitHub API rate limits at scale, error handling for a failed remote commit) that deserves its own discovery/definition pass rather than a short-track retrofit.
