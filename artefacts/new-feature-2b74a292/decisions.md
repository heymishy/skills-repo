## `ep4-s1` `/branch-setup`: baseline acknowledged, 1 pre-existing/environmental failure; DoR built against a fictional `routes/features.js`/`pod-assignment-manager.js`/"Feature settings page" architecture; real touch points identified, real gap is larger than any prior story in this feature (2026-09-22)

**Baseline:** `node scripts/run-all-tests.js` on the freshly-created `feature/ep4-s1` worktree (built from latest `master`, including the fully-merged, fully-DoD-complete `reversibility-audit-trail` epic) showed 1 failure: `tests/check-p3.5-validate-trace.js` — the same pre-existing/environmental failure acknowledged repeatedly across every other worktree this session (695 files run, 1 failed). Acknowledged as pre-existing, proceeding per `/branch-setup`'s Option 2.

**Architecture investigation (before `/implementation-plan`):** `ep4-s1`'s DoR assumes: a `src/web-ui/routes/features.js` file with feature-settings GET/POST handlers, a new `src/web-ui/modules/pod-assignment-manager.js` module, a `features-settings.html` page reachable via "Feature A2 settings", and — per the story's own Architecture Constraints — that `getFeatureCollaborators()` is already "the canonical builder that handles multi-pod resolution" under ADR-026. None of this exists. This is the 7th+ occurrence of this feature's now-established fictional-DoR pattern (see `ep3-s1-dod.md`'s running count) — but this is the largest gap yet: every prior instance was a wrong file/table/field name pointing at something real; this one assumes an entire page that has never existed anywhere in the app.

**What the real code actually does, verified directly:**
1. **No per-feature settings page exists anywhere.** Grepped the whole `src/web-ui` tree for "feature settings" / "assign pod" / "features.js" — zero matches outside the fictional DoR text itself. `routes/features.js` does not exist; feature (journey) creation lives in `routes/products.js` (`ep1-s3`'s own real touch point, confirmed in `ep3` epic's decisions), and per-journey pages live in `routes/journey.js`. Neither file has any "settings" section today.
2. **`getFeatureCollaborators()` (`feature-collaborator-store.js`) is NOT a multi-pod resolution builder — it's a flat `SELECT ... WHERE feature_id = $1` over `feature_collaborators`.** No union logic, no removal/override handling, no awareness of `pod_assignments` at all. It has 3 real, already-shipped call sites depending on its current flat-read shape: `_getCollaboratorsPresencePayload` (ep2-s1 presence sidebar), `handleGetJourneyCollaboratorsPresence`, and `handlePostJourneyApprove`'s approver-role lookup (ep2-s3/ep3-s3). Any change to this function's behaviour must not break those three.
3. **`feature_collaborators` is a write-time MATERIALIZED table, not a read-time computed view.** `populateFeatureCollaboratorsFromPod` (called once, from `routes/products.js`, at feature-creation time when a product has a default pod) INSERTs one row per pod member. There is no existing "recompute on demand" path — the established pattern in this codebase is: write the resolved set once, read it flatly forever after. This is the real precedent `ep4-s1` should extend (write-time union, not a dynamic per-request resolver), consistent with ADR-026's actual principle (reuse an existing entity/pattern rather than introduce a new one) — the DoR's citation of ADR-026 to justify a *dynamic* resolution builder was itself a misreading; ADR-026 argues the opposite (extend the already-materialized shape).
4. **`pod_assignments` schema already supports multiple rows per `feature_id`** (`setFeatureDefaultPod` always INSERTs, never upserts, for `feature_id NOT NULL` rows — only the `feature_id IS NULL` product-default case has a uniqueness constraint) — so AC1/AC3's "multiple pods per feature" is schema-compatible today with zero migration needed. Confirmed by reading `pod-assignment-store.js` directly.
5. **`feature_collaborators` has `UNIQUE(feature_id, user_id)`** — inserting the same person twice (present in two assigned pods) will conflict; any multi-pod union-insert needs `ON CONFLICT (feature_id, user_id) DO NOTHING` (or equivalent), not a naive per-pod repeat of `populateFeatureCollaboratorsFromPod`.
6. **The closest real UI precedent for "assign this feature to something, from a per-feature control"** is `products.js`'s existing module-assignment mechanism (`featureModuleAssignments`, `PUT /products/:id/modules/:moduleId`) — but it's shaped as bulk multi-feature-to-one-module assignment (checkboxes across many features, assigned in bulk to a taxonomy bucket), not one-feature-to-multiple-pods. It's useful precedent for "how this codebase renders a per-feature-row control on the product page and submits it via `fetch`" (there is no separate settings page anywhere in this app — every per-feature control lives inline on the product page's feature list), but the interaction shape itself (single-select-target vs. multi-select-source) doesn't transfer directly and will need its own design in `/implementation-plan`.
7. **AC2's "removal for this feature only" has a real edge case the DoR doesn't address**: because `feature_collaborators` is write-time materialized (not recomputed live), a naive "removal = DELETE the row" is correct for THIS story's own scope (pod membership itself doesn't change dynamically — that's `ep4-s2`, explicitly out of scope here) but would silently resurrect a removed member if a future operation ever re-runs the population logic for an already-assigned pod (e.g. re-saving the same pod selection). Resolved by adding a small, permanent `feature_collaborator_removals(feature_id, user_id)` record on every removal, consulted by the assignment write path so a removed member is never re-inserted regardless of how many times pods are (re-)assigned — a guard, not a documented limitation.
8. **The DoR's own "Implementation Specification" proposes turning `getFeatureCollaborators()` itself into a dynamic recompute-from-`pod_assignments`-every-call builder** ("called from multiple places (feature load, pod assignment save, ep2-s1 sidebar render)"), explicitly including the sidebar's own read path — despite the same DoR's "Files you MUST NOT modify" list separately naming "Feature presence sidebar (ep2-s1) — no changes." **This is internally contradictory** (CLAUDE.md's B1/D1 contract-vs-test-plan mismatch check applies equally to a contract's own two sections contradicting each other) and, independent of that, is the larger-blast-radius option: `feature_collaborators` is a genuinely persisted table today (confirmed by checking every reference to `is_approver`, one of its own columns — it is written at table-creation time and never read anywhere, i.e. this table already IS treated as real, durable storage, not a cache safe to bypass). Rewriting `getFeatureCollaborators()` to stop reading that table and instead recompute from `pod_assignments`+`pod_members` on every call would change the behaviour of all 3 existing real call sites (`ep2-s1` presence, `handleGetJourneyCollaboratorsPresence`, `ep2-s3`/`ep3-s3`'s approver-role lookup) for every journey in production, not just ones this story touches — a strictly larger, riskier change than this story's own 3 ACs require. **Decision: keep `getFeatureCollaborators()` completely unchanged** (matching the DoR's own "MUST NOT modify" list, taken as authoritative over its self-contradicting Implementation Specification) and do the real work write-side only: extend the already-established write-time-materialize pattern (`populateFeatureCollaboratorsFromPod`) to insert the union of multiple pods with conflict-safe dedup and removal-awareness. This is the smaller, ADR-026-consistent option (reuse the existing entity's read path unchanged) and was chosen over the DoR's own literal proposal.

9. **The test-plan's own "archived pods filtered from selector" scenario tests behaviour this app cannot currently produce.** `pods.status` defaults to `'active'` (real column, confirmed in `pod-store.js`'s schema) but no route anywhere in this codebase ever sets it to anything else — pod archiving has never been built. Rather than modify the shared, already-shipped `listPods()` (used today by `ep1-s1`'s own `GET /api/pods`) to add a `status = 'active'` filter clause — which is currently a no-op given no archived pod can exist, but would be an unrequested, out-of-scope change to a pre-existing endpoint's contract — this story reuses `listPods()` completely unchanged and defers real archived-pod filtering until a pod-archiving story actually exists to build and test it meaningfully.

**Decision:** Correct `ep4-s1`'s estimated touch points for `/implementation-plan`: real files are `src/web-ui/routes/products.js` (per-feature-row UI + new assign/remove endpoints, following the existing inline-on-product-page pattern rather than a nonexistent settings page) and `src/web-ui/modules/pod-assignment-store.js` / `feature-collaborator-store.js` (extended, not replaced, for multi-pod union-insert-with-conflict-handling and per-feature removal tracking) — not `routes/features.js` / `pod-assignment-manager.js` / `features-settings.html`. `getFeatureCollaborators()` itself should need zero changes (matching this feature's own repeated "the read path already works" pattern) — the real new work is entirely on the write side (multi-pod union insert, removal handling) and a genuinely new UI surface (no settings page exists to extend, so this story does original UI design work, unlike `ep3-s1`/`ep3-s2`/`ep3-s3` which all extended something that already existed).
**Story:** ep4-s1 — no AC text change; touch-points and scope corrected, to be carried into `/implementation-plan`. This story has real, substantive new-code scope (unlike `ep3-s2`'s zero-new-code finding) — the correction here is about WHERE the code goes and what it can safely assume already exists, not whether work is needed at all.

## `ep3-s3` `/branch-setup`: baseline acknowledged, 1 pre-existing/environmental failure; DoR/test-plan built against a fictional `feature_approvals`/`reApprovalOf` schema; real gap identified and scoped down (2026-09-22)

None of this exists — the same fictional-architecture class of gap as every prior story in this epic (6th+ occurrence, per `ep2-s3-dod.md`'s own running count).

**What the real code actually does, verified directly:**
1. **AC2 (stage advances on re-approval) needs ZERO new code.** `handlePostGateConfirm` (`journey.js`) operates purely on `journey.activeSessionId`'s current session state (`completeStage()`, advance to next stage) — it has no concept of "was this stage previously regressed" and doesn't need one. 2. **AC1's literal `reApprovalOf` foreign-key linking is impossible** (no `feature_approvals` table exists, no approval record has an `id` to link to) — but its *substance* (the audit trail should make clear that this approval follows a prior regression at the same stage, not look identical to a first-time approval) is a **real, currently-unmet gap**: `handlePostJourneyApprove` (`ep2-s3`) writes an identical-shaped decisions.md entry (`"<stage> approved by <user>"` title, generic context/decision text) regardless of whether this is the stage's first approval or a re-approval following a regression. 3. **AC3 ("distinct from, not overwriting, the original regression entry")** is trivially true by construction — `decisions.md` is append-only and `handlePostJourneyApprove` already only ever appends, never rewrites. But "describing the re-approval and what changed" (AC3's fuller text) is the same real gap as AC1: the entry doesn't currently say anything different for a re-approval vs. a first approval.

**Decision:** Scope `ep3-s3` down to the one real gap: enhance `handlePostJourneyApprove`'s entry-construction logic to detect, by reading `decisions.md` itself (the only persistent record — no DB), whether the most recent entry mentioning this exact stage was a `"Regressed to <stage>"` entry (as opposed to this being the stage's first-ever approval, or an approval with no intervening regression). If so, use a distinct title (`"<stage> re-approved by <user>"`, matching this codebase's own established title-pattern-as-type-marker convention already used for `"Regressed to X"` entries) and reference the regression in the context text — giving the audit trail a real, decisions.md-native equivalent of `reApprovalOf`'s intent (linkage by content/adjacency in an append-only log, not a DB foreign key) without inventing a structured field or table nothing in this codebase would ever read.
**Story:** ep3-s3 — no AC text change; touch-points and scope corrected, to be carried into `/implementation-plan`. Real touch point: `src/web-ui/routes/journey.js`'s existing `handlePostJourneyApprove` function (not a new `approval.js`/`approval-recorder.js`).

## `ep2-s4` final review + NFR-Perf-3 closure: found and fixed a second, genuine false-conflict bug in the "fixed" LCS-anchor merge algorithm; found and fixed a real HIGH cross-tenant write vulnerability in the save route itself (2026-09-21)

**Context — closing MEDIUM finding M2 (missing NFR success-rate suite) surfaced a new HIGH-severity algorithm bug:** The final cross-task review's M2 finding (no test exercised the DoR/NFR claim "merge success rate >=99% across 100+ randomized scenarios") was closed by writing `tests/check-ep2-s4-nfr-merge-success-rate.js` — a seeded, deterministic 100-scenario suite (99 genuinely non-overlapping random-edit scenarios that must all succeed, 1 deliberately-overlapping scenario that must fail gracefully). On first run this failed: 94/100 succeeded, with 5 scenarios producing an unexpected `MERGE_CONFLICT_HARD` on edits that were disjoint by construction (different, non-adjacent-by-index line sets on two different users).
**Root cause investigated and found:** `merge-artefact-edits.js`'s Task-1-code-quality-review-era rewrite (the LCS-anchor version that replaced the original positional-index algorithm) computed conflicts at whole-SEGMENT granularity — the gap between "dual anchors" (base lines left unchanged by BOTH sides). When two ADJACENT base lines were each changed by only ONE side, with no unchanged line between them to anchor on, the entire gap was treated as one indivisible span and falsely flagged as conflicting, even though the two sides never touched the same line. Confirmed via direct reproduction: user A editing line 19 and user B editing line 20 (adjacent, genuinely disjoint) threw `MERGE_CONFLICT_HARD`.
**First fix attempt (also had a bug):** Rewrote the algorithm to compute each side's own independent list of "hunks" (maximal contiguous base-line ranges that side changed) and merge them by base position, raising a conflict only when two hunks' ranges genuinely overlap. This is structurally correct (the standard `diff3`-style approach) but the first implementation used `nextX.baseStart <= clusterEnd` to decide whether to absorb a hunk into a growing cluster — `<=` incorrectly treats two hunks that are merely ADJACENT (e.g. `[19,20)` and `[20,21)`, sharing only a boundary point, not actually overlapping) as one overlapping cluster. Reproduced the exact same false-positive with this first fix, traced `hunksA`/`hunksB` directly to confirm the adjacency-vs-overlap distinction was the issue, and corrected the absorption condition to strict `<` (with a separate exact-position seeding step so hunks that genuinely start at the same base position are still correctly clustered together).
**Verification, beyond the original 100-scenario suite:** Ran an additional 1000 randomized disjoint-edit trials across 20 different seeds and varying base-document sizes (30-70 lines, 1-6 edited lines per user) — 0 false positives. Ran an additional 400 randomized genuine-overlap trials across 20 seeds — 400/400 correctly detected as `MERGE_CONFLICT_HARD`, 0 missed. Re-ran all of Task 1's own 8 original tests, Task 5's 13 integration tests, and Task 6's 2 E2E tests — all still pass. Full `run-all-tests.js` re-run showed only the 1 pre-existing baseline failure.
**Decision:** Fixed directly by the coordinating session (the same "narrow, well-understood, correctness-critical" reasoning applied to every other direct fix this story required). This is the SECOND distinct bug found in this exact module across this story's own delivery (the first was the original positional-index desync, fixed during Task 1's own code-quality review) — both were real, both were caught by deliberately adversarial testing (an insert/delete regression test in the first case, a randomized-scenario NFR suite in the second) rather than the hand-authored example-driven tests that shipped with each version. ## ep1-s3 Task 7's E2E spec was genuinely vacuous; fixed with a test-only DB-state-read endpoint

**Date:** 2026-09-17
**Context:** Task 7's implementation plan (this session's own design) reasoned that since no UI exists to inspect `pod_assignments`/`feature_collaborators` directly and the real handler returns no JSON body, "the redirect succeeding with a real session id IS the observable proof available at this layer that the real dispatch path, including the new pod-inheritance code, executed without throwing." **A second, more serious bug was found while wiring this fix, unrelated to the vacuous-test problem itself:** `fake-test-db.js` had ONE branch matching `INSERT INTO pod_assignments (` as a bare prefix, which matched BOTH `setProductDefaultPod`'s 6-param product-level upsert (ep1-s2, no `feature_id` column) AND `setFeatureDefaultPod`'s 7-param feature-level insert (ep1-s3, with `feature_id`) — identical SQL prefix, different column lists. This bug was invisible to Tasks 1-5's own unit tests specifically because they never route through the real HTTP server + `fake-test-db.js` — only Task 7's E2E spec does, which is exactly why it was found only now, and exactly why building a genuine (non-vacuous) E2E check mattered here beyond process box-ticking.
**Story:** ep1-s3 — no AC change; both fixes close real gaps in test *infrastructure* (the vacuous assertion, and the fake-test-db.js branch collision), not defects in the production pod-inheritance logic itself, which Tasks 1-5's own unit tests (using a different, correct mock) already proved correct at the handler level.

## ep1-s3's DoR touch-points and response-shape assumptions are wrong; corrected against the real codebase before any code was written

**Date:** 2026-09-17
**Context:** Found while planning ep1-s3's implementation, before writing any code — the same class of gap as ep1-s2's DoR inaccuracies (route-prefix convention, a nonexistent "product settings" page), but deeper here since it's about the core data model, not just a route path.

The DoR (`artefacts/new-feature-2b74a292/dor/ep1-s3-dor.md`) states: touch point `src/web-ui/routes/features.js`, endpoint `POST /api/features`, a `features` table with primary key `featureId`, and a JSON response `{featureId, productId, podAssignments: [...], collaborators: [...]}`. 2. There is no `/api/features` route anywhere in `server.js`.
3. The real feature-creation handler is `handlePostProductFeature` in `src/web-ui/routes/products.js`, wired at `POST /products/:id/features` (the same route family ep1-s2 already extends with `set-default-pod`).
4. **There is no `features` table with a `featureId` primary key.** What this story's ACs call "a feature" is, in this codebase's real domain model, a **journey** — created via `journey-store.js`'s `createJourney()`/`setJourneyFields()`, which dual-writes to an in-memory Map, disk, and a real Postgres `journeys` table (`journey_id`, `tenant_id`, `product_id`, ... columns, confirmed via `journey-store-pg.js`). `journeyId` is the real, durable, tenant/product-scoped identifier this story's "featureId" concept maps onto.
5. The handler's real response is an **HTTP 303 redirect** to a skill-chat session page (`/skills/:skill/sessions/:sid/chat`) — there is no JSON response body at all, so AC1's literal "the feature is created with podAssignments... recorded against it" cannot be verified by inspecting a response body. It must be verified by querying `pod_assignments` directly after the redirect.

**Decision:** Implement pod-inheritance in `handlePostProductFeature`, injected immediately after the existing `_journeyStore.setJourneyFields(journeyId, {..., tenantId, productId})` call (the earliest point `journeyId`/`tenantId`/`productId` are all in scope AND durably persisted to Postgres via that call's own `_pgWrite`). Reuse `pod_assignments` (from `pod-assignment-store.js`, ep1-s1/ep1-s2) directly — its `feature_id` column was deliberately left nullable in ep1-s1's original migration specifically anticipating this story (see `pod-assignment-store.js`'s own header comment). Write with `feature_id: journeyId`, `assignment_type: 'feature-inherits-product-default'`, matching the DoR's own specified `assignmentType` value. Create a new `feature_collaborators` table (genuinely new, DoR's schema for it is otherwise accurate) keyed by `feature_id: journeyId`. Treat the whole pod-inheritance step as best-effort/non-fatal — matching this handler's own established resilience pattern for its other side effects (disk write, PostHog capture) — a missing or failed pod lookup must never block feature/journey creation itself.
**Rationale:** The underlying intent (a newly-created feature inherits its product's default pod) is unchanged and fully achievable; only the mechanical touch-points needed correcting against what the codebase actually is. Verifying test/AC evidence via direct `pod_assignments`/`feature_collaborators` DB queries (not response-body parsing) is the only way to actually prove this works, given the real handler's redirect-based response shape.
**Story:** ep1-s3 — no AC change; ACs remain accurate to the real, observable outcome (a pod IS assigned and collaborators ARE pre-populated), only the mechanical verification method changes from "read the response body" to "query the database after the redirect."
