# Decisions: Multi-User Role-Aware Synchronous Collaboration

## `ep2-s3`'s DoR was built against an architecture that doesn't exist — and this time, most of the real mechanism already ships in production; corrected before any code was written (2026-09-18)

**Context:** `ep2-s3`'s DoR assumed a new `feature_approvals` Postgres table, a new `POST /api/features/{featureId}/approve` route on `routes/features.js`, and a new "stage advance" mechanism built from scratch. This is the same recurring pattern as every prior story in this feature — but this time the investigation found something more significant than a wrong route/table name: **this codebase already has a fully-built, production-hardened, real "sign off and advance" mechanism, and a real decisions.md-write mechanism, both shipped and working today.** Verified before writing `artefacts/new-feature-2b74a292/plans/ep2-s3-plan.md`:
1. **`handlePostGateConfirm` (`routes/journey.js`, wired at `POST /api/journey/:journeyId/gate-confirm`) is the real, already-shipped "advance to next stage" mechanism.** It is large and deeply production-hardened: disk write, Postgres dual-write, git-repo dual-write (`das-s1`), DoR artefact validation, pipeline-state-writer notification, PostHog capture, and `completeStage()` — the exact mechanism this session has personally driven through for real, for every one of this feature's own prior stories. It is triggered today by a plain "Continue to [nextStage] →" button, rendered in `routes/skills.js` (not `features.js`) on the skill-session chat page — the page a collaborator sees immediately after completing a stage's artefact, which is exactly the moment `ep2-s3`'s own AC1 describes ("Hamish... is at the discovery stage of Feature A1"). **This is the real UI location for ep2-s3's "Sign Off" button — not `features.js`, which is a different page (the artefact-listing/Team-sidebar/stage-list page `ep2-s1`/`ep2-s2` extended) with no stage-advance concept of its own at all.**
2. **`handlePostDecisions` (`routes/journey.js`, wired at `POST /api/journey/:journeyId/decisions`, story `owle.2`) is the real, already-shipped decisions.md-write mechanism** — path-traversal-guarded, auto-creates the file with a header if absent, appends a structured entry via `fs.appendFileSync` to `artefacts/<featureSlug>/decisions.md`. This is exactly what `ep2-s3`'s own AC3 wants. Its real entry format is `title` / `**Date:**` / `**Context:**` / `**Decision:**` / `**Rationale:**` — not the AC3 text's own field list (`date`, `session-phase: discovery-approved`, `decision`, `reason`, `timestamp`), which conflates decisions.md's real format with `workspace/capture-log.md`'s separate 5-field schema (`date`/`session-phase`/`signal-type`/`signal-text`/`source`) — two genuinely different files/conventions in this repo, confirmed by reading both real formats directly, not assumed from the AC's own prose.
3. **No `feature_approvals` table exists, and none should be created.** This repo's own `CLAUDE.md` already establishes `decisions.md` as the durable, git-tracked accountability record for exactly this kind of thing ("a decision + rationale + who/when... invisible to future operators, `/trace`, and `/improve`" without it) — the same principle this session has applied to every decision in this file all along. A new Postgres table would be a second, parallel, redundant accountability mechanism for the same information `handlePostDecisions` already durably records.
**Decision:** Build `ep2-s3` as a small, additive layer alongside the two existing mechanisms above, modifying neither:
   - **New "Sign Off" button + reason-capture modal**, added next to (not replacing) the existing "Continue to [nextStage] →" button in `routes/skills.js`'s journey-gate panel — the real UI location for this action.
   - **New endpoint, `POST /api/journey/:journeyId/approve`** (in `routes/journey.js`, alongside `handlePostGateConfirm`/`handlePostDecisions`, not modifying either): validates the reason (non-empty, ≤500 chars), resolves the approver from `req.session` (matching every other handler this feature has built — `ep2-s1`/`ep2-s2`'s own precedent), and writes a decisions.md entry using `handlePostDecisions`'s own real format — `title: "[Stage] approved by [approver login] ([role])"`, `context: "Approval recorded via Sign Off at the [stage] stage of feature [slug]"`, `decision: "[Stage] approved and advancing to [nextStage]"`, `rationale: [the reason text entered]` — preserving every piece of information AC3 wants (approver, stage, reason, and a timestamp via the entry's own Date field and file position), in the real, already-established schema rather than a new invented one.
   - **On success, the client calls the EXISTING, unmodified `gate-confirm` endpoint** (the same form action `Continue to [nextStage] →` already uses) to actually advance the stage — reusing the real, proven mechanism rather than duplicating any part of its logic. The new approval endpoint records WHO approved WHY; the existing gate-confirm endpoint (untouched) does the actual advancing, exactly as it already does for every stage transition in this codebase today.
**Rationale:** This is by far the largest architecture correction this feature has made, but also the safest possible implementation once corrected: touching `handlePostGateConfirm` directly (a ~300-line, deeply production-hardened function with git/Postgres/pipeline-state/PostHog side effects) to inject a reason field would be high-risk for a Medium/High-complexity story; the additive design touches none of it. Reusing `handlePostDecisions`'s real entry format (rather than the AC's own invented field list) keeps this feature's accountability trail consistent with every other decision ever recorded in this repo, including every entry in this very file.
**Story:** ep2-s3 — no AC change in substance (approver, reason, stage, and timestamp are all still recorded, and the stage still advances); AC3's specific field-name list (`session-phase: discovery-approved`) is adapted to decisions.md's real, established field names rather than implemented literally, since the literal field doesn't exist in this file's real schema.

## ep1-s3 Task 7's E2E spec was genuinely vacuous; fixed with a test-only DB-state-read endpoint

**Date:** 2026-09-17
**Context:** Task 7's implementation plan (this session's own design) reasoned that since no UI exists to inspect `pod_assignments`/`feature_collaborators` directly and the real handler returns no JSON body, "the redirect succeeding with a real session id IS the observable proof available at this layer that the real dispatch path, including the new pod-inheritance code, executed without throwing." **Rationale:** The underlying intent (a newly-created feature inherits its product's default pod) is unchanged and fully achievable; only the mechanical touch-points needed correcting against what the codebase actually is. Verifying test/AC evidence via direct `pod_assignments`/`feature_collaborators` DB queries (not response-body parsing) is the only way to actually prove this works, given the real handler's redirect-based response shape.
**Story:** ep1-s3 — no AC change; ACs remain accurate to the real, observable outcome (a pod IS assigned and collaborators ARE pre-populated), only the mechanical verification method changes from "read the response body" to "query the database after the redirect."
