# Decisions: Completed Stages Can Silently Lack Durable Git Backing

## 2026-09-02 — Scope expanded from observability-only to root-cause-and-fix, following /clarify

**Context:** The discovery originally scoped this as adding a distinguishing log signal for `das-s1`'s 3 possible stage-completion-commit outcomes, with two open, symmetric hypotheses for why `new-feature-af17f555`'s 8 artefacts never landed in git (genuinely repo-less at completion time, vs. a live bug in `das-s1`'s AC2 guard).

**Decision:** During `/clarify`, the operator (Hamish King) confirmed `new-feature-af17f555` was linked to the `skills-framework` product for the entire period its 8 stages completed. This rules out the "genuinely no-repo" hypothesis and elevates the AC2-guard-bug hypothesis to the leading, evidence-backed explanation. The operator then chose to expand this discovery's own MVP scope to include root-causing and fixing that guard bug directly, rather than splitting it into a separate follow-up discovery/story.

**Rationale:** With the no-repo hypothesis ruled out for a confirmed real case, "just add a log line" would ship a discovery layer on top of an actively broken safety guard — detecting the next occurrence without fixing the one already found. Fixing both together (root-cause the guard, restore its AC2 contract, add the distinguishing signal so any future regression is immediately visible) is one coherent piece of work rather than two sequential passes through the same code path.

## 2026-09-02 — Reuse ep1-s6's shared cross-channel instrumentation helper, don't build a parallel logging mechanism

**Context:** This discovery independently arrived at needing a fire-and-forget, structured, `[prefix]`-tagged log + PostHog signal for 3 distinguishable outcomes — the same shape of problem `new-feature-af17f555`'s `ep1-s5`/`ep1-s6` (merged PR #811, #812, 2026-09-01/02) had already solved for a different set of events (artefact-load errors, journey-backfill errors, stage-routing errors, plus 6 success events).

**Decision:** Implementation of this discovery's distinguishing signal must extend `_logCrossChannelEvent` (`src/web-ui/routes/journey.js`, the shared helper `ep1-s6` built) with new event types, rather than building a second, parallel logging mechanism.

**Rationale:** Two divergent logging shapes for what is conceptually the same kind of signal (a named event with base fields plus event-specific details, fire-and-forget to stdout + PostHog) would be pure duplication shipped one session apart from the original. `das-s1`'s call site already lives in `journey.js` itself, so reuse requires no cross-file require — strictly simpler than building something new.

## 2026-09-02 — acdg-s1 returned to /definition after root-cause investigation revealed the real failure shape doesn't match the story's own AC2/AC2a/AC3 split

**Context:** During `/branch-setup`'s investigation step (reading `artefact-commit-writer.js` and `export-data-source.js` in full for the first time, as `acdg-s1`'s own DoR contract required before writing any fix), two things were confirmed that materially change the story's own scope:
1. `commitArtefact` is already a proper injectable adapter (D37-compliant) that throws on any real failure — AC1 is confirmed already-correct, exactly as the story's own revision (post-review finding 1-M1) anticipated.
2. `ownerRepoForFeature` **never returns falsy without throwing** — it always either throws `ExportNotFoundError` or returns a fully-valid `{owner, repo}`. AC2a (the falsy-without-throw scenario, added post-review finding 1-M2) describes a code path that cannot occur in the real implementation.
3. `ownerRepoForFeature` throws the **same** `ExportNotFoundError` for four structurally different underlying reasons (no `journeys` row for this feature_slug, missing `product_id`/`tenant_id` on that row, no matching `products` row, missing `repo_owner`/`repo_name`) — by design, for a privacy reason from its original export-feature use case (AC3 of that function: never leak owner/repo/tenant identifiers in the error). This means AC2 ("resolution fails for a distinguishable reason") and AC3 ("genuinely no repo, distinguishable skip") cannot actually be told apart by error type alone — the function's own contract doesn't expose the distinction the story's ACs assumed existed.
4. The `journeys` Postgres table `ownerRepoForFeature` queries is a **separate** data source from the in-memory `journeyStore` `journey.js` actually operates on — the same "at least three distinct journey storage models that don't share a read path" gap this session's own `ep1-s1` definition work already diagnosed and deliberately deferred (see that story's own capture-log entry, 2026-09-01). The leading explanation for `new-feature-af17f555`'s original incident is very likely a `journeys`-table row that was never created or never had `product_id` set for this feature, independent of what `/products/:id`'s own separate query showed the operator.

**Decision:** Presented three options to the operator (minimal fix removing AC4's silent-skip entirely; a cross-check against the in-memory journey object, which would require extending `journey-store.js`'s own shape — new scope; or returning to `/definition` to revise the story). The operator chose to return to `/definition` rather than resolve this unilaterally mid-implementation, given the scope-boundary implications.

**Rationale:** This is not a small implementation detail — it means the story's own AC2/AC2a/AC3 split, written before either adapter file was read, doesn't match the real shape of the problem. Continuing to implement against ACs that describe an unreachable code path (AC2a) and a distinction that doesn't structurally exist (AC2 vs AC3 by error type) would have produced either a fix that doesn't address the real incident, or silent scope creep into the deferred journeys-table sync gap. Returning to `/definition` keeps the artefact chain honest and gives the operator the actual decision — which of the three real options to take — rather than the agent choosing one mid-implementation. `acdg-s1`'s worktree was removed with no code changes committed (investigation only).

## 2026-09-02 — acdg-s1 revised: cross-check journey.productId, no new plumbing needed

**Context:** The operator chose the "deeper" fix direction (cross-check against the in-memory journey object) over the minimal fix, despite that direction being flagged as likely needing its own story. Further investigation (reading `products.js`'s `handlePostProductFeature`, `journey-store-pg.js`'s `saveJourney`/`listJourneys`, and the prior `dfr-s1` story's own fix) found `journey.productId` is already a fully-wired, correctly-persisted-and-reloaded field — not something requiring new schema or plumbing work. `new-feature-af17f555`'s own slug format (`new-feature-` + an 8-char journey-ID prefix) is an exact match for `handlePostProductFeature`'s slug-generation pattern, strongly confirming this feature was created via that exact path, which sets `productId` at creation time.

**Decision:** `acdg-s1`'s AC2/AC2a are superseded (kept inline, struck through) by AC2-revised (block+error when `journey.productId` is set but `ownerRepoForFeature` still throws) and AC3-revised (unchanged skip when `productId` is unset). Fix is entirely contained within `journey.js`'s existing catch block — no changes needed to `export-data-source.js`, `artefact-commit-writer.js`, or the journey-store modules. Complexity rating revised from 2 to 1.

**Rationale:** The "this likely needs its own story" concern raised when presenting the option turned out not to hold once the actual field lifecycle was traced — `journey.productId` was already solved infrastructure (via `dfr-s1`'s own prior fix), not a new gap. This is a good example of why "investigate before implementing" matters even after a story is already DoR-signed-off: the story's own DoR contract required reading both adapter files as the first implementation step specifically because their real shape wasn't yet known, and that reading changed the picture twice in one investigation session (first invalidating the original AC split, then revealing the actual fix was simpler than either of the two presented options assumed).
