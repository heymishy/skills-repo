**2026-08-05 | ARCH | /definition (rb-s3)**
**Decision:** Harness-agnostic instruction files (`CLAUDE.md`, `AGENTS.md`, `.cursorrules`, `.github/copilot-instructions.md`) are generated by extending the existing copy-based `scripts/assemble-copilot-instructions.sh` (per ADR-005), paired with a new drift-check validator — not by symlinking the files together.
**Alternatives considered:** Symlinks (one real file, others as symlinks pointing at it) — the mechanism the qm reference architecture uses.
**Rationale:** This repo's own dev environment is Windows, where git's symlink support is opt-in (`core.symlinks`) and inconsistent on checkout — a user without it enabled silently receives a plain-text file containing the link path instead of a working symlink, breaking the guarantee with no visible error. A copy-based assembly step plus a drift-check validator recovers the same "impossible to diverge" property without depending on a platform-specific filesystem feature that can silently fail, and extends a mechanism this repo already has rather than introducing a second one.
**Made by:** Hamish King — Platform maintainer / Product owner
**Revisit trigger:** If this repo's primary dev environment ever shifts away from Windows, or if git's Windows symlink support becomes reliable-by-default, symlinks could be revisited as a simpler alternative.

**2026-08-06 | ARCH | Inner coding loop (rb-s5)**
**Decision:** The default (no `--with-outer-loop` flag) bootstrap install is narrowed to inner-loop + ancillary skills only, on both the fresh-repo (`rb-s1`) and SaaS-connected (`rb-s4`) entry points. `--with-outer-loop` restores outer-loop skills additively, identically on both paths. This supersedes discovery.md's original MVP Scope line ("copies the full skill set uniformly every time... rather than conditional file-copying logic in the bootstrap command itself").
**Context:** Before this story, `installFullSkillSetAndRegistry` (`cli/lib/init.js`) copied every one of the 46 skills unconditionally on every `runInit()` call, on both entry points, with zero category filtering — confirmed by running the merged rb-s1/rb-s2/rb-s3/rb-s4 test suites and observing `[skills-repo-init] Installed 46 skill(s) (full skill set)` regardless of any flag. This directly falsified rb-s5's own AC2 ("SaaS-connected without the flag -> only inner-loop and ancillary installed") as written against the actual pre-rb-s5 code.
**Rationale:** Two textual signals resolved the ambiguity in favour of narrowing both entry points rather than only the SaaS-connected one: (1) `rb-e2`'s own epic Goal statement — "Optionally, either bootstrap path (fresh or SaaS-connected) can also install the full outer loop" — reads as additive/opt-in on both paths, not installed-by-default on either; (2) AC3's wording ("the flag behaves identically regardless of which entry point it's combined with") only makes sense as a meaningful claim if the flag has a real, non-redundant effect on both paths — if the fresh path already installed everything unconditionally, the flag would be a no-op there, making AC3's cross-entry-point claim vacuous on one side. Discovery.md's original "no flag, copy everything uniformly" framing pre-dates rb-e2's own definition and is treated as superseded by it, not as a conflict requiring a further /definition cycle, per the same "narrow wording/scope fixes resolved during implementation" pattern already used for rb-s1/rb-s2/rb-s3's RISK-ACCEPTs above.
**Add-on mode reconciliation (AC4 vs rb-s1 AC3):** Resolved with zero special-case code. `copySkillsFromRegistry`'s existing per-file skip-unless-force logic (rb-s1/rb-s2) already treats every file independently. A new `installableSkills(registry, withOuterLoop)` helper in `cli/lib/skills-registry.js` filters which registry entries get passed into that unchanged function — it is the only place allowed to branch on category, keeping `copySkillsFromRegistry` itself category-agnostic per its own docstring and rb-s2 AC3. Re-running `init --with-outer-loop` against an already-bootstrapped directory therefore just presents more files to copy (the previously-excluded outer-loop skill directories, which don't exist in the target yet) while every already-present inner-loop/ancillary file is left untouched by the same skip-unless-force behaviour rb-s1 AC3 already established. Verified by a checksum-before/after test (`addOnModeInstallsOuterLoopWithoutDiscardingExistingBootstrap`).
**Cross-story finding — assemble-copilot-instructions.sh (rb-s3) had its own separate hardcoded outer-loop list:** `scripts/assemble-copilot-instructions.sh`'s `OUTER_LOOP_SKILLS` bash array (from an earlier, unrelated Phase 1 initiative predating this whole feature) reads each listed skill's `SKILL.md` unconditionally to build the "Progressive Skill Disclosure" section of the assembled `CLAUDE.md`/`AGENTS.md`/etc. Before rb-s5, every skill was always installed, so this never surfaced a defect. After rb-s5 narrowed the default, a fresh bootstrap without `--with-outer-loop` produced a `CLAUDE.md` claiming `/discovery`, `/benefit-metric`, etc. were "available at session start" with the literal body text "(skill file not found)" — a real, user-visible correctness bug, reproduced and confirmed before fixing. Fixed minimally: the Progressive Disclosure loop now skips a skill whose `SKILL.md` is missing, matching the pattern the same script's own Core Platform Layer section already used. Not reconciled further: this script's `OUTER_LOOP_SKILLS`/`INNER_LOOP_SKILLS` arrays remain a second, independent categorisation list, separate from rb-s2's registry (e.g. `/workflow` is `ancillary` in rb-s2's registry but appears in this script's `OUTER_LOOP_SKILLS` array) — reconciling the two into one source of truth is a larger refactor than this story's scope and is flagged as a follow-up, not fixed here.
**RISK-ACCEPT — NFR (performance) measured shortfall on Windows/Git-Bash:** The story's NFR states `--with-outer-loop` adds no more than 3 seconds versus the default install, reasoning that the added cost is "copying already-materialized files from the same registry-driven skill set." Measured on this Windows/Git-Bash dev environment, the actual added cost is consistently ~3.1-3.3 seconds, not from the file copy itself (measured independently at ~90-100ms for the 8 additional outer-loop skill directories) but from `assemble-copilot-instructions.sh` (rb-s3) re-describing each newly-installed outer-loop skill via multiple per-skill `awk`/`sed`/`tr` subprocess spawns across two sections of the generated instruction file (~24-32 additional subprocess spawns). Windows process-creation overhead per spawn is materially higher than POSIX `fork`, and this cost was never previously observable because skill count was always fixed at 46 regardless of any flag prior to rb-s5. Proceeding with the NFR test left in place and honestly failing (documents the real ~5-10% overrun rather than loosening the threshold to force a pass) rather than reworking rb-s3's subprocess architecture, which is a separate, larger performance-optimisation concern outside this story's scope.
**Alternatives considered:** (a) Leave the default as "install everything always" and treat `--with-outer-loop` as fresh-path-only meaningful — rejected as inconsistent with AC3's cross-entry-point claim and the epic Goal's "optionally... also" phrasing. (b) Rewrite `assemble-copilot-instructions.sh`'s subprocess calls to fix the NFR shortfall now — rejected as out of this story's scope and risking destabilising a previously-verified, separately-governed script for an unrelated performance concern.
**Made by:** Coding agent (dispatched inner-loop run) — 2026-08-06
**Revisit trigger:** If a future story reconciles `assemble-copilot-instructions.sh`'s own outer/inner-loop categorisation with rb-s2's registry, or optimises its per-skill subprocess calls, re-verify the NFR threshold above and remove this RISK-ACCEPT if it then passes cleanly.
