**2026-08-05 | ARCH | /definition (rb-s3)**
**Decision:** Harness-agnostic instruction files (`CLAUDE.md`, `AGENTS.md`, `.cursorrules`, `.github/copilot-instructions.md`) are generated by extending the existing copy-based `scripts/assemble-copilot-instructions.sh` (per ADR-005), paired with a new drift-check validator — not by symlinking the files together.
**Alternatives considered:** Symlinks (one real file, others as symlinks pointing at it) — the mechanism the qm reference architecture uses.
**Rationale:** This repo's own dev environment is Windows, where git's symlink support is opt-in (`core.symlinks`) and inconsistent on checkout — a user without it enabled silently receives a plain-text file containing the link path instead of a working symlink, breaking the guarantee with no visible error. A copy-based assembly step plus a drift-check validator recovers the same "impossible to diverge" property without depending on a platform-specific filesystem feature that can silently fail, and extends a mechanism this repo already has rather than introducing a second one.
**Made by:** Hamish King — Platform maintainer / Product owner
**Revisit trigger:** If this repo's primary dev environment ever shifts away from Windows, or if git's Windows symlink support becomes reliable-by-default, symlinks could be revisited as a simpler alternative.

**2026-08-06 | ARCH | Inner coding loop (rb-s5) — corrected design: enablement signal, not file filtering**
**Decision:** `--with-outer-loop` controls an *enablement signal*, not which skill files exist on disk. Every skill file (outer-loop included) is always present under `.github/skills/` on both bootstrap entry points, regardless of the flag — `installFullSkillSetAndRegistry()` in `cli/lib/init.js` and `copySkillsFromRegistry()` in `cli/lib/skills-registry.js` are restored to their exact rb-s2-merged, unconditional behaviour (verified byte-identical via `git diff` against the pre-rb-s5 commit). Instead, the flag writes `outerLoop.enabled: true` into the bootstrapped `context.yml` (default `false`/absent), and `scripts/assemble-copilot-instructions.sh` (rb-s3) reads that signal when generating the session-start section of the instruction file: skills are presented as active tooling when enabled, or named as installed-but-not-yet-enabled (with the exact flag to enable them) when not.
**Context — why the first pass (entry above) was wrong:** `rb-s2`'s AC1 ("the target directory contains the platform's complete current skill set... not a subset or placeholder") is an unconditional, already-shipped, already-tested guarantee with no conditions attached. The first implementation pass narrowed that guarantee retroactively to satisfy this later story's own AC2 as originally worded. That is the wrong direction of resolution: an already-shipped, already-tested guarantee should win over a later story's assumption, and discovery.md's own MVP Scope explicitly recorded the original design intent ("copies the full skill set uniformly every time... rather than conditional file-copying logic in the bootstrap command"). Editing `rb-s2`'s passing regression test to match the narrower behaviour (as the first pass did) is exactly the kind of change that should raise a flag for review rather than be resolved by editing the test — which is what happened: coordinator review caught it and pushed corrected story/test-plan artefacts (commit `33536eda`) reversing the direction.
**What changed in the story/test-plan:** ACs 1-4 now speak in terms of `outerLoop.enabled` and instruction-file presentation, not file presence. AC4's "add-on mode" reconciliation question against `rb-s1` AC3 (which occupied significant analysis in the first pass) disappears entirely under this design — no skill file's on-disk presence ever changes across any AC, so there is nothing to reconcile. Re-running `init --with-outer-loop` against an already-bootstrapped directory (add-on mode) now just flips one field in `context.yml` and regenerates the instruction file; every other file, including every skill file, is untouched — verified by a before/after checksum test covering the *entire* target directory, not just the skills folder.
**Reverted in full:** `cli/lib/skills-registry.js` and `cli/lib/init.js`'s `installFullSkillSetAndRegistry()` (both restored to their exact `rb-s2`-merged content via `git checkout <pre-rb-s5-commit> -- <path>`, confirmed zero-diff). `tests/check-rb-s2-full-skill-set-and-registry.js`'s `fullSkillSetAndRegistry_buildOnRbS1Output` restored to its original, unmodified assertion — rb-s2's test suite needs no change at all for this story, and is back to its original 10/10 passing state. The "(skill file not found)" fix to `scripts/assemble-copilot-instructions.sh`'s Progressive Disclosure loop was also reverted — with every skill file always present, that bug can no longer occur, so the fix is unnecessary (it would have been dead code).
**Kept as a follow-up, not fixed here:** The separate, pre-existing issue found during the first pass — `scripts/assemble-copilot-instructions.sh`'s own hardcoded `OUTER_LOOP_SKILLS`/`INNER_LOOP_SKILLS` bash arrays (from an earlier, unrelated Phase 1 initiative) are a second, independent skill categorisation, separate from `rb-s2`'s registry (e.g. `/workflow` is `ancillary` in the registry but appears in this script's `OUTER_LOOP_SKILLS`) — is still real and still worth reconciling into one source of truth eventually, but is out of scope for this story either way.
**New mechanism added:** `cli/lib/init.js`'s new `ensureOuterLoopSignal(resolvedTarget, withOuterLoop)` reads/writes only the `outerLoop:` block of `context.yml` via a targeted regex, leaving every other line byte-identical when the desired value already matches. It only ever flips `false` → `true`, never `true` → `false` — matching the story's explicit out-of-scope note that no removal mechanism is being built, so a later bootstrap run without the flag can never silently disable an outer loop a previous run enabled. `assembleHarnessInstructions()` gained a narrow `forceRegen` parameter (separate from the existing, much broader `--force`) so a signal flip on an add-on run forces the instruction file to regenerate without pulling in `--force`'s "overwrite every seeded file" semantics. `scripts/assemble-copilot-instructions.sh` gained a `_outer_loop_enabled()` YAML-read helper (same pattern as the existing `_vcs_type`/`_vcs_format` helpers, same MC-SEC-02 non-credential-field reasoning) and conditional presentation in both the Progressive Disclosure and Core Platform Layer sections.
**RISK-ACCEPT — NFR (performance) measured shortfall on Windows/Git-Bash, larger than under the first pass:** The story's NFR states `--with-outer-loop` adds no more than 3 seconds. Measured on this Windows/Git-Bash dev environment under the corrected design: ~3.6-3.7 seconds (worse than the ~3.1-3.3 seconds measured under the reverted first pass). Root cause, confirmed by isolating each step: file copying is now identical in both cases (always all 46 skills, matching `rb-s2` AC1 unconditionally) and contributes nothing to the delta. The entire delta comes from `assemble-copilot-instructions.sh`'s "enabled" branch describing each of the 8 outer-loop skills via multiple per-skill `awk`/`sed`/`tr` subprocess spawns (skill description + triggers, extracted twice each in the pre-existing, unmodified `Core Platform Layer` loop) — the "disabled" branch is now much cheaper (a plain skill-name listing, no subprocess calls at all), which widens rather than narrows the gap versus the reverted design. This subprocess cost is inherent to the feature's own requirement to *describe* each outer-loop skill when presenting it as active, in a script this story does not own (`rb-s3`); reworking its subprocess architecture is a separate, larger performance-optimisation concern outside this story's scope. Left the NFR test honestly failing rather than loosening the threshold.
**Alternatives considered:** (a) Keep the first pass's file-filtering design and instead argue `rb-s2` AC1 should be read as "complete set once fully bootstrapped" rather than fully unconditional — rejected; the AC's own wording ("not a subset or placeholder") leaves no room for a conditional reading, and it is an already-shipped, already-tested guarantee that should not be reinterpreted after the fact to accommodate a later story. (b) Optimise `assemble-copilot-instructions.sh`'s subprocess calls now to close the NFR gap — rejected as out of this story's scope, same reasoning as the first pass's RISK-ACCEPT.
**Made by:** Coding agent (dispatched inner-loop run), following explicit coordinator-directed correction — 2026-08-06
**Revisit trigger:** If a future story reconciles `assemble-copilot-instructions.sh`'s own outer/inner-loop categorisation with `rb-s2`'s registry, or optimises its per-skill subprocess calls, re-verify the NFR threshold above and remove this RISK-ACCEPT if it then passes cleanly.

**2026-08-07 | RISK-ACCEPT (re-affirmed with fresh measurements) | scr-s1 AC4 re-verification**
**Decision:** `scr-s1` (artefacts/2026-08-07-skill-categorization-reconciliation) implemented the revisit trigger above — `assemble-copilot-instructions.sh`'s "Core Platform Layer" enabled branch was fixed to call `get_skill_triggers` once per skill instead of twice, reusing the stored result for both the presence check and the formatted output. Re-measuring the NFR (`--with-outer-loop` overhead vs. the 3-second budget) on the same Windows/Git-Bash environment this entry originally measured on: the fix is real and verified in isolation (direct `assemble-copilot-instructions.sh` invocation, `OUTER_LOOP_ENABLED=true` vs `false`, 8 samples each, dry-run: delta dropped to ~155ms average, down from a per-skill double-subprocess-spawn cost previously included in that branch) — but the full end-to-end `runInit()` overhead this NFR actually gates (matching this entry's own original measurement method) remains **not resolved**: 5 post-fix samples measured 3680ms, 3775ms, 3858ms, 3867ms, 5766ms (average ~4189ms), statistically indistinguishable from the ~3.6-4.6s pre-fix range. **Correction to this entry's original root-cause claim:** the `get_skill_triggers` double-call was a real, independently-worth-fixing defect (AC3), but it is not — and was never, on reflection — the dominant contributor to the end-to-end NFR gap; it accounted for at most a few hundred milliseconds of an ~3-4 second delta. The dominant cost lives elsewhere in the `runInit()` path (skill copying, the `--all-harnesses` assembly + drift-check subprocess chain, or general Windows/Git-Bash subprocess-spawn and filesystem overhead common to any `spawnSync` in this environment) and was not isolated further — doing so is a distinct, larger performance-investigation task outside `scr-s1`'s scope (its DoR contract scoped the fix specifically to the `get_skill_triggers` redundancy, not a general performance audit of `runInit()`).
**Alternatives considered:** Declare the NFR resolved based on the isolated ~155ms improvement alone — rejected as dishonest; the NFR's own wording gates the end-to-end `--with-outer-loop` overhead a user actually experiences, not the isolated cost of one subprocess call.
**Made by:** Coding agent (dispatched inner-loop run, scr-s1) — 2026-08-07
**Revisit trigger:** A future story that profiles `runInit()`'s full `--with-outer-loop` path end-to-end (not just the assembly script) to find the actual dominant cost contributor, then re-verify this NFR and close this RISK-ACCEPT if it then passes cleanly.
