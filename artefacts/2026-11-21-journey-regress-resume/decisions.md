# Decisions: journey resume stage after a regress (rgsr-s1)

## D1. Resolve the resume stage from the journey store's record first, instead of changing what the store writes to disk (2026-11-21)

**Context:** `regressToStage` correctly sets the in-memory `activeSkill` and saves the journey to disk in the store's shape, which has no `currentStage` field. `handleGetJourneyResume` read only the disk record's `currentStage`, falling back to `discovery`, so a regressed journey (and any store-saved journey with no live session) resumed at `discovery`. A Postgres deployment is unaffected because the handler builds its disk-shaped record from memory there.
**Decision:** in `handleGetJourneyResume`, `currentStage = memJourney.activeSkill || diskJourney.currentStage || 'discovery'`. `memJourney` is the journey store's record that the handler already uses for the access check and the active session, and `regressToStage` and `setActiveSession` both set `activeSkill` on it. In disk mode that record comes from `listJourneys` (the saved store-shaped record), so it is current as of the last save by `completeStage`, `setJourneyFields` or `regressToStage` (`setActiveSession` alone does not save to disk).
**Rationale:** one line at the point of the wrong read; no data-shape change, no change to what is saved, no migration; the Postgres path already behaves this way; a disk-native journey with nothing in memory keeps its old behaviour.
**Alternatives rejected:** writing `currentStage` from `regressToStage` or from `saveJourney` (a data-shape change that every disk reader would have to be checked against, and it leaves `setActiveSession` and the other store mutators still not writing it); giving the store's journeys a `currentStage` field (same, plus a second source of truth to keep in step with `activeSkill`); making the regress handler call the disk adapter's `updateStage` (fixes only the regress case; T2 shows the same wrong landing without any regress); changing the spec (the spec is right and the product was wrong).
**Risk accepted:** if a CLI or an editor advances the disk record's `currentStage` while the store's record holds an older `activeSkill`, resume now follows the store's record. The disk-backed mode is local development, the handler already trusts that record for everything else, and the case did not work before either (the store's disk records carry no `currentStage` at all). A stage started with `setActiveSession` and never saved is not yet in the disk-listed record; that is no worse than before and the live-session paths earlier in the handler cover it.
**Found, not fixed (follow-up):** `loadAllFromDisk` maps the disk `currentStage` to `activeSkill` and the disk `stages` object to `completedStages`; a store-saved journey has neither, so after a restart in disk mode it reloads with no stage and no completed stages. Same root (two disk shapes, one reader each), separate defect and fix.
