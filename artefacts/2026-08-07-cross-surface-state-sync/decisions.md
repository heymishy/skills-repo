**2026-08-07 | ASSUMPTION | /clarify**
**Decision:** Feature-slug string matching is a sufficient correlation key for the sync mechanism, provided the design always propagates the originating side's slug rather than requiring two independently-chosen slugs to coincidentally match.
**Alternatives considered:** A more robust explicit cross-reference (e.g. storing a `journeyId` field directly on the `pipeline-state.json` feature entry, or a `pipelineStateSlug` field on the journey row) instead of relying on slug-string equality.
**Rationale:** Confirmed via direct code inspection: `journey.js`'s `_slugify()` is a deterministic lowercase-dasherize function, and `das-s1`'s own dual-write already commits artefacts under the journey's own slug (`artefacts/<journey.featureSlug>/...`). The realistic scenario is a feature originating on one surface, with sync creating the corresponding entry on the other using that exact slug — not two independently-typed names needing to coincidentally match.
**Made by:** Hamish King — Platform maintainer / Product owner (confirmed via direct code inspection during /clarify)
**Revisit trigger:** If a future scenario emerges where the same conceptual feature is genuinely, independently initiated on both surfaces with different human-chosen names, revisit whether an explicit cross-reference field is needed instead of slug matching.

**2026-08-07 | ARCH | /clarify**
**Decision:** The web-UI-to-pipeline-state.json sync direction is asynchronous/best-effort with a retry/reconciliation safety net — distinct from `das-s1`'s already-synchronous artefact commit, which stays blocking since it gates real stage completion.
**Alternatives considered:** A fully synchronous bidirectional sync, where the web UI's stage-completion request blocks on both the artefact commit (already required by `das-s1`) and a second commit updating `pipeline-state.json`.
**Rationale:** `das-s1` already adds ~2 seconds of synchronous latency for its own artefact commit. A second synchronous commit for `pipeline-state.json` would roughly double that, and the two files can't easily be combined into one atomic commit via the simple GitHub Contents API (would require the lower-level Git Data API — trees/blobs/commits — a materially more complex mechanism). Cross-surface consistency can tolerate a few seconds of propagation lag without affecting the requesting operator's own action; only the operator's own artefact durability needs to be synchronous.
**Made by:** Hamish King — Platform maintainer / Product owner (confirmed via direct comparison against `das-s1`'s already-shipped design during /clarify)
**Revisit trigger:** If the async propagation's lag ever causes a real, observed reconciliation failure (e.g. an operator making a decision based on stale `pipeline-state.json` data within that lag window), reconsider whether the sync needs to be synchronous after all, or whether the lag window needs to be bounded more tightly.

**2026-08-07 | ARCH | /definition (Step 1.5 — architecture constraints scan)**
**Decision:** The web-UI-to-pipeline-state.json async/best-effort sync direction (per the earlier ARCH decision above) is implemented as a bounded in-request retry only — a small, fixed number of retry attempts within the original authenticated request's lifetime, using the live session token already present. No token or credential is stored for later background retry. If retries are exhausted, the gap is logged for css-s4's reconciliation safety net to pick up on a future live request.
**Alternatives considered:** Storing the session token (or a scoped derivative) so a background job could retry later without the original request being open.
**Rationale:** ADR-020 requires the authenticated user's own OAuth token for any GitHub Contents API write to `pipeline-state.json` — a requirement naturally satisfied only within the original request's lifetime. Storing a token for later background use would satisfy the retry mechanism but introduces a new credential-storage/security surface that ADR-020 never anticipated and that conflicts with `product/constraints.md` #12's "credentials are structural, never persisted in the agent's environment" principle. Bounded in-request retry keeps the mechanism within ADR-020's existing compliance boundary.
**Made by:** Hamish King — Platform maintainer / Product owner
**Revisit trigger:** If in-request retry proves insufficient in practice (a high rate of exhausted retries reaching css-s4's reconciliation log), reconsider a token-storage approach with an explicit new security review, rather than silently degrading the reconciliation safety net's effectiveness.

**2026-10-24 | ARCH | /implementation-plan (css-s3, "last synced" marker design)**
**Decision:** The "last synced" marker css-s3's DoR contract leaves to the coding agent's judgment (Assumptions section) is a single new field, `lastSyncedStage`, added ONLY to `pipeline-state.json`'s story-level schema (`.github/pipeline-state.schema.json`, per ADR-003 schema-first) — not a new column on the `journeys` table. This keeps the story's own Data Model section accurate as written ("no schema change" to `journeys`) and matches ADR-003's own trust model (`pipeline-state.json` is the git-committed, canonical, audit-trailed side — the natural home for the shared "what did both sides last agree on" marker, read by both directions rather than duplicated on both sides). Conflict detection logic: `detectConflict(lastSyncedStage, pipelineStateValue, journeyValue)` is a pure function returning `null` (no conflict) unless BOTH `pipelineStateValue !== lastSyncedStage` AND `journeyValue !== lastSyncedStage` AND `pipelineStateValue !== journeyValue` — i.e. both sides independently moved away from the last-agreed value, to different values. Wiring: (a) css-s1's direction (`src/sync/journey-sync-client.js`'s `syncGateAdvanceToJourney`) gains a `lastSyncedStage` parameter (read from the local `pipeline-state.json` by its caller, `cli-gate-advance.js`, which already has the full state object in memory) and compares it against the resolved journey's own current stage value before deciding whether to call the transport's normal 'update' action or the conflict-resolution path. (b) css-s2's direction hooks into `pipeline-state-github-writer.js`'s existing `applyStateUpdate(state, featureSlug, storyId, stateUpdate)` — `state` already holds the freshly-fetched CURRENT pipeline-state.json value (read via the same call this function already makes, no new fetch needed) and `stateUpdate` gains a `lastSyncedStage` field (threaded from `journey.js`'s own call site, which already knows the journey's own just-completed stage value as `session.skillName`) for the same comparison, before applying the mutation.
**Alternatives considered:** (a) Store the marker on the `journeys` table instead (e.g. a new `last_synced_stage` column) — rejected because it contradicts the story's own Data Model section's explicit "no schema change" framing for `journeys`, and because it would require keeping two independently-writable copies of the same marker in sync with each other, which is exactly the class of problem this story exists to solve, not something to introduce as an implementation detail. (b) Store the marker only in-memory per sync call (no persistence at all) — rejected because conflict detection requires knowing the value BEFORE the current sync attempt, across requests/processes; an in-memory value cannot survive between a CLI process exiting and a later web-UI request, or vice versa.
**Rationale:** `pipeline-state.json` is already the single git-committed, versioned record both directions read from and (per css-s1/css-s2) ultimately agree is canonical on conflict — adding the shared marker there, read by both directions rather than duplicated, is the simplest design that satisfies AC1-AC4 without introducing a second source of truth for the marker itself.
**Made by:** Hamish King — Platform maintainer / Product owner (confirmed via design review during /implementation-plan, 2026-10-24, within the DoR's own explicitly-delegated judgment call)
**Revisit trigger:** If a future story needs to detect conflicts for a gate/stage this marker scheme can't represent (e.g. the full-vocabulary coverage css-s4 adds), extend `lastSyncedStage` to a per-gate map rather than a single scalar, revisiting this decision explicitly rather than silently overloading the single-value field.

**2026-10-25 | ARCH | /implementation-plan (css-s3, Task 7 — AC2's journey-correction half, found missing at final cross-cutting review)**
**Decision:** The final cross-cutting reviewer found that AC2's second half — "the web-UI journey's Postgres record is corrected to match pipeline-state.json's value" — was never implemented; Task 4 only prevented pipeline-state.json from being overwritten, leaving the journey's own already-persisted (losing) stage permanently uncorrected. Investigation found the real fix is NOT a simple Postgres write at the conflict-detection point: `journey.js`'s `handlePostGateConfirm` determines the NEXT session/stage (`nextStage = _journeyStore.getNextStage(session.skillName)`, the `PER_STORY_SEQ` per-story-cycle branch, multiple `setActiveSession` calls, and several `session.skillName === '<gate>'`-guarded trace-emission blocks) entirely from `session.skillName` — the web-UI's own (potentially losing) view — later in the SAME request, which would silently re-diverge from any standalone Postgres correction written earlier in that same request. Fix: `pipeline-state-github-writer.js`'s `applyStateUpdate`/`pipelineStateGithubWriter` now return `{ conflict }` (the resolved conflict object, or `null`) instead of nothing; `journey.js` captures this and, when a conflict was resolved, reassigns its own local `session.skillName = writeResult.conflict.resolved` immediately after the write succeeds, before any downstream trace-emission guard or next-stage computation runs. Every downstream branch that already keys off `session.skillName` — `nextStage`, `PER_STORY_SEQ.indexOf(...)`, the `definition-of-ready`/`infra-plan`/`schema-migration-review` trace-emission guards, every `setActiveSession` call driven by the resulting `nextStage` — automatically becomes conflict-aware without any of those individual branches needing to change, because they all already correctly handle every real stage name in `STAGE_SEQUENCE`; this fix only changes WHICH stage name they see.
**Safety analysis:** `_journeyStore.completeStage(journeyId, session.skillName, ...)` (which persists the journey's own historical `completedStages` entry — the true audit record of what the session actually was) runs at line 2737, well before the pipeline-state write (~2814) and this reassignment — so the historical record is written with the TRUE skill name regardless of any later conflict correction, never corrupted. No code after the reassignment point reads `session.skillName` to persist anything about the ORIGINAL (pre-reassignment) session identity — confirmed by grep across the full file. **2026-10-25 | ARCH | /implementation-plan (css-s3, Task 7's own independent review — Critical vocabulary-mismatch finding)**
**Decision:** Task 7's own independent review found a Critical, reachable bug in the just-implemented `session.skillName` reassignment: it assumed the resolved conflict value is always one of the 8 outer-loop stage names the web journey's own `STAGE_SEQUENCE` models, but `pipeline-state.json`'s own feature-level `stage` schema enum is far broader (23 values, confirmed directly against `.github/pipeline-state.schema.json`) — and the story-level `stage` field this conflict path actually writes has no enum constraint at all, so the real value space is wider still. (Correction to this entry's own first draft, made during a SECOND review pass: `infra-plan`/`schema-migration-review` are NOT schema-enum members — they are free-form `session.skillName` literals used elsewhere in `journey.js`'s own trace-emission guards. This doesn't weaken the finding; if anything an unconstrained value space is a stronger reason for the guard below, not a weaker one.) This is exactly the shape a real conflict takes once the CLI side is ahead of the outer loop (AC1's own core scenario). Reassigning to an unmodeled value caused two concrete harms: `getNextStage()` silently returning `null` (treated as "journey complete" — a false completion), and `infra-plan`/`schema-migration-review`'s own trace-emission guards firing using session fields (`infraPlanPath`/`migrationReviewPath`) this session never populated, fabricating an audit trace record for a sign-off that never happened — a direct violation of this repo's own disk-canonicity/`/trace` integrity principle. Fixed by adding `journey-store.js`'s `isKnownStage(stage)` (true only for `STAGE_SEQUENCE` members) and gating the reassignment on it: only reassign when the resolved value is representable in the journey's own model; otherwise log a `cross_surface_conflict_correction_skipped` event and fall back to the pre-Task-7 behaviour (pipeline-state.json's own side remains correctly protected either way — only the journey-side "catch-up" is skipped for a stage this model has no concept of).
**Alternatives considered:** Extending `STAGE_SEQUENCE`/journey.js's own stage model to cover the full inner-loop/other-track vocabulary too — rejected as substantially out of this story's own scope (css-s3 is about conflict detection/resolution, not about extending the web journey's own stage model to parity with the CLI's full vocabulary; that is a materially larger change this session should not attempt unreviewed).
**Rationale:** A silent false-completion or a fabricated audit trace record are both worse outcomes than simply not correcting the journey side for this reachable sub-case — this matches the story's own AC2 priority ordering (pipeline-state.json's value is always canonical and protected; the journey-side correction is the secondary, "also fix this side" half) and avoids introducing a NEW correctness bug while fixing the one the final cross-cutting review found.
