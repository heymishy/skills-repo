## ARCH — Fix departs from the story's own suggested implementation (explicit tenant match, not `isSameTenant()`)

**Date:** 2026-08-22
**Context:** During `/implementation-plan`, found that `tests/check-p0.1-journey-access.js` (the original test file for `requireJourneyAccess()`, unmodified since p0.1) has a Test 4 ("non-owner throws FORBIDDEN") whose fixture — `journey = { ownerId: 'bob' }`, `session = { login: 'alice' }`, both with no `tenantId` field at all — would flip from denying to granting access if the story's own suggested fix (`policy === POLICY.TENANT && isSameTenant(journey, session)`) were implemented literally. `isSameTenant()`'s own tests (Test 14/15 in the same file) confirm this is deliberate, documented behaviour: `isSameTenant(journey, session)` returns `true` whenever *either* side's `tenantId` is missing, a permissive passthrough built for Phase-0 (pre-multi-tenancy) legacy compatibility — not a positive same-tenant confirmation.
**Decision:** Implement the grant path with an explicit, positively-verified tenant match instead: `policy === POLICY.TENANT && journey.tenantId != null && session.tenantId != null && journey.tenantId === session.tenantId`. Do not call `isSameTenant()` from this new branch at all.
**Rationale:** This repo's own security standard, injected into this story's DoR ("Access control: Deny by default"), argues directly for the stricter version — a new access-granting code path should require positive confirmation of tenant identity, not inherit a permissive passthrough designed for a different, legacy purpose. The stricter version also requires zero changes to `check-p0.1-journey-access.js` (all 16 of its existing tests, including Test 4, continue to pass unmodified — verified directly, not assumed) and zero changes to `isSameTenant()` itself, minimizing blast radius versus the story's own suggested shape. `jatg-s1`'s own AC1/AC2/AC3 are unaffected either way, since all three use explicit, present `tenantId` values on both sides.

## ARCH — Full-suite regression check revealed a genuine contradiction; resolved by completing incomplete test fixtures, not by weakening the guard

**Date:** 2026-08-22
**Context:** After implementing the strict design above and confirming AC5 (`check-wsm2-collaborative-sessions.js`), a full-suite run surfaced 6 newly-failing files: `check-p0.2-journey-guard-wiring.js` (and its subprocess-callers `check-p1.1-oauth-tenant-resolution.js`/`check-p1.2-tenant-session-journey.js`), `check-s3.4-item-detail-view.js`, `check-kcrs-s1-kanban-card-resume-session.js`, and `check-dsh-s2-shared-durable-read.js`. Since AC5 requires `wsm2` to pass, and `wsm2`'s own fixture (both `journey.tenantId` and `session.tenantId` entirely absent) is structurally identical to `check-p0.1-journey-access.js`'s own Test 4 fixture (which expects DENY), initially attempted the alternative design — `isSameTenant()`'s existing permissive "either side missing → true" passthrough — which made `wsm2` pass but immediately broke the 6 files above. Two designs, two different failures: neither a coin-flip nor a simple fixture typo.

**Investigation (per operator's explicit request to fully investigate before choosing):**
- `check-p0.2-journey-guard-wiring.js` (+ `p1.1`/`p1.2`, which re-run it as a subprocess): "cross-user" tests written when this guard module was first introduced (p0.1/p0.2), before multi-tenancy existed as a concept at all. Fixtures never set `tenantId` anywhere. Re-ran cleanly under the **strict** design with zero fixture changes — this was never actually in conflict; it only appeared to conflict because the earlier attempt (via `isSameTenant()`) incorrectly granted these too.
- `check-s3.4-item-detail-view.js` and `check-kcrs-s1-kanban-card-resume-session.js`: both explicitly set `journey.tenantId` to represent "another tenant" (using the owner's own login as a personal-tenant ID, e.g. `owner@example.test`), but their attacker/different-login session fixtures never set `session.tenantId` at all — an incomplete fixture, not a deliberate test of the passthrough case. Fixed by adding the missing, explicit, *different* `tenantId` to the session side, completing what the test's own name already claimed to assert.
- `check-dsh-s2-shared-durable-read.js`: genuinely different from the other five. Its target function, `session-turns-pg.js`'s `getTurnsForStage()`, reads actual conversation *content* (not journey metadata) and calls `requireJourneyAccess(..., POLICY.TENANT)` — but its own test, `"same tenantId but not the owner login is rejected"`, explicitly and deliberately wants owner-only access even when the tenant matches. This was a separate, pre-existing bug at that one call site (wrong policy constant), exposed — not caused — by fixing the dead-code branch in `requireJourneyAccess` itself. Fixed by changing that one call site to `POLICY.OWNER`.
- `wsm2` itself: re-examined against the same standard applied to `s3.4`/`kcrs-s1` — its fixture was *also* simply incomplete (never intentionally representing the ambiguous-passthrough case), not a deliberate "no tenant data = shared" test. Fixed by adding explicit, matching `tenantId: 'acme'` to both the journey and the relevant viewer sessions in `T2`/`T4`.

**Decision:** Keep the strict, explicit-tenant-match design (confirmed, not reverted). Complete the four incomplete test fixtures (`wsm2`, `s3.4`, `kcrs-s1`) with real `tenantId` values matching each test's own already-stated intent, and fix `session-turns-pg.js`'s one-line policy-constant bug (`POLICY.TENANT` → `POLICY.OWNER`) at its single call site. Revert `check-p0.1-journey-access.js`'s Test 4 and this story's own new test file back to their pre-conflict state (no changes needed under the strict design).
**Rationale:** Every one of the 6 newly-failing files, once actually read, was either (a) already correctly handled by the strict design with zero changes needed (`p0.2`/`p1.1`/`p1.2`), (b) an incomplete fixture whose own test name/comment already declared cross-tenant or same-tenant intent that the fixture simply failed to fully express (`s3.4`, `kcrs-s1`, `wsm2`), or (c) a genuinely separate, pre-existing bug at a different call site with a different, legitimately stricter access requirement (`dsh-s2`). None of the 6 files required weakening `requireJourneyAccess` itself — the full-suite regression check did exactly what AC6/AC4 intended: it surfaced real, pre-existing gaps in test-fixture completeness and one separate mis-wired call site, none of which were about this story's own core fix being wrong. Full suite re-confirmed clean: 533 files, 3 pre-existing/unrelated failures, 0 new (down from an initial 4, since `wsm2` itself is now fixed).
