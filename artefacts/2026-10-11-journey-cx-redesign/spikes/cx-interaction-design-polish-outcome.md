## Part 1 — Rendered grid visual polish

### Outcome: REFINE (visual/interaction design quality of the already-correct grid — not a further structural change)

### What was found

`jcx-s6` fixed the real structural gap (swimlane/timeline grid, columns, aligned rows) the prior two spikes identified, and `jcx-hotfix3` closed the one regression it introduced. The grid itself — column layout, row alignment, curve-on-chart stage labels — is confirmed correct and live. The "still clunky" feeling has a different, more specific root cause: **the grid has no visual hierarchy between real content and empty/placeholder content, and its spacing doesn't follow a consistent rhythm.** Both are concrete, fixable, and were directly measured against the live DOM, not guessed at.

1. **Empty-cell placeholder text renders with full-strength body-text color — identical to real data.** Direct `getComputedStyle` extraction: a cell showing "Not set" and a cell showing a real pain-point both render at `color: rgb(20,23,26)` (near-black), `font-size: 13px`. Every empty-state design-system source checked (Carbon, Supabase, Segment, Cloudscape) converges on the same rule: empty-cell content must be visually dulled (muted color and/or reduced weight) relative to real data, precisely so a dense grid doesn't read as uniformly "full" of noise. This is the single most load-bearing finding — it's a one-line CSS fix with an outsized effect on perceived polish, and it directly explains "feels clunky" better than any structural factor, since the structure is already fixed.

2. **A newly created stage defaults to the literal, unstyled text "new" as its own name** — confirmed live via a fresh zoom-screenshot (a 4th stage was added to the test journey since the last check, rendering as lowercase "new" with no placeholder styling, identical treatment to a real stage name). This is the same root defect as finding 1 (default/placeholder content given no visual distinction from real content) showing up one level higher, in the stage header itself rather than just the data rows.

3. **Grid spacing doesn't follow a consistent base unit.** Direct measurement: row padding is `10px 0px`; column-gap between cells is `12px` (confirmed from the inline CSS). Every data-table density source checked (Atlassian's design system, Material Design) is built on an 8px base spacing scale — 8/16/24px multiples throughout. `10px` and `12px` are both off-rhythm: neither is a multiple of 8, and the two values don't even match each other. On their own each is a tiny visual discrepancy; compounded across 5 repeated rows and multiple columns, this is a real contributor to a layout "feeling" slightly off without any single element being obviously wrong — exactly the kind of defect a structural review (checking "does the grid exist, are columns aligned") would never surface, and exactly what the operator's own "clunky" word describes.

4. **Row label font-size (11px) is below the general ~12px sustained-reading floor**, while the row height itself (measured: `48.5px`) is actually already close to Atlassian's own "Regular" 48px density token — so row height is fine, but the label reading comfortably inside it is slightly undersized. Label color (`rgb(63,69,76)`, a muted slate) and weight (700) are already the right treatment for a secondary label — only the size needs a small bump.

5. **The emotion curve reserves a fixed 164px of vertical height regardless of content.** Per the eleken.co guidance on timeline-chart density, a chart's height should scale with what it's actually showing, not reserve a fixed block disproportionate to its information content. Now that `jcx-s6` already put stage names directly on the chart (closing the prior spike's own finding 2), the curve itself is a fairly simple 3-dot line — 164px of height ahead of 5 more data-dense rows below pushes real content further down the page than it needs to be, without adding legibility.

6. **Tool-comparison research directly validates the operator's own word choice.** A fresh search on Smaply/UXPressia/Custellence (the closest commercial comparables to this feature) found UXPressia specifically called "clunky" by reviewers — and the concrete complaints behind that word were consistently about visual density and inconsistent empty/placeholder treatment, not missing structure. This is a strong signal that "clunky" in this exact product category is a visual-polish word, not a structure word — consistent with findings 1-5 and with the operator's own explicit "ui is better" acknowledgment that the structural fix already landed.

### Reasoning

`jcx-s6` closed the gap the first two spikes measured (does a swimlane/timeline grid exist, are stage columns and rows aligned, does the curve carry stage labels) — and live verification confirms it did so correctly. The operator's continued "clunky" read is not inconsistent with that; it's evidence of a different, narrower category of gap that a structural review is not designed to catch: consistency of visual treatment (empty vs. real content) and consistency of spacing rhythm. Both are measurable (confirmed via direct `getComputedStyle` reads above, not inferred) and both have a single well-established fix pattern in design-system literature, independent of which specific journey-mapping competitor is used as the reference.

## Part 2 — Authoring/editing flow ("the journey of making a journey")

### Outcome: FIX + REFINE (one confirmed functional defect, plus a genuine interaction-flow gap)

### What was found

The operator's redirect was correct and surfaced something Part 1 could not have found, because Part 1 only examined the already-populated, rendered grid. Reading `journeys.js`'s own stage-creation/edit code directly, then reproducing the actual click flow live, found the authoring experience has a real defect at its very first step, plus a genuine multi-step friction gap matching the "sequence of steps" framing.

1. **CONFIRMED LIVE DEFECT: "+ Add stage" is non-functional from both the Canvas and Customer-experience views — the two views a user actually works from by default.** Mechanism, read directly from the code and reproduced live: clicking "+ Add stage" inserts a new, unsaved stage-name `<input>` into `#sw-journey-stages`, the legacy stage-card list. That container is hidden (`display:none`) in BOTH the Canvas view (the page's own default on load) and the Customer-experience view (`jcx-s6`'s own view, where a user populating CX data is actually working) — it is visible only in the Delivery view. The code then calls `input.focus()`, which silently no-ops on a descendant of a `display:none` ancestor per the HTML spec. Live reproduction via `javascript_tool` confirms both failure modes exactly: `stagesListDisplay` stayed `"none"` after the click, the new input existed in the DOM but was fully invisible, and `document.activeElement` remained the Add-stage button itself, never the new input. **A user on the Customer-experience tab — exactly where the operator and this whole epic are focused — who clicks "+ Add stage" sees nothing happen at all.** No visual feedback, no focus change, no error. This is not a new regression from `jcx-s6`; the underlying `#sw-journey-stages{display:none}` rule for the Canvas view predates it (from `ep2-s3`'s own 3-view toggle), and `jcx-s6` only extended the same already-broken pattern to the Customer-experience view too, following its own established precedent. It has likely been broken, silently, since the 3-view toggle shipped — directly relevant to "feels very clunky," since this is literally the first action in building a journey.

2. **On successful save, the page performs a full `window.location.reload()`** — even once the invisible-input defect above is fixed, saving a new stage's name discards the user's current view (the toggle is pure client-side state, not persisted or round-tripped) and always returns them to the default Canvas view, not wherever they were working. A user adding a 4th stage while reviewing the Customer-experience grid is unconditionally bounced back to Canvas just to see their own new stage. **Elevated during the internal-consistency research pass:** this app's own `.github/standards/web-ui/web-ui-patterns.md` already documents a repo-wide rule ("Client-side DOM patch vs. full page reload after a POST action") that a page with live, in-progress client state — exactly what the Customer-experience canvas has (the open edit side panel, any typed-but-not-yet-blurred field text) — must patch the specific DOM element in place from the response body and must NOT reload; it explicitly names `products.js`/`settings.js`/`kanban-view.js` as the only pages where reload is the correct, intentional convention (static/administrative, no in-progress state to lose) — the journey canvas is not one of those three. This is not just a UX nicety anymore: it is a confirmed violation of this repo's own already-documented architecture standard, found by checking internal consistency before inventing an external-best-practice fix.

3. **Populating a stage's actual CX content (the 7 fields the swimlane grid displays) requires leaving the grid entirely for a separate side panel.** The name is set inline (when reachable at all, per finding 1); every other field — description, customer actions, touchpoints, channel, emotion, pain points, opportunities, moment of truth — lives only in a single shared "Edit stage" drawer, opened by a small link, with no visible connection to the specific swimlane row it will populate. Each field also autosaves independently on blur (8 separate requests per stage, no combined submit), with one shared, 1.5-second "Saved" flash for the whole panel rather than per-field confirmation — tabbing quickly through several fields can blur-save field 2 before field 1's own flash has even cleared, with no way to tell which fields actually persisted.

4. **This is consistent with, not contradicted by, how comparable tools structure the same flow.** A fresh search on journey-mapping-tool authoring conventions (Splice, QuestionPro, Figr) converges on a hover-reveal "+" directly at the point of insertion in the map itself, with the name entered in place and no modal/drawer round-trip for the primary create action — the opposite of both defects above (hidden-list insertion point, full-page reload, separate-panel-for-everything-else). This is a genuine, multi-source-grounded interaction-design gap, not a matter of taste.

### Reasoning

The operator's own framing — "user does this, then that, sequence of steps... the journey of making a journey" — pointed at exactly the right layer. Part 1's findings (empty-state color, spacing rhythm) are real but can only make an already-functioning grid look more polished. Finding 1 here is different in kind: it is a confirmed, reproduced functional defect in the very first step of the authoring sequence, from the two views a user is actually meant to use, not a cosmetic issue. It plausibly accounts for a meaningful share of "feels very clunky" on its own, independent of anything Part 1 found.

## Part 3 — Further best-practice sources (save feedback, field-density)

### Outcome: REFINE (deepens Part 2 finding 3 with a concrete pattern; confirms the panel's own basic shape is correct)

### What was found

Operator asked to keep exploring further sources before finalizing scope. Two new, well-established patterns emerged that directly sharpen (not replace) Part 2's own finding 3 — the edit panel's single, fast-fading, whole-panel "Saved" flash.

1. **The autosave-on-blur mechanism itself is correct, not a thing to redesign away from.** Autosave-on-blur is the right choice specifically for low-risk, high-frequency edits like a status or a short text field — exactly this panel's own 8 fields (description, actions, touchpoints, channel, emotion, pain points, opportunities, moment of truth). This confirms the existing per-field-PATCH-on-blur mechanism is architecturally sound; the gap Part 2 found is entirely in the FEEDBACK layer, not the save mechanism.

2. **The established feedback pattern (Notion, Linear, Figma, and GitLab's own design pattern library independently converge on the same shape) is a persistent, stateful indicator — not a transient flash:** `Saved` (default, subtle/muted) → `Saving…` (while a debounced write is in flight) → `Failed to save — Retry` (an explicit, actionable error state) — and it persists visibly rather than fading after a fixed timeout, so a user who looks back a few seconds later can still see whether their last edit actually landed. This directly sharpens Part 2 finding 3, and a careful re-read of the save handler's own `.catch` path (correcting an earlier, less precise read of this same code) found something sharper than "missing": **a `.catch` path does exist** — it sets `panelSaved.textContent = "Error: " + e.message` — but it reuses the exact same `sw-stage-panel-saved` element and CSS class as the success case, and that element's own CSS rule is `color:var(--success)` unconditionally. A failed save renders its error text in the same GREEN, success-styled element as a successful one. This is not a missing error state; it is a MISLEADING one — a save failure can visually read as a success. That is a materially worse defect than an absent indicator, and the fix must give the error state its own distinct class/color (e.g. `var(--danger)`, matching this panel's own established `sw-stage-reorder-error`/`sw-feature-mapping-warning` convention elsewhere on the same page), not just add a `Saving…` state on top of the existing single class.

3. **Progressive disclosure / field-chunking is the established pattern for a many-field editor, and directly explains part of why the panel "feels clunky" independent of the save-feedback issue.** Per Miller's Law (5-7 items in working memory) and the progressive-disclosure literature, 8 flat, equally-weighted fields in one panel asks more of working memory than is comfortable — the standard fix is to group related fields (e.g. "Description" + "Channel" as context; "Emotion" + "Pain points" + "Opportunities" as the CX-insight cluster; "Customer actions" + "Touchpoints" as the behavioural cluster) with light visual separation (a heading or divider per group), not necessarily collapsing anything — side drawers are confirmed as the correct container choice for desktop (no change needed there), the gap is purely information-chunking within it.

4. **Miro/Mural's own journey-mapping templates confirm the same swimlane rows this app already has (actions, touchpoints, emotions, pain points, opportunities) but did not surface any further authoring-specific technical pattern beyond what Splice/QuestionPro/Figr already established in Part 2** — named here to confirm this avenue was checked, not to claim a new finding.

### Reasoning

Part 2 correctly identified that panel feedback is too weak (one shared, fast-fading flash), but hadn't yet named a concrete target shape. This pass converges three independent, authoritative sources (Notion/Linear/Figma's own shipped pattern, GitLab's own public design-pattern library, and general autosave-UX research) on the same 3-state indicator — turning a vague "add more confirmation" into a specific, implementable spec. The field-chunking finding is new and explains part of the "clunky" feeling Part 1/Part 2 hadn't fully accounted for: even with perfect empty-state styling and perfect save feedback, 8 undifferentiated fields in a flat list asks more cognitive effort to scan than necessary.

## Part 4 — Deeper dive: dedicated journey-mapping-tool authoring UX (FlowMapp, Smaply, Touchpoint Dashboard)

### Outcome: REFINE (two further, code-confirmed interaction gaps; both small)

### What was found

Operator asked to go deeper specifically on how dedicated journey-mapping tools handle the full create-a-stage-and-fill-it-in flow, beyond the tool-comparison breadth already done in Part 1/2. Three more dedicated tools (FlowMapp, Smaply, Touchpoint Dashboard) were researched directly, and two new findings emerged — both confirmed against this app's own code, not just inferred from the competitor research.

1. **FlowMapp and Smaply both support inserting a new stage directly between two existing ones (hover-between, click "+"); this app can only append a stage at the end.** Confirmed directly in code: `handlePostJourneyStage` always computes the new stage's position server-side as `MAX(position) + 1` — there is no path to insert at an arbitrary position in one action. Inserting "in the middle" here requires two separate actions of two different interaction types: add (via the button, lands at the end) then drag-and-drop or the `.sw-stage-move` buttons to reorder it into place — both of which already exist and work (per `handlePatchJourneyStagesOrder`), so this is a friction/extra-step gap, not a missing capability.

2. **Smaply's primary stage/card-editing entry point is double-clicking the card itself; Touchpoint Dashboard's is clicking a touchpoint cell directly.** This app's only entry point into the same 8-field editor is a single small text link ("Edit stage"), either inside a drawflow canvas node or in the swimlane grid's own header cell — confirmed directly in the rendering code (`'<a href="#" class="sw-stage-edit"...>Edit stage</a>'`, styled at `font-size:12px` inside the grid header). The small-link entry point is a real, if minor, contributor to "clunky" — smaller hit target, easy to miss. **Correction made during this same research pass, before this became a recommendation:** a further, targeted search on double-click as a web convention found it is NOT the right fix to copy from Smaply — double-click is uncommon on the web (a desktop-app relic), not self-evident, fails WCAG 2.1.1's keyboard-operability requirement without a separate accessible alternative, and causes real "micro-failure" timing errors. Smaply itself is a specialized canvas/diagramming tool, closer to desktop-app conventions, so its own double-click pattern doesn't generalize to a standard web page. Touchpoint Dashboard's "click the cell directly" (single-click) is the better-grounded convention to borrow instead, and single-click on a native, focusable element is keyboard-accessible by default (Enter/Space), with no extra work needed.

### Reasoning

Both findings are specific, code-confirmed, and small in scope — neither requires touching the swimlane grid's own structure (`jcx-s6`) or the panel's own fields. Finding 1 is a nice-to-have (the capability already exists two steps away, just not as one direct action). Finding 2's real fix is enlarging the SINGLE-click target (e.g. making the whole grid header cell clickable, not only its small text link), not adopting double-click — caught and corrected within this same research pass rather than carried into a recommendation and found wrong later.

## Part 5 — Internal consistency check (this app's own existing patterns)

### Outcome: one finding elevated to a standards violation; no new conflicting convention found

### What was found

Before finalizing any new convention (a save-feedback indicator, a larger click target), checked whether this codebase already has an established pattern for either, to avoid inventing a second, inconsistent one.

1. **No existing autosave-indicator pattern exists anywhere else in this codebase to reuse.** A repo-wide search for save-state indicator markup (`*-saved`/`*-saving` classes, `aria-live` save regions) found exactly one match: `journeys.js`'s own `sw-stage-panel-saved` span — the very element Part 3 recommends upgrading. There is no competing or more-mature convention elsewhere; the Part 3 recommendation would be establishing this codebase's first proper save-state-indicator pattern, not deviating from one.
2. **The view-reset-on-save behaviour (Part 2, finding 2) is not merely an external best-practice gap — it directly violates this repo's own already-documented standard.** `.github/standards/web-ui/web-ui-patterns.md` has a dedicated rule, "Client-side DOM patch vs. full page reload after a POST action": a page with live, in-progress client state must patch the DOM in place from the response, never reload, and reload is reserved for exactly 3 named static/administrative pages (`products.js`, `settings.js`, `kanban-view.js`) — the journey canvas is not one of them. This single check turned an "also worth doing" item into a confirmed standards violation, and its priority has been raised accordingly in the combined list below.
3. **No other competing single-click-target or double-click convention was found elsewhere in this app** — the Part 4 single-click-target correction stands without any internal precedent either confirming or contradicting it.

### Reasoning

Checking internal consistency before committing external research to a recommendation caught one real escalation (finding 2) and confirmed no risk of introducing a second, conflicting convention for the other two items. This is now standard practice worth repeating for any future spike that proposes a new UI/interaction pattern in this codebase.
