**2026-10-11 | RISK-ACCEPT | jcx-s1 /verify-completion**
**Decision:** Accept jsdom-based `dispatchEvent`-driven DOM interaction tests (including `getComputedStyle` visibility assertions) as the verification evidence for AC5 (placeholder renders with a distinct `sw-mapping--placeholder` class + "Placeholder" label) and the story's own Accessibility NFR (keyboard-operable Add-placeholder/Trigger affordances, visible focus state), in place of a real browser check or a Playwright spec.
**Context:** `/verify-completion`'s mandatory live-browser render check could not be performed — the local dev server starts and logs "listening on port 3000" with a real Postgres connection, but every HTTP request to it (including a cold `GET /`, before any of jcx-s1's own routes are reached) never completes. Reproduced two independent ways (the Claude-in-Chrome extension's `navigate`, and a plain `curl`); both show the TCP connection reach `ESTABLISHED` (confirmed via `netstat`) but no HTTP response ever returns. Not explained by this story's own diff. No Playwright spec exists for this new UI either (it is new this story).
**Rationale:** The substituted jsdom tests go beyond mere DOM-presence checks — they assert `getComputedStyle(form).display` transitions (hidden → visible on "Add placeholder" click) and real `dispatchEvent`-driven click/submit flows against the actual rendered markup, matching this codebase's own established "(new route, E2E)" convention (e.g. `check-ep2-s3-delivery-view.js`'s Remove-button test) for exactly this situation. The new UI elements are plain native `<button>`/`<input>`/`<form>` elements with no custom focus-trap or `outline:none` override, so default browser keyboard-operability and focus-visibility apply by standard HTML semantics — not independently re-verified live this story, which is the actual residual gap this RISK-ACCEPT covers.
**Made by:** Claude (session), approved by Hamish King (Platform Owner) via `AskUserQuestion` before `/branch-complete`.
**Revisit trigger:** If the local dev server's HTTP-hang issue is resolved in a future session, perform a real live-browser check against jcx-s1's shipped UI retroactively and update this entry's outcome. Also revisit if any future story adds custom focus-management or non-native interactive elements to this same Add-placeholder/Trigger UI, since the "default HTML semantics cover it" rationale would no longer hold.

**2026-10-11 | DESIGN | /spike (cjm-best-practice)**
**Decision:** Treat the journey-map job and the flow/process-diagram job as two distinct workstreams rather than converging the canvas and the Customer experience tab into one merged visual. The Customer experience tab becomes the real, standards-compliant journey map (emotion curve + persona card, added to its existing swimlane shape); the free-form canvas (`ic-s1`–`ic-s4`) keeps its existing implementation but has its own stated purpose reframed as a stage-structure/flow editing view, not a second journey-map attempt.
**Context:** Operator shared 3 reference journey-map examples (Spotify flow, supermarket shopping map, Hustle Badger template) as a quality bar and asked for a CX research spike to inform the best way to converge the existing canvas and Customer experience tab toward that bar.
**Rationale:** A CX/UX best-practice spike (`artefacts/2026-10-11-journey-cx-redesign/spikes/cjm-best-practice-outcome.md`) found that journey maps (empathy/stakeholder artefacts: what the user experiences) and flow/process diagrams (design/dev artefacts: what the system does) are established as different tool categories with different purposes (Nielsen Norman Group, Six Sigma). All 3 reference examples are journey maps by this definition; the existing canvas is structurally a flow diagram regardless of restyling. Tools that offer both (e.g. Miro) keep them as distinct, linked views rather than one merged visual — no precedent found for forcing convergence. The Customer experience tab is the structurally correct target for closing the gap to the references, and already has the right shape (swimlane) and most of the needed data (emotion, pain points, opportunities per stage) — the gap is presentation, not data.
**Made by:** Claude (spike investigation), confirmed by Hamish King (Platform Owner) via direct reply to the spike outcome.
**Revisit trigger:** If a future need emerges for the canvas itself to carry empathy/stakeholder-communication framing (not just stage structure/flow), revisit whether a third, purpose-built view is warranted — ruled out this time only because nothing in the current scope calls for it.

**2026-10-11 | ASSUMPTION | /clarify**
**Decision:** Resolved all 4 unconfirmed assumptions flagged in `/discovery`, locking scope before `/benefit-metric`:
1. **Placeholder-feature trigger mechanics:** creates a new `artefacts/[feature-slug]/` folder, seeds `/discovery`'s Section 1 only with journey-stage context (name, description, emotion, pain points, opportunities, touchpoints). Operator still walks through the rest of discovery normally.
2. **Mapping persistence:** the journey-stage-to-feature mapping persists and auto-converts from "placeholder" to "linked real feature" once the triggered discovery is approved. Requires a new state field on `ep2-s3`'s existing `feature_customer_journey_stage_mappings` data model.
3. **Authorization:** triggering a new outer-loop run uses the same authorization as any other mutating action in this app (non-viewer tenant member) — no new, finer-grained permission tier. The pipeline's own human-approval gates (discovery approval, DoR sign-off, etc.) are the structural safeguard against low-quality triggers, not a special access check.
4. **Emotion-data coverage:** confirmed existing journeys' `emotion` field is mostly empty today — this is genuinely new behaviour operators haven't used via the current plain-text tab. MVP scope now explicitly requires a "no emotion data yet" empty state for the emotion curve, not an assumption of pre-populated real data from day one.
**Context:** `/clarify` pass following `/discovery` approval, resolving the 4 `[ASSUMPTION]` lines the discovery artefact's own mandatory gate flagged (≥2 unconfirmed assumptions triggers the `/clarify` recommendation block).
**Rationale:** Each answer was chosen for consistency with this app's own already-established conventions rather than inventing new patterns: item 3 mirrors the uniform non-viewer-only authorization check used by every existing mutating route in this codebase; item 1/2 mirror how `/discovery` and `ep2-s3`'s own mapping model already work, extended rather than replaced; item 4 was a direct, confident operator answer (not inferred), with a real MVP-scope consequence (the empty state is now required, not optional) captured immediately in both `discovery.md`'s Assumptions and MVP Scope sections to keep the artefact internally consistent.
**Made by:** Claude (session), confirmed by Hamish King (Platform Owner), answer-by-answer.
**Revisit trigger:** If usage data after release shows item 3's authorization model is being abused (e.g. spam placeholder-triggers with no real intent to build), tighten to a restricted role rather than leaving it uniform — not pre-built now since no evidence calls for it yet.

**2026-10-11 | DESIGN | /definition (jcx-s4 data model)**
**Decision:** The journey-map persona card uses a new, dedicated end-customer persona concept (distinct from this platform's own pipeline personas already captured in every feature's `discovery.md` "Who It Affects" section) — stored as 3 new `TEXT` columns directly on `customer_journeys` (`persona_name`, `persona_role`, `persona_goal`), not a new table and not a markdown artefact. The persona editor pre-populates suggestions by scanning `artefacts/[feature_slug]/discovery.md` "Who It Affects" sections for every `feature_slug` associated with the journey's own `product_id` (via the legacy `journeys` table), rather than starting from a blank form.
**Context:** Confirmed via an `ADR-026` reuse-check (no existing table covers this concept) and a direct operator clarification on two points: (1) which persona concept the card should show (pipeline persona vs. a dedicated end-customer persona — operator confirmed the latter), and (2) whether it should be DB columns or a markdown artefact (operator confirmed DB columns), plus an operator-requested enhancement to pre-populate from existing discovery artefacts rather than starting blank.
**Rationale:** `customer_journeys.product_id` already exists (confirmed by reading `server.js`'s own inline migration directly), giving a precise, already-available scope boundary for the discovery-artefact scan — no new association mechanism needed. DB columns (not a markdown artefact) keep the persona editable inline on the same page as the rest of the journey's data, consistent with how `emotion`/`pain_points`/`opportunities` are already stored and edited today.
**Made by:** Claude (session), confirmed by Hamish King (Platform Owner), answer-by-answer.
**Revisit trigger:** If a future need emerges for multi-persona support per journey, or for the pre-population scan to also incorporate structured persona data (not just prose from "Who It Affects"), revisit this data model.
