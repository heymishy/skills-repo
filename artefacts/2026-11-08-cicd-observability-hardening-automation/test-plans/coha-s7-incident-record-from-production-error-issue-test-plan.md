## Component names used below (final file names are the implementation plan's call)

- **Logic module:** `scripts/lib/error-issue-incident.js`. Pure functions over data: `recogniseIssue(event, config)`, `branchNameFor(id)`, `planRecord(recognised)`, `buildPullRequest(recognised)`, `decideIdempotency(facts)`. No git, no network.
- **Command-line script:** `scripts/error-issue-incident.js`. Reads the event JSON from a file path (never from a command-line argument), takes the bridge author login and a facts file (existing branches, open pull requests) as inputs, requires an explicit `--incidents <path>` to the incident file copy (it never defaults to `workspace/incidents.json`), and has `--dry-run`. It writes a plan JSON (`action` is one of `open`, `skip`, `decline`, `dry-run`, plus a fixed `reason`) and, for `open`, appends the record to the given file copy using the real `recordIncident` from `src/modules/incident-recorder.js`.
- **Workflow:** `.github/workflows/error-issue-incident-record.yml`, a recognise job then a record job, as the story's architecture constraints say. The git and `gh` steps live in the workflow; they are inspected structurally by the wiring tests W1 to W12 and proven live only after merge.
- **D37 (injectable adapter rule):** this design introduces no injectable adapter (decisions are made on data passed in, and the git and pull request steps are plain workflow steps), so the D37 stub, wiring task and wiring-test rule do not apply. If the implementation plan introduces an adapter after all, D37 applies to it in full.

## Test data strategy

- **Source:** Mixed. (1) Issue bodies are generated by the REAL producer, not hand-written: the test builds the body with `require('../src/web-ui/routes/error-bridge')._internals.buildBody(fields, marker)` and the real exported label constant, so the parser is tested against what coha-s6 actually emits and a drift between the two fails here (mock-shape verification, CLAUDE.md). (2) The surrounding GitHub event envelope is synthetic, generated in setup with the documented fields `action`, `issue.number`, `issue.html_url`, `issue.title`, `issue.body`, `issue.user.login`, `issue.labels[].name`, `repository.full_name`; variants (other author, no label, no marker, two markers, bad ids, hostile titles) are produced by small builders. (3) Incident files are temporary copies seeded with two synthetic records written in setup; the real `workspace/incidents.json` is never read or written by any test. (4) Git behaviour (two records branched from one base, the conflict, the rebuild) uses real `git` in a temporary directory with a local bare "origin"; nothing contacts GitHub.
- **Sensitivity:** none. Generated UUIDs and made-up logins only. The bridge author login in tests is a made-up value, never the real account. Log-capture tests seed a canary string in the issue body and assert it never appears in any output line.
- **Gaps:** the exact payload GitHub sends for an `issues` `opened` event and the shape `gh api` returns for the hand-start path are taken from GitHub's documentation, not captured from a real run (see the gap table). Everything else is available now.

## Findings from writing this plan (all four settled at `/definition-of-ready`, 2026-11-14; see "Resolution" under each)

1. **A single concurrency group loses runs.** The story says a concurrency group serialises two simultaneous runs so neither fails. GitHub Actions keeps at most one running and one pending run per group and cancels an older pending run when another arrives, so with three issues opened at once one run is cancelled and its record never made. The tests therefore require a group that includes the issue number (so runs for different issues never cancel each other) and `cancel-in-progress: false` (W3). Runs for different issues do not need to be serialised: each uses its own branch built from the current `master`; a later merge conflict is handled by the rebuild (AC7, I4). The same-issue duplicate case is handled by the idempotency check (AC2). This refines the story's wording. **Resolution:** accepted by the operator and written into the story's constraints (DoR amendments).
2. **The real pull request creation has no automated or acceptance-criterion proof.** Only AC8's dry run creates nothing. The path that matters (the branch push and `gh pr create` under the workflow's own token, with Actions allowed to create pull requests) is exercised by no test and no AC until the first real production error. **Resolution:** the operator chose to add a ninth acceptance criterion, AC9, a live non-dry run on a hand-opened test issue that opens a real data-only pull request which the operator then closes unmerged (and whose branch is deleted). It is public-repository activity, so it needs the operator's approval immediately before it runs, like coha-s6's live run. The story was amended and its amendments reviewed (review run 4).
3. **Author comparison is exact and fails closed (U7, U8).** The workflow variable must hold the account's login in the exact letter case GitHub reports. If the variable is unset or empty, no issue is ever recognised. A wrong-case variable therefore declines everything (visible in the run log) rather than accepting an unintended account. **Resolution:** accepted and written into the story.
4. **Pull request text hardening (U13).** The story says the pull request title and body contain only the fixed code and issue number. A code such as `@everyone` or one with markdown would still notify people or render oddly if inserted raw. The test requires the code to appear only inside inline code formatting, single-line, with any backtick neutralised, so nothing in it can ping or format. **Resolution:** accepted and written into the story.

## Unit tests

Logic module and command-line script, with no GitHub and no real incident file. Each starts from fresh temp files.

**U1 (AC1): the fixed fields are read from the real coha-s6 issue body.** Precondition: an event whose body was built by the real `buildBody` with a known code, first-seen time, environment `production`, PostHog link and UUID, author equal to the configured bridge author, label `production-error`. Action: `recogniseIssue(event, config)`. Expected: recognised, and it returns exactly the code (from the title), first-seen time, environment, PostHog link, PostHog id and the issue number and URL. (Separate assertions per field so a failure names the field.)

**U2 (AC1): the PostHog id and branch name.** Action: as U1, then `branchNameFor(id)`. Expected: the id equals the marker's UUID and the branch is exactly `incident/posthog-<id>`.

**U3 (AC1): the record plan.** Action: `planRecord(recognised)`. Expected: `summary` equals the fixed code verbatim; `tags` contain `production-error` and `posthog:<id>` (both lowercase, as the store lowercases tags); the joined tags are within the store's 200-character limit.

**U4 (AC1): the trigger names the issue link and the PostHog id.** Expected: the `trigger` text contains the GitHub issue URL and the PostHog id, and contains no first-seen time, environment or PostHog link text beyond what the story fixes.

**U5 (AC1): the pull request text.** Action: `buildPullRequest(recognised)` with a canary placed in the first-seen, environment and PostHog link fields of the issue. Expected: the title and body contain the fixed code and the issue number, and the canary appears in neither; title is one line and at most 200 characters. The hand-off the recognise step gives the record step (a JSON file or env-only outputs) contains only the fixed fields (code, first-seen time, environment, PostHog link, issue number, PostHog id) and none of the canary text from the issue body.

**U6 (AC3): an issue from any other author is declined.** Action: events identical to U1 but with a different `user.login`, including one whose title, body and label match perfectly. Expected: `recognised: false`, reason `author`, and the plan action is `decline`.

**U7 (AC3): an unset or empty bridge author variable declines everything.** Action: configuration with the author `undefined`, `''` and whitespace; events with an author and with `user` missing or `login` empty. Expected: every case declines (never recognised), including an event with an empty login against an empty variable.

**U8 (AC3): the login comparison is exact.** Action: the configured author `Example-Bot`; events with `Example-Bot`, `example-bot`, `Example-Bot ` and `Example-Bo`. Expected: only the first is recognised. (Decision recorded in the findings above.)

**U9 (AC4): the label is required at the moment of opening.** Action: events with no labels, `labels: []`, `labels: null`, labels `production-errors`, `Production-Error`, `production_error`, and the correct label among several others. Expected: only the exact `production-error` label recognises; the others decline with reason `label`.

**U10 (AC4): the marker must be a whole line.** Action: bodies with no marker; the marker embedded in a sentence; the marker preceded by `> ` or by spaces; the marker line written without the space after the colon; the correct marker with `\n` line endings and with `\r\n` line endings. Expected: only the two correct forms recognise; the others decline with reason `marker`. (A marker line that does start at the beginning of a line but whose value is not a lowercase UUID, such as a valid id followed by trailing text, is U12's `id` case, not this one.)

**U11 (AC4): two different markers are ambiguous.** Action: a body holding two marker lines with different UUIDs; a body holding the same marker twice. Expected: different ids decline with reason `marker-ambiguous`; the same id twice is accepted as one.

**U12 (AC6): a marker whose id is not a lowercase UUID creates no branch.** Action: ids `../x`, `a b`, `ABCDEF01-...` (uppercase), a 35-character and a 37-character id, a valid id followed by `;rm`, and an empty id. Expected: each declines with reason `id`, no branch name is produced, and the reason text never contains the raw id.

**U13 (AC6): hostile text stays inert data.** Action: titles `` `touch x` ``, `$(touch x)`, `"; touch x; "`, `${{ secrets.X }}`, `<img src=x onerror=alert(1)>`, `@everyone`, a title with a backtick and a title at 120 characters. Expected: the record plan's `summary` equals the title verbatim (stored as data, tested through the real store in I1); the pull request title and body place the code only inside inline code formatting with any backtick replaced, contain no raw `@`-mention outside it, and stay single line.

**U14 (AC2): the idempotency decision.** Action: `decideIdempotency` over facts. Expected, each as its own assertion: a record tagged `posthog:<id>` already in the master incident file gives `skip` with reason `already-recorded`; an existing branch `incident/posthog-<id>` gives `skip`, `branch-exists`; an open pull request for that branch gives `skip`, `pr-open`; none of these gives `open`. The tag match is exact: `posthog:<id>` does not match a record tagged `posthog:<id>-x` or one containing the id as a prefix or suffix. The three reasons are distinct strings.

**U14b (AC7, AC2): the rebuild switch lifts only the branch and pull request skips.** Action: `decideIdempotency` over the same facts with the rebuild flag set, plus a hand-start rebuild through the script. Expected: with the branch present, or an open pull request present, the decision is `rebuild` (not `skip`); with a record tagged `posthog:<id>` already on the master incident file the decision is still `skip`, `already-recorded` (a record on master always skips, even with the switch); with nothing present the decision is `open`; the rebuild plan names the same `incident/posthog-<id>` branch and never a second branch name or a second pull request.

**U15 (AC2): closed pull requests.** Action: facts where the only pull request for the branch is closed and unmerged, with the branch gone; and closed and unmerged with the branch still present. Expected: the first gives `open` (a new attempt is allowed); the second gives `skip`, `branch-exists` (the existing branch decides). The case is documented so the behaviour is deliberate.

**U16 (AC8): the dry-run plan.** Action: run the script with `--dry-run` on a recognised event against a temp incident file. Expected (also with the rebuild flag set together with `--dry-run`: a dry run never changes anything): the plan action is `dry-run`; the output contains the record fields and the pull request title and body that would be used; the incident file's bytes are unchanged (hash before and after); no branch name is written anywhere except the printed plan.

**U17 (AC8, safety): an explicit incident file path is required.** Action: run the script without `--incidents`, and with a path inside a directory that does not exist. Expected: exits non-zero with a fixed message and prints no plan with action `open`; and a source-text check of `scripts/error-issue-incident.js` finds neither `DEFAULT_INCIDENTS_FILE` nor the text `workspace`, so there is no code path that can fall back to the real incident file (the real `recordIncident` falls back to it when given no path, so the script must always pass one).

**U18 (AC6): a hostile event run as a real child process executes nothing.** Action: write an event file whose title and body contain `$(touch SENTINEL)`, `` `touch SENTINEL` ``, `; touch SENTINEL`, and newlines; run the real script as a child process with arguments passed as an array (no shell). Expected: exit code is 0 or the fixed decline code, the sentinel file does not exist, and the output contains no part of the body text.

## Integration tests

**I1 (AC1, AC5): the real record creation against a temp copy.** Components: script, `recordIncident`, the incident store, the triage drafter. Precondition: a temp incident file seeded with two synthetic records. Action: run the script for a recognised event in `open` mode against the copy. Expected: the file now holds exactly three records; the first two are byte-identical to before; the third has `type` `incident`, `status` `open`, `summary` equal to the code, tags containing `production-error` and `posthog:<id>`, a `trigger` naming the link and id, a non-empty `triageSummary` (the drafter ran), and passes the store's own `validateRecord`.

**I2 (AC5): the product page renders it.** Components: the real product page handler used by `tests/check-itar-s3-web-ui-rendering.js` (`handleGetProductView` with the real `realFetchRepoPath` over a stubbed `global.fetch` that serves the file's text). Action: render with the I1 file. Expected: the page contains one incident item per record (three), shows the new record's code and its status, and does not throw; a second case with code `<b>x</b>` shows the characters escaped, not as markup.

**I3 (AC5): the store loads it.** Action: `loadIncidentRecords`, `withDefaultType` and `validateRecord` on the I1 file. Expected: all three records load, `withDefaultType` returns the new record unchanged, and no function throws.

**I4 (AC7): two branches from one base conflict, and a rebuild fixes it.** Components: script and real `git` in a temp directory with a local bare origin. Precondition: `master` holds the seeded incident file. Action: build record A on `incident/posthog-A` and record B on `incident/posthog-B`, both from the same base; merge A into master; then try to merge B; then rebuild B from the current master (the same operation the workflow performs: `git checkout -B incident/posthog-B origin/master`, build, commit) and merge again. Expected: the first attempt to merge B conflicts (this proves the rebuild is needed); after the rebuild the merge is clean and master's incident file holds the seeded records plus A and B, each exactly once. The rebuild's push uses `--force-with-lease` against the temporary origin and updates the existing `incident/posthog-B` branch in place: afterwards the origin still has exactly one branch for B and its tip is the rebuilt commit (the force push is proven here with real git, not left to the live runs).

**I5 (AC7, AC8): a hand-started run applies the same recognition.** Action: run the script in hand-start mode (the issue fetched by number; its labels are the issue's current labels) with an issue object shaped like GitHub's REST issue response (same fields as the event) for (a) a recognised issue, (b) an issue by another author, (c) an issue with no marker, (d) an object carrying a `pull_request` key (the issues API also returns pull requests). Expected: (a) opens, (b) and (c) decline with the same reasons as the event path, (d) declines with a fixed reason. A hand start never bypasses recognition.

**I6 (AC1, AC2): the full script flow, twice.** Action: run `plan` then `open` for an issue with empty facts, then run again with facts that now list the branch and the record. Expected: the first run's plan is exactly one action `open` with one branch name and one pull request; the second run's plan is `skip` with `branch-exists` or `already-recorded` and the incident file is not changed a second time.

## Workflow-file wiring tests (always run; read the YAML text, no YAML library, in the style of `tests/check-cif-s1-deploy-concurrency-guard.js`)

**W1 (AC4): the trigger is issue opened only, plus hand start.** Expected: `on:` has `issues` with `types` declared explicitly and exactly `[opened]` (omitting `types` would trigger on every issue activity, including labelling) (not `labeled`, `edited`, `reopened`, `transferred`) and `workflow_dispatch` with inputs for the issue number, `dry_run` and `rebuild`.

**W2 (security, NFR): least-privilege job permissions.** Expected: the top-level permissions are `contents: read` or empty; the recognise job has `contents: read` and `issues: read` and nothing else (the second only to fetch the issue on a hand start); the record job has exactly `contents: write` and `pull-requests: write`; no job has `issues: write`, `actions`, `id-token`, `packages` or `write-all`; the record job needs the recognise job and runs only when its output says to.

**W3 (AC7, finding 1): concurrency does not drop runs.** Expected: a `concurrency` group whose expression covers both the event's issue number and the dispatch input's issue number (so automatic and hand-started runs for the same issue share a group) and `cancel-in-progress: false` (or absent).

**W4 (AC6): untrusted text never reaches a shell or an expression.** Expected: no `run:` block contains any `${{ ... }}` expression other than `github.repository`, `github.run_id` and `runner.temp` (everything else, including inputs, variables, secrets and the outputs of other jobs and steps, reaches a step only through its `env:` block); the strings `github.event.issue.title`, `.body`, `.user`, `.labels` and `github.event.comment`, `github.head_ref` appear nowhere in the file; the event is read by the script from `$GITHUB_EVENT_PATH` or a file written from `gh api`.

**W5 (security, NFR): the workflow never pushes to or merges into `master`.** Expected: every `git push` targets `refs/heads/incident/posthog-` followed by a validated id; no step pushes to `master` or `main`, uses `--admin`, `gh pr merge`, `gh pr ready`, or approves a pull request; `gh pr create` names `--base master` (the operator, not the workflow, reviews and merges).

**W6 (AC8): the dry run creates nothing.** Expected: the branch push and the `gh pr create` steps run only when the script's plan output is `open`; with `dry-run` or `skip` or `decline` they do not.

**W7 (security, NFR): checkout and credentials.** Expected: the recognise job's checkout sets `persist-credentials: false`; each job has `timeout-minutes`; no `pull_request_target` trigger; the workflow checks out `master` (never the issue's or a pull request's ref).

**W8 (security, NFR): no third-party actions.** Expected: every `uses:` is `actions/checkout` (pinned to a version tag or commit hash already used by other workflows in this repository); no other action.

**W9 (AC7): the branch is rebuilt from the current master.** Expected: the record job creates the branch with a fresh reset from `origin/master` (`git checkout -B incident/posthog-<id> origin/master` or equivalent), and a re-push of its own branch uses `--force-with-lease` limited to that branch name; the incident file is never taken from the issue.

**W10 (AC3): the bridge author is a workflow variable.** Expected: the author comes from `vars.<name>` and no literal login string for the operator's account appears in the workflow file.

**W11 (reliability, NFR): bounded and visible.** Expected: both jobs set `timeout-minutes`; the recognise job writes the plan's `reason` to the run log (a step that prints the plan summary), so a decline is visible.

**W12 (security, NFR): no credentials in tracked files.** Expected: none of the new files (workflow, script, module, fixtures) contains a string matching `ghp_`, `github_pat_`, `gho_`, `AKIA` or a private key header; the workflow uses only `secrets.GITHUB_TOKEN`.

## NFR / behaviour tests

**N1 (Audit): every outcome logs once with a fixed reason and no issue text.** Action: run the script for each outcome (open, skip x3, decline x5 for author, label, marker, ambiguous marker, id, dry-run) with a canary seeded in the body's extra text, the first-seen time, the environment and the PostHog link (not the title: a dry run prints the title as the record's summary, by design). Expected: exactly one result line per run (a line starting `error-issue-incident: `) carrying the outcome, the fixed reason string and the issue number; the canary never appears in stdout, stderr or the output file. A dry run may print one further line, starting `error-issue-incident-dry-run: `, holding the record and pull request it would create.

**N2 (Reliability): a failed run leaves nothing half done.** Action: run `open` against (a) an unreadable incident file, (b) an incident file holding invalid JSON, (c) a path that is a directory. Expected: non-zero exit with a fixed message, no plan with action `open` printed, and, where the file exists, its bytes unchanged.
