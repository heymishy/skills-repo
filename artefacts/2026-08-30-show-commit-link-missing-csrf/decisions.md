### ARCH — Root cause confirmed via real logs before designing a third fix attempt (2026-08-30)

**Context:** This is the third fix attempt at the same user-reported "Forbidden" bug in one session. `cptr-s1` fixed a real but ultimately unrelated session-persist timing race. `jgcc-s1` fixed a real, confirmed-missing `_csrf` field on the server-rendered gate-confirm form — necessary, but live re-validation showed it was not sufficient: a fresh, single click still 403'd. Rather than design a fourth guess, `csdl-s1` added temporary, non-secret-leaking diagnostic logging (session id prefix, machine id, token prefixes) to `csrf.js`, deployed it, and reproduced the failure twice cleanly (brand-new journeys, uncontaminated by prior test sessions).

**Decision:** Read the real logs (`flyctl logs -a wuce-staging`) before writing any more fix code. This required the operator to authenticate `flyctl` themselves (`flyctl auth login`, a browser OAuth flow) — done in-session at the operator's initiative.

**Finding:** `flyctl machines list -a wuce-staging` showed exactly ONE machine — directly refuting the leading (unconfirmed) hypothesis from `csdl-s1`'s own decisions.md that multi-machine stale in-memory session-cache drift was the cause. The real log lines for both clean repros showed `submittedPrefix: "(empty)"` against a correctly-populated `expectedPrefix` — not a mismatch between two different valid tokens, a genuinely empty submitted value. Direct DOM inspection (`javascript_tool`, `querySelector('input[name="_csrf"]')`) on the same page, immediately before the failing click, showed the field correctly populated in the DOM at rest. This pointed away from any session/persistence mechanism entirely and toward a rendering-path bug: something in this codebase builds a SECOND copy of this same form that omits the field. Reading `showCommitLink()`'s source directly confirmed it: a client-side JS function that live-injects its own gate-confirm form via `innerHTML` whenever a stage completes during the streaming response, entirely separate from the server-rendered path `jgcc-s1` fixed, and never given a `CSRF_TOKEN` JS variable to embed.

**Rationale:** Every fix in this investigation that was designed WITHOUT first gathering direct evidence (the SIGTERM-based `cptr-s1` design, and implicitly `jgcc-s1`'s assumption that the server-render path was the only one) either had to be walked back or turned out to be necessary-but-incomplete. The one design step in this whole investigation that WAS preceded by direct evidence-gathering (`csdl-s1`'s logging, then reading the real logs) identified the actual mechanism on the first attempt. This confirms the standing pattern from this session's earlier corrections: verify before designing, not after.

**Follow-up (tracked, not deferred silently):** `csdl-s1`'s diagnostic logging remains live in production after this fix merges — removing it is an explicit follow-up noted in `csdl-s1`'s own decisions.md, deliberately not bundled into this PR to keep this fix's diff minimal and reviewable on its own.
