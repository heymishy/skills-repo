# Decisions: Customer Journey as First Class

## D1: Migration script lives at `scripts/migrate-schema-journeys.js`, not `src/web-ui/migrations/`

**Date:** 2026-10-08
**Context:** The ep5-s1 DoR's own "Estimated touch points" named `src/web-ui/migrations/migrate-schema-journeys.js` as the new file's location, but no `src/web-ui/migrations/` directory exists anywhere in this codebase.
**Decision:** Created the migration at `scripts/migrate-schema-journeys.js` instead, matching the real, already-established convention for this repo's other schema migrations (`scripts/migrate-schema-credits.js`, `scripts/migrate-schema-pg.js`, `scripts/migrate-schema-users.js`).
**Rationale:** Following a DoR-assumed path that doesn't match any real convention in the codebase would create a one-off inconsistency future operators would have to rediscover. The existing `scripts/migrate-schema-*.js` family already establishes the injectable-`setDbClient`/`migrate(dbOverride)` pattern this script also follows.

## D2: `journeys.product_id` references `products(product_id)`, not `products(id)`

**Date:** 2026-10-08
**Context:** The ep5-s1 DoR's own authored SQL wrote `product_id UUID REFERENCES products(id)`. The real `products` table (created in `src/web-ui/server.js`, line ~870) has its primary key column named `product_id`, not `id` — there is no column literally named `id` on that table.
**Decision:** Fixed the FK to reference `products(product_id)`.
**Rationale:** The DoR's SQL would have failed at migration time in any real environment (Postgres rejects a FK referencing a non-existent column) the first time this script actually ran against a database where `products` already exists. Caught by cross-checking the DoR's assumption against the real table definition before implementing, not after a failed deploy.

## D3: Migration test SKIPs (not fails) when `DATABASE_URL` is absent

**Date:** 2026-10-08
**Context:** The ep5-s1 DoR's own test design specified: "All tests require `DATABASE_URL` to be set — if absent, all tests fail." `npm test`'s CI run (`.github/workflows/pr-checks.yml`) has no `DATABASE_URL` wired for any job.
**Decision:** `tests/check-ep5-s1-migration.js` prints a `[SKIP]` message and exits 0 when `DATABASE_URL` is unset, matching this repo's own already-established convention for every other DATABASE_URL-dependent integration test (e.g. `tests/check-idp-s1-persist-ideas-in-postgres.js`).
**Rationale:** Following the DoR's literal instruction would make this one new test file unconditionally fail every future PR's CI run, not just this story's own — a real regression to the whole pipeline, not a scoped risk to this story alone.

## D4: Renamed `journeys`/`journey_stages`/`feature_journey_stage_mappings` to `customer_journeys`/`customer_journey_stages`/`feature_customer_journey_stage_mappings`

**Date:** 2026-10-08
**Context:** `src/web-ui/adapters/journey-store-pg.js` already owns a table literally named `journeys` — the platform's own outer-loop session persistence (`journey_id VARCHAR PRIMARY KEY, tenant_id, owner_id, feature_slug, created_at, data JSONB`), created on every server boot via `migrateSchema()` (`server.js:421`). `ep5-s1`'s own `CREATE TABLE IF NOT EXISTS journeys (...)` (a completely different, incompatible shape) silently no-ops against this in every real environment — the feature's intended schema never actually gets created. Found while investigating the real wiring pattern for `ep1-s1`'s own route handler, before implementing it against a broken foundation.
**Decision:** Renamed all 3 of the feature's own tables to a non-colliding, feature-specific prefix (operator's own choice, confirmed in chat 2026-10-08). `journey_stages` and `feature_journey_stage_mappings` did not themselves collide with anything (confirmed by grep across `src/web-ui`) but were renamed too for naming consistency.
**Rationale:** This is a correctness defect, not a style preference — without the rename, no downstream story in this feature can ever work against real data, since the tables they assume exist never actually get created. Fixed via a dedicated follow-up story (`ep5-s3`) rather than quietly amending `ep5-s1`'s already-merged commit, so the correction and its rationale are visible in history.

## RISK-ACCEPT: ep1-s2 AC1 ("+ Add stage" inline-card focus behaviour) — no E2E spec, manual verification only

**Date:** 2026-10-08
**Context:** `ep1-s2` AC1 ("Given I click '+ Add stage'... a new stage card appears... with an inline name field in focus") is a pure client-side DOM/focus behaviour with no server-testable component — it is not CSS-layout-dependent in the sense B2's gate targets (no visual alignment, breakpoint, or pixel rendering assertion), but it is still real browser-only behaviour a Node unit test cannot exercise.
**Decision:** RISK-ACCEPT — no dedicated Playwright spec added for this story. A manual verification step is named instead (click "+ Add stage" on a real journey canvas; confirm a new inline-input stage card appears, focused, at the end of the list).
**Rationale:** Complexity 1/Stable, and the blast radius of this specific behaviour being wrong is small and self-evident on first manual use (a missing focus call, or a card not appearing, is immediately visible — it does not silently corrupt data, since AC2/AC3's own server-side insert/validation logic is fully unit-tested regardless of whether AC1's focus behaviour works). A dedicated E2E spec is deferred to `ep1-s4` (drag-and-drop), the first story in this epic where the canvas's interactive behaviour is complex enough to justify one.

## D5: ep1-s3's focus-trap/Escape ACs get a real E2E spec, not another RISK-ACCEPT — and it cannot run this session

**Date:** 2026-10-08
**Context:** `ep1-s3`'s AC1 (interaction half), AC4, and AC5 are client-only browser behaviours, the same general category as `ep1-s2`'s own AC1 RISK-ACCEPT above. Unlike that case, `ep1-s3`'s own Architecture Constraints name WCAG 2.1 AA focus-trap/Escape-close as a hard requirement, not an optional nicety, and this story's own Complexity rating (2, vs `ep1-s2`'s 1) is specifically because of this requirement. The existing closest precedent in this codebase (`products.js`'s `ep4s1-pods-modal`) explicitly disclaims having a full keyboard focus trap, calling one "disproportionate" for its own bounded scope — `ep1-s3` does not have that latitude, since AC5 names the requirement directly.
**Decision:** Write a real Playwright spec (`tests/e2e/ep1-s3-stage-panel-focus-management.spec.js`) covering all three, rather than deferring with RISK-ACCEPT again. It is NOT wired into CI's own Scenario A/B blocking job lists (`.github/workflows/e2e.yml` uses an explicit per-job file list, not auto-discovery; adding a new file there is a separate CI-infrastructure decision, out of this story's scope) and — confirmed by grep — `src/web-ui/adapters/fake-test-db.js` has no support for `customer_journeys`/`customer_journey_stages` at all, so the spec can only run against a real `DATABASE_URL`, which is not available in this session (no local Postgres, Docker not running, matching `ep5-s1`'s own precedent for this exact limitation).
**Rationale:** A written-but-unexecuted real test, honestly labeled as such, is stronger evidence of intent and correctness than a RISK-ACCEPT for a WCAG-mandated hard requirement — it is immediately runnable by the operator or by a future DATABASE_URL-backed CI job, and precisely documents the expected behaviour (Tab/Shift+Tab wrap points, Escape target, focus-restore target) in executable form rather than prose alone. Extending `fake-test-db.js` to support these two tables (so this and future journey-canvas E2E specs can run in the standard harness, matching the explicit follow-up already logged against `bmau-s1`'s own spec) is real, separable work and is not done here to avoid scope-creeping this already-large story further.

## D6: ep1-s4's stage-reorder endpoint is `PATCH /journeys/:id/stages-order`, and position updates use a real `BEGIN`/`COMMIT`/`ROLLBACK` transaction, not a per-row `pool.query()` loop

**Date:** 2026-10-09
**Context:** `ep1-s4`'s own Architecture Constraints require "position rebalancing on drop: update all affected `position` values in a single transaction." The obvious path name (`/journeys/:id/stages/order`) would collide with the existing dispatch regex `/^\/journeys\/[^/]+\/stages\/[^/]+$/` (`ep1-s3`'s `PATCH /journeys/:id/stages/:stageId`), which treats any single segment after `/stages/` as a `stageId` value — a request to `/stages/order` would be indistinguishable from a request to patch a stage literally named `order`. Separately, this codebase's existing mutating handlers (`handlePostJourneys`, `handlePostJourneyStage`, `handlePatchJourneyStage`) all use plain `pool.query()` calls, which give no cross-statement atomicity guarantee on a `pg.Pool` (each call may be routed to a different pooled connection) — insufficient for a multi-row position rebalance where a partial write would leave stages with duplicate or gapped `position` values.
**Decision:** (1) Name the new route `PATCH /journeys/:id/stages-order` (no slash before "order") — structurally unambiguous with the existing `/stages/:stageId` pattern, requiring no change to it. (2) Implement the handler using `pool.connect()` → `client.query('BEGIN')` → one `UPDATE` per stage → `client.query('COMMIT')`, with `ROLLBACK` in the catch branch and `client.release()` in `finally` — reusing `tenant-admin-bootstrap.js`'s `bootstrapTenantAdminIfNeeded` pattern verbatim (the only other transactional write in this codebase) rather than inventing a second convention.
**Rationale:** A distinct, unambiguous route avoids a latent routing bug that would only surface if a journey ever had (or a client ever sent) a stage id/name that happened to be the literal string `order` — cheap to avoid now, expensive to debug later. Reusing the existing transaction pattern rather than designing a new one keeps exactly one reference implementation for "how this codebase does atomic multi-row writes," which `/review` and future stories can point to.

## D7: ep1-s4's live browser render check (/verify-completion) is RISK-ACCEPT, deferred to post-deployment — same gap as D5

**Date:** 2026-10-09
**Context:** `/verify-completion`'s own "live browser render check" step requires a real browser check, Playwright visible-state evidence, or a logged RISK-ACCEPT for any diff that changes rendered UI — this story's draggable stage cards, up/down move buttons, and the reorder-error toast all qualify. Neither a real browser check nor Playwright visible-state evidence is possible this session: this is unmerged code on `feature/ep1-s4`, with no deployed environment running it, and attempting to run the new `tests/e2e/ep1-s4-stage-reorder.spec.js` locally (confirmed by actually running it with `NODE_ENV=test`) fails at `seedJourneyWithStages`'s own `POST /journeys` call — `journeyRes.headers()['location']` is `undefined` because `fake-test-db.js` has zero support for `customer_journeys` (the same gap D5 already documented for `ep1-s3`'s own spec, confirmed again here by grep). `ep1-s3-stage-panel-focus-management.spec.js` fails identically when run the same way (no usable CSRF token on the mocked home page) — proving this is the pre-existing environment gap, not a regression introduced by this story's diff.
**Decision:** RISK-ACCEPT the live render check for this session. A post-deployment smoke-test item is logged in `workspace/state.json`'s `pendingActions`: once deployed to staging, drag a stage card to a new position and confirm it persists on reload, use the up/down keyboard buttons and confirm persistence, and force a reorder failure to confirm the exact toast text appears.
**Rationale:** Matches `ep1-s3`'s own already-accepted precedent (D5) for the identical underlying constraint — this story's own W6 RISK-ACCEPT at DoR already flagged "no automated run this session" for the same reason. Blocking this story on fixing `fake-test-db.js` (a separately-logged, explicitly out-of-scope follow-up shared with `ep1-s3`) would be disproportionate and inconsistent with how the immediately-prior story in this same epic was handled and merged.

## D8: `ep4-s1`'s journey list page is `/customer-journeys`, not `/journeys` — a route-level platform collision, the same class of problem D4 fixed at the database-table level

**Date:** 2026-10-09
**Context:** `ep4-s1`'s own AC1 (as originally written at `/definition`) specifies a journey list page at `GET /journeys`. Grounding at `/test-plan` found that `GET /journeys` is already live, real route owned by an entirely unrelated platform feature: `handleJourneys` in `src/web-ui/routes/journey.js` (singular file — "bee.2," the first-run empty-state screen for this platform's own *skill-session* tracking concept, which happens to also be called "journeys" but has nothing to do with customer journeys). No story in this epic hit this collision before now because `ep1-s1`–`ep1-s4` only ever used `POST /journeys` and `GET /journeys/:id` (different HTTP method, or a sub-path with an id) — `ep4-s1` is the first story in this epic that needs the plain `GET /journeys` path itself.
**Decision:** The new journey list page lives at `GET /customer-journeys` instead. `ep4-s1`'s own AC1 and `ep4-s2`'s own AC1 (the "Journeys" nav link's target) are both corrected to reference this path. The pre-existing `GET /journeys` (bee.2) is untouched. All of `ep1`'s already-shipped routes (`POST /journeys`, `GET /journeys/:id`, `.../stages`, `.../stages/:stageId`, `.../stages-order`) are unaffected — none of them collide with `handleJourneys`, so none need renaming.
**Rationale:** Directly mirrors `D4`'s own precedent (renaming the `journeys`/`journey_stages` database tables to `customer_journeys`/`customer_journey_stages` to avoid an identical platform-level naming collision, one layer down) — the new, not-yet-launched feature adapts its own identifier rather than displacing a live, currently-used feature. `/customer-journeys` also now matches the `customer_journeys` table name exactly, which is a cleaner 1:1 mapping than the originally-drafted `/journeys` ever was. Operator confirmed this resolution (over relocating the pre-existing `bee.2` feature instead) on 2026-10-09.

## D9: `ep4-s2`'s "Journeys" nav link legitimately reintroduces the literal text `pan-s1` deliberately removed — two of `pan-s1`'s own regression tests corrected, not bypassed

**Date:** 2026-10-09
**Context:** Implementing `ep4-s2`'s new `NAV_ITEMS` entry (`{ id: 'journeys', label: 'Journeys', href: '/customer-journeys' }`) broke 3 pre-existing tests at the full-suite run: `check-pan-s1-product-aware-navigation.js`'s own `U6.1` and `check-wuce18-html-shell.js`'s own `T3.1` both asserted, as an explicit regression guard, that the literal rendered text `>Journeys<` would **never** reappear in the sidebar under any `active`/`isAdmin` combination — written specifically to protect `pan-s1`'s own 2026-07-30 removal of the *old*, product-duplicate skill-session `'journey'` `NAV_ITEMS` row (see `artefacts/2026-07-30-product-aware-navigation/decisions.md`). A third failure (`check-jrf-s1-new-feature-redirect.js`'s own `IT6`) was a downstream meta-check that re-runs `check-pan-s1`'s own suite and failed only because that one did.
**Decision:** Both tests were updated, not deleted or skipped. `T3.1` now asserts the Journeys link is present AND targets `/customer-journeys` specifically (the new, correct behaviour) instead of asserting its absence. `U6.1` now checks only for `"Run a Skill"`'s continued absence (the other half of `pan-s1`'s own original guard, still fully valid and unrelated to this story) and drops the `"Journeys"` half of its own assertion, with a comment explaining why.
**Rationale:** `pan-s1`'s own removal targeted a specific, now-defunct concept (the old skill-session journeys list, which duplicated each product's own List/Board view) — not the string "Journeys" in perpetuity. `ep4-s2`'s own `customer_journeys` feature is a different, genuinely tenant-wide concept (a journey can have no product), matching the already-established `pod-manager`/`signals` precedent for *adding* a tenant-wide `NAV_ITEMS` row post-`pan-s1`. Silently weakening or deleting the two failing assertions would have been the wrong fix — `pan-s1`'s `"Run a Skill"` guard remains fully valid and is preserved intact; only the now-incorrect half of each assertion (which conflated "the specific old journey concept" with "the string Journeys itself") was corrected, and the corrected assertions are, if anything, more precise than the ones they replaced (checking the exact href, not just presence/absence of a label).

## D11 (RISK-ACCEPT): `ep2-s1`'s live browser render check deferred to post-merge staging verification

**Date:** 2026-10-09
**Context:** `/verify-completion`'s mandatory live-browser-render-check step applies, since `ep2-s1` adds a new "Map feature" button and a feature-picker modal to the journey canvas page's rendered output. A pre-merge local real-browser check (the technique proven for `ep4-s1`/`ep4-s2`: `NODE_ENV=test` local server + `/test/session` auth bypass) is not viable for this story specifically: the canvas page itself (`GET /journeys/:id`) cannot render at all without a real `customer_journeys` row already existing in the database, and `src/web-ui/adapters/fake-test-db.js` has no in-memory backing for `customer_journeys`/`customer_journey_stages` — the same pre-existing gap already logged for `ep1-s3`, `ep1-s4`, and `ep4-s1` (D5 and those stories' own DoDs). Confirmed directly this session: the two matched `tests/e2e/*.spec.js` specs that exercise `GET /journeys/:id` (`ep1-s4-stage-reorder.spec.js`, `ep1-s3-stage-panel-focus-management.spec.js`) both fail locally with `DATABASE_URL` unset, specifically inside their own `seedJourneyWithStages`/journey-creation helper — upstream of any code this story touches, both spec files' own header comments already documenting this exact prerequisite as pre-existing and not introduced by this story.
**Decision:** RISK-ACCEPT the pre-merge live-browser-render-check gap for this story. In its place: the feature's three mutually-exclusive rendering states (error/empty/populated) and the filter/open/close behaviors are proven via 9 passing unit + jsdom behavioral tests (real script extraction + real DOM assertions, not just markup presence — see `check-ep2-s1-feature-picker.js`). A full live-browser confirmation against real staging data (clicking "Map feature" on a real stage card, confirming the real feature list renders, confirming filter/close work against the real deployed page) is committed as a required step of this story's own `/definition-of-done`, matching the exact precedent already set by `ep1-s4`'s own DoD for an identical fake-test-db-gap-driven deferral.
**Rationale:** The story's own data dependency (a real `pipeline-state.json`-reading page that also needs a real DB-backed journey to render at all) makes pre-merge local verification structurally impossible without first solving the long-standing `fake-test-db.js` gap — out of scope for this story to fix unilaterally. Deferring to a post-merge real-staging check, with an explicit commitment logged here (not a silent gap), matches CLAUDE.md's B2 rule for CSS/render-dependent ACs with neither an automated visual-regression test nor a viable pre-merge manual check.

## D13: `ep2-s2`'s AC5 reinterpreted from 403 to 404, matching this file's own established cross-tenant policy

**Date:** 2026-10-09
**Context:** `ep2-s2`'s own AC5 (as drafted) specifies a 403 response for a cross-tenant `journey_stage_id`. Every existing mutating handler in `journeys.js` uses a deliberate, explicitly-commented "404, not 403, for a cross-tenant journey id" policy (`handlePostJourneyStage`, `handlePatchJourneyStage`, `handlePatchJourneyStagesOrder` — the latter two citing it as matching every other handler in the file, tracing back to `handlePostProductModule`'s own original FORBIDDEN-vs-NOT_FOUND policy). A literal 403 would be the first handler in this entire file to diverge, leaking the existence of a stage id to a cross-tenant caller.
**Decision:** AC5 implemented as 404, matching the established, security-motivated, already-consistent convention — not logged as a fresh operator decision since this is the same resolution pattern already confirmed once this session for an analogous mismatch (`ep4-s1`'s own D8, AC5 reinterpretation).
**Rationale:** Directly mirrors D8's own precedent: a drafted AC's literal wording contradicts a deliberate, consistently-applied, security-motivated codebase convention — correcting the AC to match the established convention is the right fix, not introducing the first inconsistent handler in the file. 404 is strictly more secure than 403 here (no existence leak), so this is not a weakening of the AC's own intent.
