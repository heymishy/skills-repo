# Decisions: Customer Journey as First Class

## D1: Migration script lives at `scripts/migrate-schema-journeys.js`, not `src/web-ui/migrations/`

**Date:** 2026-10-08
**Context:** The ep5-s1 DoR's own "Estimated touch points" named `src/web-ui/migrations/migrate-schema-journeys.js` as the new file's location, but no `src/web-ui/migrations/` directory exists anywhere in this codebase.
**Decision:** Created the migration at `scripts/migrate-schema-journeys.js` instead, matching the real, already-established convention for this repo's other schema migrations (`scripts/migrate-schema-credits.js`, `scripts/migrate-schema-pg.js`, `scripts/migrate-schema-users.js`).
**Rationale:** Following a DoR-assumed path that doesn't match any real convention in the codebase would create a one-off inconsistency future operators would have to rediscover. The existing `scripts/migrate-schema-*.js` family already establishes the injectable-`setDbClient`/`migrate(dbOverride)` pattern this script also follows.

## D2: `journeys.product_id` references `products(product_id)`, not `products(id)`

**Date:** 2026-10-08
**Context:** The ep5-s1 DoR's own authored SQL wrote `product_id UUID REFERENCES products(id)`. The real `products` table (created in `src/web-ui/server.js`, line ~870) has its primary key column named `product_id`, not `id` — there is no column literally named `id` on that table.
**Decision:** Fixed the FK to reference `products(product_id)`.
**Rationale:** The DoR's SQL would have failed at migration time in any real environment (Postgres rejects a FK referencing a non-existent column) the first time this script actually ran against a database where `products` already exists. Caught by cross-checking the DoR's assumption against the real table definition before implementing, not after a failed deploy.

## D3: Migration test SKIPs (not fails) when `DATABASE_URL` is absent

**Date:** 2026-10-08
**Context:** The ep5-s1 DoR's own test design specified: "All tests require `DATABASE_URL` to be set — if absent, all tests fail." `npm test`'s CI run (`.github/workflows/pr-checks.yml`) has no `DATABASE_URL` wired for any job.
**Decision:** `tests/check-ep5-s1-migration.js` prints a `[SKIP]` message and exits 0 when `DATABASE_URL` is unset, matching this repo's own already-established convention for every other DATABASE_URL-dependent integration test (e.g. `tests/check-idp-s1-persist-ideas-in-postgres.js`).
**Rationale:** Following the DoR's literal instruction would make this one new test file unconditionally fail every future PR's CI run, not just this story's own — a real regression to the whole pipeline, not a scoped risk to this story alone.

## D4: Renamed `journeys`/`journey_stages`/`feature_journey_stage_mappings` to `customer_journeys`/`customer_journey_stages`/`feature_customer_journey_stage_mappings`

**Date:** 2026-10-08
**Context:** `src/web-ui/adapters/journey-store-pg.js` already owns a table literally named `journeys` — the platform's own outer-loop session persistence (`journey_id VARCHAR PRIMARY KEY, tenant_id, owner_id, feature_slug, created_at, data JSONB`), created on every server boot via `migrateSchema()` (`server.js:421`). `ep5-s1`'s own `CREATE TABLE IF NOT EXISTS journeys (...)` (a completely different, incompatible shape) silently no-ops against this in every real environment — the feature's intended schema never actually gets created. Found while investigating the real wiring pattern for `ep1-s1`'s own route handler, before implementing it against a broken foundation.
**Decision:** Renamed all 3 of the feature's own tables to a non-colliding, feature-specific prefix (operator's own choice, confirmed in chat 2026-10-08). `journey_stages` and `feature_journey_stage_mappings` did not themselves collide with anything (confirmed by grep across `src/web-ui`) but were renamed too for naming consistency.
**Rationale:** This is a correctness defect, not a style preference — without the rename, no downstream story in this feature can ever work against real data, since the tables they assume exist never actually get created. Fixed via a dedicated follow-up story (`ep5-s3`) rather than quietly amending `ep5-s1`'s already-merged commit, so the correction and its rationale are visible in history.

## D6: ep1-s4's stage-reorder endpoint is `PATCH /journeys/:id/stages-order`, and position updates use a real `BEGIN`/`COMMIT`/`ROLLBACK` transaction, not a per-row `pool.query()` loop

**Date:** 2026-10-09
**Context:** `ep1-s4`'s own Architecture Constraints require "position rebalancing on drop: update all affected `position` values in a single transaction." The obvious path name (`/journeys/:id/stages/order`) would collide with the existing dispatch regex `/^\/journeys\/[^/]+\/stages\/[^/]+$/` (`ep1-s3`'s `PATCH /journeys/:id/stages/:stageId`), which treats any single segment after `/stages/` as a `stageId` value — a request to `/stages/order` would be indistinguishable from a request to patch a stage literally named `order`. Separately, this codebase's existing mutating handlers (`handlePostJourneys`, `handlePostJourneyStage`, `handlePatchJourneyStage`) all use plain `pool.query()` calls, which give no cross-statement atomicity guarantee on a `pg.Pool` (each call may be routed to a different pooled connection) — insufficient for a multi-row position rebalance where a partial write would leave stages with duplicate or gapped `position` values.
**Decision:** (1) Name the new route `PATCH /journeys/:id/stages-order` (no slash before "order") — structurally unambiguous with the existing `/stages/:stageId` pattern, requiring no change to it. (2) Implement the handler using `pool.connect()` → `client.query('BEGIN')` → one `UPDATE` per stage → `client.query('COMMIT')`, with `ROLLBACK` in the catch branch and `client.release()` in `finally` — reusing `tenant-admin-bootstrap.js`'s `bootstrapTenantAdminIfNeeded` pattern verbatim (the only other transactional write in this codebase) rather than inventing a second convention.
**Rationale:** A distinct, unambiguous route avoids a latent routing bug that would only surface if a journey ever had (or a client ever sent) a stage id/name that happened to be the literal string `order` — cheap to avoid now, expensive to debug later. Reusing the existing transaction pattern rather than designing a new one keeps exactly one reference implementation for "how this codebase does atomic multi-row writes," which `/review` and future stories can point to.
