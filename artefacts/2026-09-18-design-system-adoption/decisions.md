# Decisions: Design System Adoption

## FEATURE-WIDE: the real CSS selector structure is inverted from earlier DoR/test-plan descriptions — `:root` is light, `[data-theme="dark"]` is dark (2026-09-19)

**Context:** `dsa-s1`'s (and every sibling story's) earlier Architecture Constraints described `html-shell.js`'s "`:root`/dark-mode blocks," implying `:root` held dark-mode values. Direct read at `/implementation-plan` time found the opposite: bare `:root` is LIGHT mode (the default — no attribute needed to activate it), `[data-theme="dark"]` on `<html>` is the DARK override (set by a real JS toggle at `html-shell.js:269-287`), plus a no-JS `@media (prefers-color-scheme: dark)` fallback block guarded to apply only when no explicit `data-theme` attribute exists. Also found: `--surface-2` and `--muted-3` don't exist yet in either mode (must be added new, not updated), and the current `--sans` font-family is `'Inter'`, while `DESIGN.md` specifies `'Inter Tight'` — a real, additional change beyond color tokens that the original restyle scope hadn't named.
**Decision:** Corrected `dsa-s1`'s own Architecture Constraints with the real selector structure and the additional font-family change. Did not re-run `/review`/`/test-plan`/`/definition-of-ready` again for this — the story's ACs themselves (user-facing "dark mode"/"light mode" states) were always correct; only the underlying CSS-selector implementation detail and the font-family scope were imprecise, corrected before any code was written, matching this session's own established discipline of fixing DoR-vs-real-architecture mismatches before implementation rather than after.
**Rationale:** Getting the selector direction backwards would have meant every one of `dsa-s1`-`dsa-s4`'s dark/light-mode tests targeting the wrong CSS block — caught and fixed before any implementation plan or code was written.
**Story:** dsa-s1 (corrected) — applies feature-wide to `dsa-s2`/`dsa-s3`/`dsa-s4`, which will each need the same correction (and the `--sans` font-family awareness) at their own `/implementation-plan` time.

## FEATURE-WIDE: `DESIGN.md`'s light-mode table is missing 3 tokens (`--line-2`, `--muted-2`, `--muted-3`) — values derived, not found (2026-09-19)

**Context:** `DESIGN.md`'s "Light mode" table lists only 10 of the 16 dark-mode tokens' light equivalents — `--line-2`, `--muted-2`, and `--muted-3` have no defined light-mode value anywhere. Confirmed via direct search of the real Style Guide mock (`Skills Platform - Style Guide.dc.html`, the document's own stated "source of truth for visual examples") — it uses inline hex values throughout (per `DESIGN.md`'s own rule 1: "no CSS variables inside `.dc.html` files"), so there is no named-token reference anywhere to recover these 3 values from. This is a genuine gap in the design system's own source materials, not something further searching can resolve.
**Decision:** Derived reasonable light-mode values by extending the same lightness-inversion relationship `DESIGN.md` already establishes for every other token pair (each dark value gets a light counterpart at the equivalent point on the opposite end of the lightness scale, preserving relative ordering among the muted variants): `--line-2: #EDEFF2` (slightly lighter than `--line`'s `#E4E7EB`, mirroring `--line-2`'s dark-mode relationship of being darker than `--line`), `--muted-2: #52585F` (darker than `--muted`'s `#6B7280`, mirroring the dark-mode ordering), `--muted-3: #3A3F45` (darkest of the three muted variants, mirroring dark mode's `--muted-3` being the darkest/least-prominent).
**Rationale:** Low-risk, reversible (color values only, not a structural decision), and follows the exact pattern the design system's own author already established for every other token — not inventing a new palette or a new relationship, just extending the documented one to the 3 tokens it omitted.
**Story:** dsa-s1 (uses these values in its own AC1/AC2 test assertions) — also applies feature-wide to `dsa-s2`/`dsa-s3`/`dsa-s4`, which will consume the same real values once added to `html-shell.js` by `dsa-s1`.

## FEATURE-WIDE: `--green`/`--amber`/`--red` cannot be renamed — must be added as aliases (2026-09-19)

**Context:** `dsa-s1`'s (and, by the same `/clarify` decision, every other restyle story's) Architecture Constraints instructed renaming `--green`/`--amber`/`--red` to `--success`/`--warn`/`--danger` in `html-shell.js`. Found at `/implementation-plan` time for `dsa-s1`: these old variable names are used in 25+ places across 8 files entirely outside this epic's 4 named screens — `settings.js`, `views/kanban-view.js`, `routes/journey.js`, `views/chat-view.js`, `routes/features.js`, `views/commit-view.js`, `views/features-view.js`, and dead-code `views/artefact-view.js` (confirmed via direct grep, with real sample usages read in `settings.js` and `kanban-view.js` — e.g. `.kb-health-on-track { border-left: 4px solid var(--green); }`). A literal rename would silently break every one of those screens' color-coded UI (an undefined CSS custom property resolves to nothing, not an error, so the breakage wouldn't even throw). This is a materially larger blast radius than this epic (or any single story in it) was ever scoped for — the epic's own Out of Scope explicitly excludes "any screen beyond the 4 named... as a hard requirement," but a shared-file variable rename doesn't respect story-level scoping the way markup changes do.
**Decision:** Presented to the operator with the corrected approach (add `--success`/`--warn`/`--danger` as NEW aliases, same hex values, alongside the untouched `--green`/`--amber`/`--red`) vs. the full 8-file rename vs. pausing; operator chose the aliasing approach. `dsa-s1`'s story updated to reflect this. **This decision applies feature-wide, not just to `dsa-s1`** — `dsa-s2`/`dsa-s3`/`dsa-s4`'s own Architecture Constraints sections (written before this finding) still say "rename" and will need the same correction before their own implementation begins, referencing this entry rather than re-investigating from scratch.
**Rationale:** Aliasing is strictly additive and carries zero regression risk to any of the 8 out-of-scope files, versus either a much larger unplanned rename (8 files, none of which have a story in this feature) or a full pause. The new names are still real, genuinely used by this epic's own 4 restyled screens — this isn't a workaround that avoids adopting `DESIGN.md`'s naming, it just doesn't force-migrate unrelated screens onto it in the same pass.
**Story:** dsa-s1 (Architecture Constraints corrected) — also affects `dsa-s2`/`dsa-s3`/`dsa-s4` (not yet corrected as of this entry; correct each at its own `/implementation-plan` time, referencing this entry).

## `dsa-s1` implementation-technique grounding: server-side sign-off-status detection, real pool relationship, and E2E-testability boundary for POST /sign-off (2026-09-18)

**Context:** Before writing `dsa-s1`'s implementation plan, three further real findings refined (not changed) the already-signed-off Architecture Constraints: (1) `handleArtefactRoute` already has the fetched markdown before rendering, so AC6's "already signed off" state can be determined server-side by calling the existing, already-tested `detectExistingSignOff(markdown)` function (`adapters/sign-off-writer.js`) once at render time — no client-side guess-then-fail POST needed. (2) `_userRolesPool` (the real migration-wiring pool every other module in `server.js` uses) and `_pshPool` (the pool `handleArtefactRoute` receives) are separate Node `Pool` objects but both connect to the same `DATABASE_URL` — confirmed via direct trace — so the new comments table's migration can be wired via `_userRolesPool` (matching precedent exactly) while `handleArtefactRoute` reads/writes it via `_pshPool`, with no cross-pool inconsistency. (3) `tests/e2e/sign-off.spec.js`'s own header comment and 3 `test.skip()` entries (already shipped, unrelated to this story) confirm the real backend success/409 round trip for `POST /sign-off` cannot be automated in E2E without real GitHub write access — deferred to manual verification since that story shipped. No `route.fulfill`-style response-mocking precedent exists anywhere in this codebase's E2E suite.
**Decision:** All three findings folded directly into the story's Architecture Constraints (not a new review round — these are implementation-technique clarifications of already-approved AC5/AC6 behavior, not new ACs or behavior changes). The test plan (below) follows the same manual-verification boundary this codebase's own existing sign-off tests already established, rather than inventing a new, unprecedented E2E mocking technique.
**Rationale:** Reusing real, already-tested functions and matching established patterns (migration wiring, E2E testability boundaries) is lower-risk than inventing new mechanisms, and keeps this story consistent with how the rest of this codebase already handles the exact same class of problem (a backend action requiring a real external write).
**Story:** dsa-s1 — no AC change; Architecture Constraints refined with real implementation grounding.

## `dsa-s1` major architecture correction and scope expansion: the real artefact viewer has no Sign-off/Comments UI; operator chose to build it, not just restyle (2026-09-18)

**Context:** `dsa-s1`'s DoR/story described restyling the artefact viewer's "two-column layout, Sign-off card, Comments card" to match `DESIGN.md`'s mock. Investigation at `/implementation-plan` time found this UI does not exist anywhere reachable in the real application:
1. `views/artefact-view.js`'s `renderArtefact` function is never imported or called by any real route — confirmed via a full codebase grep, only self-references and references inside `src/web-ui/port-extract/port/` (a separate ported/reference sub-project, not the live app).
2. `routes/sign-off.js`'s `handleArtefactRead` function is imported into `server.js` but never dispatched to any route — same dead-code pattern.
3. The REAL, reachable artefact page (`GET /artefact/:slug/:type` → `handleArtefactRoute` in `routes/artefact.js`) renders via a different function, `renderArtefactToHTML` (markdown→HTML), wrapped in `renderShellWithNav`'s generic single-column shell (`<div class="sw-doc">`) — no sidebar, no sign-off UI, no comments UI anywhere in this real rendering path.
4. A real `POST /sign-off` route exists and is dispatched (`handleSignOff` in `routes/sign-off.js`), but no real page anywhere renders a form or button with `action="/sign-off"` — confirmed via a full grep — so this action endpoint is real but currently has no UI entry point.
5. A real, generic-looking comments module exists (`modules/agency-client-comments.js`), but it is tightly coupled to a *different* feature's org-scoped model (`story-5-client-agency-comments`) — every real call site (`routes/products.js`) requires a `clientOrgId`/`agencyOrgId` tied to an `organisations` row with `org_type: 'agency'|'client'`. Reusing it as-is for artefact comments would misuse that model for users with no real agency/client relationship — the exact mock-shape-mismatch pattern `CLAUDE.md` warns against (`tir-s5` precedent).
6. Separately (unrelated, not fixed here): `agency-client-comments.js`'s own `migrateCommentsSchema` function is defined and exported but never called anywhere in `server.js` startup or the centralized `scripts/migrate-schema-*.js` migrations — the `comments` table this existing feature depends on is very likely never actually created in a real deployment. A real, pre-existing bug in a different, already-shipped feature, logged here for visibility, explicitly out of scope for `dsa-s1` to fix.

**Decision:** Presented to the operator with three options (restyle the real simple page only / build the full mock as new functionality / pause to look first); operator chose to build the full mock as new functionality — a real Sign-off UI wired to the existing `POST /sign-off` action, and a real Comments feature. For comments specifically, presented a further three options (reuse the org-scoped module as-is / build new generic comments infra / drop comments from this story); operator chose to build new, generic comments infrastructure scoped simply by resource + user, with no `org_id`/`org_type` dependency — and to correctly wire its migration at server startup this time, not repeat the orphaned-migration mistake found in the existing agency-client comments feature.
**Rationale:** This is a real, deliberate scope expansion the operator explicitly chose after being shown the actual gap between the design mock and the real shipped application — not a silent absorption of new scope into an existing story. Given the ACs and touched surface are now materially different from what `/review`, `/test-plan`, and `/definition-of-ready` already signed off on, `dsa-s1`'s story will be amended and re-run through `/review` → `/test-plan` → `/definition-of-ready` before any implementation plan is written, per the operator's own explicit choice of the "full re-run" process option over a lighter-weight alternative (splitting into a separate story).
**Story:** dsa-s1 — story, DoR, test plan, and review artefacts will all be amended/re-run to reflect this expanded scope.
