## `dsa-s4` Task 4: `npm test` found 4 genuine regressions from Tasks 1-3 (not environmental) — root-caused and fixed forward by updating 4 pre-existing check-scripts' assertions to match the new, approved architecture (2026-09-20)

**Context:** The full local E2E regression pass (previous entry) found only already-documented pre-existing/environmental failures. The full Node `npm test` suite told a different story: 6 failures, only 2 of which (`check-p3.5-validate-trace.js`, `check-pcr-s1-test-runner.js`) matched the acknowledged baseline. The other 4 — `check-cdpl-s1-canvas-panel-layout-fix.js`, `check-inc2.1-conditions-panel.js`, `check-iwu2-right-panel-layout.js` (a Node-level check, distinct from the same-named Playwright spec already covered), `check-mfc2-chat-ux-improvements.js` — were genuinely new, unlike anything seen in any prior task's own regression check (which only ran E2E specs, never the full Node suite until this step).
**Investigation:** Ran each failing check-script directly and read its exact failing assertion.
- **3 of the 4** (`cdpl-s1`, `inc2.1`, `iwu2`) shared one root cause: each asserted a literal `max-height` (or `max-height:42%`) inline style on a specific content element (`#artefact-panel`, `#condition-items`, `#assumption-cards`). Task 3's own plan explicitly specified "replacing the current fixed `max-height%` divs" with a resizable wrapper — this was the plan's own intended outcome, not an accident, but it silently broke 3 pre-existing check-scripts from earlier, unrelated stories (`cdpl-s1`, `inc2.1`, `iwu2`) that encoded the old mechanism as a literal invariant. Confirmed via direct inspection of the real rendered HTML: the height cap is now expressed as `flex:0 0 <pct>%` + `overflow:hidden` on a new wrapping `.sw-resize-group` div (`#sw-artefact-top-group`, `#sw-ideate-cond-group`, `#sw-ideate-assum-group` respectively) — the content element itself is no longer height-capped directly, its ancestor is.
- **The 4th** (`check-mfc2-chat-ux-improvements.js`'s T2.2) was a different class of conflict: an earlier story (`mfc.2`) added a blanket prohibition against any numeric question-count text ("3 of 7", "questions remaining") appearing anywhere in `renderChat()`'s output, written when only one chat view existed. Task 2's new, approved Focused-mode view legitimately displays exactly this pattern in its own progress indicator (`id="sw-focused-progress-label"`) — required by `DESIGN.md`'s own mock and this story's own AC3. Confirmed via direct string search that the count text appears ONLY inside the new `#sw-focused-view` container, nowhere in the default Chat view's own sub-heading (`mfc.2`'s actual original concern, per its own test name).
**Decision:** Fixed forward (narrow, well-understood, directly reasoned) by updating each check-script's specific failing assertion to match the new, legitimate architecture, rather than reverting Task 3's plan-specified design or suppressing Task 2's approved new feature:
- `cdpl-s1`/`inc2.1`/`iwu2`: each assertion now checks the new wrapping `.sw-resize-group` element for `flex:0 0 <pct>%` + `overflow:hidden` instead of checking `max-height` on the content element — preserving each check's original protective intent (the content section must not be allowed to grow unboundedly and squeeze its siblings) against the new, correct mechanism.
- `mfc2`: T2.2's assertion now scopes its "no question count" check to everything before the `#sw-focused-view` container's opening tag (the actual default-Chat-view content the AC was originally written to protect), rather than the whole page — preserving the original protection against clutter in the DEFAULT view while permitting the new, approved, opt-in Focused view's own progress indicator.
Every fix is documented with an inline code comment in the check-script itself explaining the change and cross-referencing this entry. Re-ran all 4 fixed scripts individually (16/16, 31/31, 14/14, 8/8 passing respectively) and the full `npm test` suite (683 files, 1 failure — only the already-acknowledged `check-p3.5-validate-trace.js`; `check-pcr-s1-test-runner.js` did not fail this run, consistent with its own documented marginal/inconsistent nature). Also re-ran the story's own `dsa-s4-chat-restyle.spec.js` (10/10) to confirm the check-script edits introduced no new breakage.
**Rationale:** This is the "update the check-script to match the new, approved architecture" case (analogous to CLAUDE.md's B1/D1 rule for DoR contracts: "the contract is the authoring defect... update to match"), NOT a case of weakening a real protection to make a failure go away — in each case I traced the exact new location/form of the original protection (a height cap now expressed via flex-basis+overflow on an ancestor; a clutter-prevention rule now correctly scoped to exclude a new, deliberately-approved UI surface) and updated the assertion to verify that new form precisely, not to simply delete or loosen the check. This is exactly the class of finding Task 4's full-suite regression pass exists to catch — three separate pre-existing stories' own regression tests, silently broken by this story's legitimate, plan-approved architectural change, would have shipped undetected if Task 4 had only re-run E2E specs (as every prior task's own regression check did) rather than the full Node suite.
**Story:** dsa-s4 — no AC change; these are test-assertion corrections in 4 other stories' own pre-existing check-scripts, tracking their real current architecture, not a change to `dsa-s4`'s own scope.
