**2026-11-17 | DECISION (lpw-s2) | The core is chosen by a stated rule from a per-spec measurement, not by hand**
**Context:** the operator wants a required core cherry-picked across specs by capability with no loss of capability or product coverage.
**Decision:** each local spec ran alone on a fresh server and its executed `src/web-ui` statements were recorded (`evidence/per-spec-coverage.md`). `scripts/select-core-specs.js` picks, first, the best passing spec for every capability, then more passing specs by new statements added until the next adds under 0.1 percentage point; specs that failed in the measurement or in either `lpw-s1` run are never chosen. Result: 27 spec files, 110 tests, 99.3% of the statements every passing spec reaches together (`evidence/core-coverage.md`).
**Rationale:** the browser specs differ little in server code (booting the server alone executes about 32% of the statements), so capability first and small unique gains second is the only stable way to pick; and the numbers make "no loss" checkable.

**2026-11-17 | DECISION (lpw-s3, AC8, issue #1141) | The board reads "ready" from the journey's own completed-stage record when the session is gone**
**Context:** after a restart or deploy the in-memory session store is empty and done sessions are deliberately never restored from Redis, so every card showed "not ready" until its chat was opened.
**Decision:** the durable fact is the journey's `completedStages` entry, which `completeStage` writes when the session finishes and its artefact is saved, and which carries the id of the session that completed the stage. A card is ready when its active session is in memory and done, or, only when that session is no longer in memory, when the journey has a completed-stage entry for that exact session id. A live session that is not done (a stage being revised) is never overridden. Advance rebuilds the done session in memory from that entry (artefact read from disk, then the saved Postgres copy; `_stageDone` true so gate-confirm does not commit it again) before running the real gate-confirm.
**Rationale:** it is already stored, needs no new table or query, and matching on the session id avoids marking a card ready because an earlier session of the same skill completed. Entries without a session id (older records) are not treated as ready; the card stays "not ready" until its chat is opened, as before.
**Limits:** no PostHog or staging evidence of how often it happens; verified by T6, T7 and the real-server test T4f (session evicted, card still ready, Advance moves it).

**2026-11-18 | DECISION | lpw-s4: seed the team roster through a test-only route into the fake database, and drive the real Add flow in the pod specs**

**Decision:** `POST /test/seed-team-member` (test mode only, same inline guard as its sibling seed routes) writes a person, an identity and a membership into the fake database through `_seedTeamMember`, once per identity, validating the identity (plain login string) and the role against the real team roles. A shared helper `tests/e2e/fixtures/pods.js` seeds and drives Add, Pod role and Confirm. The specs seed what they need, use the real flow, and no longer assert on an empty or exact-sized org.
**Rationale:** the fake database already answered the real roster query, so no product code changes (checked by T5); the real add-teammate flow looks the identity up on GitHub and cannot be used in tests. The ep4 modal now asserts "at least these two pods" because pods from earlier specs persist in the shared in-memory org.
**Limits:** the specs share the `e2e-tester` tenant and the in-memory org with the rest of the core, so they pass under `--workers=1` (as the core job runs) and can race under parallel workers, as other specs already do. Verified: the whole core in CI order, twice (120 passed, 3 skipped, 0 failed).
