# Decisions: staging steps retry once (sfr-s1)

## D1. One retry on the three staging commands only, flaky tests listed not enforced, two ledger entries (2026-11-21)

**Context:** the deploy-group investigation (findings note, 2026-11-21) showed 4 of 5 completed staging deploys failed on flaky assertions, not on the lock, and that a single failure blocks the promotion until someone re-runs the workflow by hand. The repository default is no in-run retries; `tests/FLAKE-POLICY.md` allows them provided every test that passes on retry has a ledger entry.
**Decision (operator, 2026-11-21, "Go" on option B, recommended as "A plus B"):** add `--retries=1` only to the staging smoke command and the two post-deploy confirmation commands; keep the global default off; write a Playwright JSON report for each and append the `flake-check --report` list to the step summary (non-strict); record the two identified flaky tests in the ledger with owner heymishy, tracking issue #1181, first seen 2026-11-21 and review by 2026-12-05.
**Rationale:** a retry clears a one-off blip, which is what four of the failures were; keeping it to the three promotion-gating commands bounds the exposure; the report keeps every flaky pass visible; the ledger gives each flake an owner and a deadline so it is a debt with a date, not an excuse.
**Alternatives rejected:** a global `retries` in `playwright.config.js` (would also retry pull request jobs and local runs and hide real failures there); `--strict` in the deploy workflow (a new flake that passed on retry would fail the run, which is the blocking behaviour being removed); retries on the pull request Scenario A and B jobs (they are required checks and a separate decision); fixing the causes first (the gateway abort and the fixed 5-second round-trip threshold need investigation and the promotion is blocked now).
**Risk accepted:** a retry can mask a real intermittent bug. Mitigations: the two tests are in the ledger with a 14-day review, flaky passes are listed in each run's summary, a test that fails twice still fails the run. **Time-dated consequence:** from 2026-12-06 `check-flk-s1` T6 fails on every pull request unless the two entries are reviewed (fixed, removed, or re-dated with a reason in `note`).
**Operator approval:** one tracking issue, #1181, was created on 2026-11-21 after the operator chose "Create one tracking issue (Recommended)"; the operator is the owner of the ledger entries.
