Once moved, the AC1 fix (sourcing `COPY_DIRS` from `skills/`/`templates/`) picks them up automatically, and this also removes their exposure to F15/`csdg-s1`'s separate `.github/skills/`-default-resolution gap (once that story's own fix lands, every skill including these 5 resolves correctly via the corrected default).
**Note:** this leaves `.github/skills/` and `.github/templates/` empty after the move — expected and correct, since those directories' only real role (per F15's own investigation) is as the bootstrap-install *destination* for consumer repos, not a source directory in this repo.

## Fourth instance of the same bug, found via CI (not local) — `scripts/assemble-copilot-instructions.sh`

**Date:** 2026-08-22
**Context:** PR #753's "Lint, typecheck, test, build" CI check failed on 2 files: `tests/check-rb-s3-harness-agnostic-instructions.js` and `.github/scripts/check-assembly.js`. Both passed locally on Windows (`node <file>` → 0 failures) because both tests gate their real assertion behind `if (process.platform !== 'win32') return 'bash';` — on Windows the test silently no-ops the actual bash-script invocation it exists to verify, so a local Windows pass gives no real signal for this path. CI runs on Linux, where the real `bash scripts/assemble-copilot-instructions.sh` invocation genuinely executes.
**Investigation:** `assemble-copilot-instructions.sh` (used to assemble this repo's own `copilot-instructions.md`/`CLAUDE.md`/etc. from SKILL.md content) had the same stale `.github/skills` source assumption as `platform-init.js`/`platform-fetch.js`/`repo-bootstrap.js` — both in its self-detection (`if [[ -d "$REPO_ROOT/.github/skills" ]]`) and its `SKILLS_DIR` variable. A fourth instance of the identical root cause, found this time via CI rather than local `npm test`, since the local Windows path structurally cannot exercise it.
**First fix attempt was too broad and had to be corrected:** simply swapping `.github/skills` → `skills` unconditionally broke a different, legitimate caller — `cli/lib/init.js`'s `--all-harnesses` step (`installFullSkillSetAndRegistry`, story `rb-s3`) invokes this same script with `--skills-repo-path <freshly-bootstrapped-target-repo>`, where the *target* genuinely only has `.github/skills/` (its own post-bootstrap copy), not root `skills/`. Caught locally via direct `bash scripts/assemble-copilot-instructions.sh` invocation (bypassing the Node test's win32 skip) before pushing, which reproduced `runInitAloneProducesAllFourHarnessFiles_wiredIntoBootstrap`'s failure the same way CI would have.
**Final fix:** `SKILLS_DIR` now prefers `$SKILLS_REPO_PATH/skills` (the canonical skills-repo's own real source) and falls back to `$SKILLS_REPO_PATH/.github/skills` when the former doesn't exist (an already-bootstrapped consumer/target repo, which correctly has only the latter) — handling both real callers correctly. Verified directly via `bash` for both cases (this repo's own root, and a synthetic target directory with only `.github/skills/` populated) before relying on `node`'s win32-skipped test wrapper, since that wrapper cannot itself prove the fix works.
**Lesson:** this session's local Windows verification loop has a structural blind spot for any check gated on `process.platform !== 'win32'` — a Windows-local pass on such a file is not evidence, only a CI-green (or a direct non-Node bash invocation, as used here) is. Worth flagging as a general pattern for future stories touching `.sh` scripts in this repo.

**Decision:** Include both fixes in this story rather than opening separate findings, since AC4 and AC6 as literally written could not otherwise be honestly satisfied — leaving `platform-fetch.js`/`repo-bootstrap.js` broken while claiming "no regressions" would be false. Logged here per `/verify-completion`'s Step 3 scope-creep check, and will be called out explicitly in the PR description.
**Rationale:** All three scripts (`platform-init.js`, `platform-fetch.js`, `repo-bootstrap.js`) share one root cause (the `.github/skills/`/`.github/templates/` → `skills/`/`templates/` repo-root migration, commit `1b1d0682`, never propagated to every source-path reference). Fixing one and leaving the other two broken would be an incomplete, inconsistent fix for what is genuinely a single underlying defect with three symptoms.
