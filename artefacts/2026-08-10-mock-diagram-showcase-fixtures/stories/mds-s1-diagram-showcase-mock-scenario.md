## Story: Add a richer mock-gateway scenario covering every diagram type a skill session can legitimately emit

**Epic reference:** None — short-track (test-infrastructure enhancement, found while validating drh-s1 on staging)
**Discovery reference:** None — short-track skips discovery; scope is the code-derived gap below
**Benefit-metric reference:** None — short-track skips benefit-metric; benefit linkage stated directly below

## User Story

As an **operator validating that diagram rendering works correctly across every skill stage**,
I want **a mock-gateway scenario that exercises every diagram type a real session can legitimately produce**,
So that **I can confirm diagram rendering (live and resumed/historical) works end-to-end without spending real LLM tokens, and future changes to the canvas-rendering mechanism get caught by tests that actually cover the full type range, not just one type per stage**.

## Benefit Linkage

**Metric moved:** Direct test-infrastructure gap (short-track, no formal benefit-metric artefact) — found while live-validating `drh-s1` (the resume-history diagram fix) on staging: the existing mock-gateway fixtures (`tests/e2e/fixtures/llm-gateway/{ideate,design,definition}.success.json`) each contain exactly one `---CANVAS-JSON:...---` marker, one type each (`cluster-tree`, `system-architecture`, `program-design`). None of the other types a real session can legitimately emit — `table`, `text` (both `/ideate`, per its lens-output convention), `data-model` (both `/design` and `/definition`, per their own SKILL.md instructions) — are exercised by any mock fixture at all. Since `getMockResponse(stage, model, scenarioName)` returns the identical canned response for every turn in a session, a mock-driven multi-turn `/ideate` conversation also cannot simulate a realistic multi-lens progression (Lens A/B/C/D/E, each potentially emitting a different content type) — every turn repeats the same single Lens-A/cluster-tree marker.

**How:** Add a new `scenarioName` value (`diagram-showcase`) alongside the existing `success`/`failure` scenarios, with one new fixture file per diagram-capable stage (`ideate.diagram-showcase.json`, `design.diagram-showcase.json`, `definition.diagram-showcase.json`), each containing multiple markers of different, skill-legitimate types in a single response. This is purely additive — the existing `success` fixtures (and every test/E2E spec that depends on their exact current content, notably `check-a3-ideate-artefact-disk-match.js`'s hard assertion that `ideate.success.json` contains *exactly one* marker) are never touched.

## Architecture Constraints

- **New fixture files only — never modify `{ideate,design,definition}.success.json`.** `check-a3-ideate-artefact-disk-match.js` explicitly asserts `ideate.success.json` has exactly one marker; `design.success.json`/`definition.success.json` have no such hard-coded test found, but the safe, zero-regression-risk path is additive regardless.
- **Diagram types per fixture must match what that skill's real SKILL.md instructs it to emit** — not an arbitrary assortment:
  - `ideate.diagram-showcase.json`: `cluster-tree`, `table`, `text` (the three manual content types `/ideate` emits per lens, per `skills/ideate/SKILL.md`).
  - `design.diagram-showcase.json`: `system-architecture` (emitted once, end of session) and `data-model` (emitted per relevant story), per `skills/design/SKILL.md`.
  - `definition.diagram-showcase.json`: `program-design` (emitted once) and `data-model` (per relevant story), per `skills/definition/SKILL.md`.
  - `drift-signal` is explicitly out of scope (see below) — it is generated by the separate as-built-comparison mechanism (`csd-s6`/`csd-s7`), not emitted during a live skill session.
- **`inventoryFixtures()`'s existing stage/scenario counting logic must continue to work unchanged** — a new scenario name is exactly the extensibility point that function's own doc comment describes; no change to `inventoryFixtures` itself should be needed.
- **`getMockResponse`'s single-response-per-stage behaviour is not changed by this story.** Multiple markers within ONE response (simulating several lenses' worth of output in one turn) is the chosen, bounded approach — building true per-turn cycling through multiple canned responses would be a separate, larger mock-gateway architecture change, explicitly out of scope here.

## Dependencies

- **Upstream:** None — extends already-shipped mock-gateway infrastructure (`bri-s3.1`) and diagram-emission instructions (`csd-s1`–`csd-s4`).
- **Downstream:** None known. Does not block or require `drh-s1` (already merged) — this is a follow-up validation-coverage improvement, not a fix to it.

## Acceptance Criteria

**AC1:** Given `getMockResponse('ideate', model, 'diagram-showcase')` is called, When the response is inspected, Then it contains three valid, parseable CANVAS-JSON markers of types `cluster-tree`, `table`, and `text`, each with realistic lens-shaped content (not placeholder/lorem text).

**AC2:** Given `getMockResponse('design', model, 'diagram-showcase')` is called, When the response is inspected, Then it contains two valid, parseable CANVAS-JSON markers of types `system-architecture` and `data-model`, each with realistic mermaid content.

**AC3:** Given `getMockResponse('definition', model, 'diagram-showcase')` is called, When the response is inspected, Then it contains two valid, parseable CANVAS-JSON markers of types `program-design` and `data-model`, each with realistic mermaid content.

**AC4:** Given the existing `success`/`failure` scenario fixtures for `ideate`/`design`/`definition`, When this story's changes are complete, Then those three files are byte-for-byte unchanged from before this story (verified by a checksum/diff assertion in the test).

**AC5:** Given `inventoryFixtures()` is called after the new fixtures are added, When its output is inspected, Then it correctly reports the new `diagram-showcase` files alongside the existing `success`/`failure` ones for each of the three stages, with no change to how `success`/`failure` are counted.

**AC6:** Given a mock session is driven through `diagram-showcase` for `ideate`, `design`, or `definition` and its stage is completed, When the completed stage is viewed via `/journey/:id/stage/:stageName` (the `drh-s1` resume-history view), Then all markers from that stage's response render as distinct diagram blocks — proving this new fixture data actually exercises the full rendering path, not just the extraction/parsing layer.

## Out of Scope

- **Modifying the existing `success`/`failure` fixtures** — additive only, per Architecture Constraints.
- **`drift-signal` diagram type** — generated by the separate as-built-comparison mechanism, not a live skill-session output; not relevant to this story's mock-scenario purpose.
- **True per-turn response cycling in the mock gateway** — a separate, larger architecture change; this story simulates multiple lenses' worth of diagram content within a single canned response instead.
- **Wiring a UI control to select the `diagram-showcase` scenario** — reachable the same way `failure` already is (however that's currently selected/tested), no new UI needed.
- **`review`/`test-plan`/other non-diagram-capable stages** — `supportsCanvas` is `ideate`/`design`/`definition` only today; out of scope to extend that.

## NFRs

- **Correctness:** Every new fixture's marker content must be genuinely parseable by the existing, unmodified `parseCanvasBlock`/`extractCanvasBlocksFromTurns` — no new parsing logic introduced or needed.
- **Test isolation:** AC4's byte-identical-existing-fixtures guarantee is the primary safety property this story must not compromise — a regression here would silently break `check-a3-ideate-artefact-disk-match.js` and the `a3` E2E spec.

## Complexity Rating

**Rating:** 1 — well-understood, additive-only: new fixture files with hand-authored, skill-legitimate content, no changes to any existing rendering/parsing/extraction code.
**Scope stability:** Stable
