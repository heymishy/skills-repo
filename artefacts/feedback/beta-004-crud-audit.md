# CRUD Audit: 2026-08-16 (operator-requested, systematic pass)

**Source:** Hamish King (operator), following a live-product review where he noticed several core domain concepts have no visible way to edit them after creation (e.g. "can't rename a product/org/feature").
**Status:** Complete. Audited against the current `master` source (`src/web-ui/routes/*.js`, `src/web-ui/modules/*.js`, `src/web-ui/server.js`'s central route table). Not validated live against `skills-framework.fly.dev` — this is a static-code audit of what exists and what is wired, not a browser walkthrough. Recommend a quick live spot-check on the three named examples (product/org/feature rename) before scoping fixes, in case a flag or role gate hides something the code otherwise supports.
**Scope:** Server-side route handlers (all matched in `server.js`'s manual `pathname`/`method` router — this app is a plain Node `http` server, not Express, so there is no router-level route table beyond this one file) cross-referenced against every `fetch(...)`, `<form action=...>`, and `<button onclick=...>` in the corresponding route file's own rendered HTML/JS.

---

## Method note

Two things are tracked separately per the operator's framing:
1. **Does a server-side handler exist for this verb+concept combination at all?** (checked via `server.js`'s route table, which lists every `pathname === '...'` / `pathname.match(...)` branch and the handler it dispatches to)
2. **Does anything in the rendered UI actually call it?** (checked by grepping the owning route file for literal and variable-method `fetch(...)` calls, `<form action=...>`, and `onclick=...` handlers that target that exact path — not just "does a similarly-named function exist somewhere")

A route that exists only because a test file calls it directly (bypassing the browser entirely) is UI-unreachable by this definition, same as a route with zero references anywhere.

## The three named examples

The operator specifically flagged "can't rename a product, an org, or a feature" as the trigger for this audit. Checked precisely, the three break down into three *different* root causes:

1. **Product rename — confirmed true. Missing UI control, NOT a missing endpoint.** `PUT /products/:id` already does exactly this server-side (`handlePutProductEdit`, AC1: "Update name/description if provided"). The fix is adding a name/description input + submit handler to the product view page and pointing it at the existing route with `{name, description}` in the body — no new backend work. Small, low-risk fix.

2. **Organisation rename — confirmed true, and it's the worst of the three. Missing endpoint, not just missing UI.** There is no `UPDATE organisations SET name = ...` anywhere in the codebase, no adapter function, no route. The only UPDATE statement against the `organisations` table changes `org_type`, never `name`. This needs a new adapter function (e.g. `updateOrganisationName(pool, orgId, name)`), a new route (`PUT /organisations/:id` or similar), a role gate (presumably admin-of-own-org, mirroring `_isAdminOfOwnOrg` in `org-conversion.js`), and a UI control — a bigger fix than Product's, comparable in shape to the module-rename pattern already proven in `products.js`.

3. **Feature rename — the operator's assumption does not hold. This one already works end-to-end.** `PUT /api/journey/:id/display-name` plus a "✎ Rename" button on every feature row (`pshRenameFeature`, story fdn-s1) is fully wired and reachable today. Worth flagging back to the operator directly: either this was fixed after the review that prompted this audit, or the small pencil-icon button (12px font, muted color, positioned as a sibling link rather than a prominent action) is easy to miss in a quick pass over the product page. If it's a discoverability problem rather than a real gap, that's a much smaller fix (visual prominence) than what "no rename capability" would imply.

## Cross-cutting reads

**"Feature" and "Journey" are the same underlying entity, not two concepts.** Every feature-facing route (`/products/:id/features`, `/features/:slug`, the "New feature"/rename/delete UI) ultimately reads and writes the `journeys` table via `journey-store.js` / `journey-store-pg.js`. The operator's original list named them separately; this audit treats them as one row to avoid double-counting the same CRUD surface twice. `/journey/:id`, `/api/journey/:id`, and the whole `journey.js` route file are the same "Feature" concept viewed through its per-stage execution lifecycle rather than its product-catalogue listing.

**The Module rename gap already happened once, and the fix pattern is proven.** `products.js`'s own comment on `_renderModulesManagement` (line ~614) records that Module CRUD shipped with a working API and *zero UI* in an earlier story, and was only made reachable in a dedicated follow-up fix ("fix-forward, post-a1"). That fix — a `submitJson()` helper posting to the existing REST-shaped routes, with inline rename-forms and delete-buttons per row — is a directly reusable pattern for closing the Product-rename and Org-rename gaps found here. This has already been solved once in this exact codebase; it doesn't need to be re-invented.

**Team member management has a "blind upsert" problem, not just a missing Delete.** Even though Update technically works (same form, upsert semantics), there is no way to see who is currently a team member or what role they hold before re-submitting the form. Read and Update are entangled here in a way the table's per-column format doesn't fully capture: Update is only *safely* usable once Read exists. Recommend treating "list team members with current roles" as the higher-priority half of any team-management fix, ahead of building a dedicated remove/delete route, since Update is already silently blocked by the missing Read in practice.

**Organisation is the thinnest domain concept in the app.** Every other audited concept (Product, Feature, Module, even Guardrail) has at least a real Read view. Organisation has none — not even a page that shows its own name. This is consistent with the codebase's architecture: `tenant_id`/`org_id` has historically been treated as a bare scoping string (ADR-025's own framing), and `organisations` only became a first-class table recently (story-1-organisation-entity, 2026-07-30) to support agency/client relationships — it was never built as something an end user directly views or manages. The operator's instinct that org rename is missing is really pointing at a broader fact: Organisation-as-an-entity has almost no user-facing surface at all yet, rename included.

## Prioritized recommendations

1. **Product rename UI control** — smallest fix in this audit. Endpoint already correct; add a name/description field + form to the product view, pointing at the existing `PUT /products/:id`. No new backend work, no new DoR story needed beyond the UI change itself (though per this repo's own Artefact-first rule, a short-track story artefact is still required before implementation).

2. **Organisation rename (endpoint + UI)** — the real gap behind the operator's report. Needs a new adapter function, a new route, a role gate, and a UI control. Use the Module-rename pattern in `products.js` as the reference implementation — same shape, same upsert/PUT-based approach, already proven in this codebase.

3. **Team member list (Read)** — currently the missing half of an already-working Update. Unblocks safe use of the existing role-upsert form and is a natural pre-requisite for any future remove/delete route. Comparatively cheap: a single joined query (`team_memberships` + `people`) and a table on the existing `/team/members` page.

4. **Team member remove (Delete)** and **team invite revoke (Delete)** — both entirely missing server-side, not just UI gaps. Group these together; they're the same shape of fix (a DELETE route + a confirming UI control, mirroring the Module-delete and Feature-delete precedents already in the codebase) applied to two adjacent concepts.

5. **Guardrail/standard delete** — missing entirely. Lower priority than the above since guardrails are file-backed (written via PR to the connected repo), so "deletion" arguably belongs in the same PR-based write flow `wugs-s6` already built for create/edit, not a bare DB delete — worth a design decision (`decisions.md`) before scoping, not a mechanical fix like the others.

6. **Epic module-reassignment UI** and **feature-rename discoverability** — smaller, lower-severity items. The epic-module PUT route has no UI at all (dropdown or drag-and-drop needed); the feature-rename button already works but may be too visually subtle to have been noticed during the operator's review that triggered this audit — worth a quick live check before assuming it needs a code fix at all.

Not recommending action on: Epic create (N/A by design — AI-generated), Story update/delete (would need real design thought about what "editing a story after definition" even means in this pipeline — bigger than a mechanical CRUD fix), Org delete (N/A, reasonable to leave unbuilt).
